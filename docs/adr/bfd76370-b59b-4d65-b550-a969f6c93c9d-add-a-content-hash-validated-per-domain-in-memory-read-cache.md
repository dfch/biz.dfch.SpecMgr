# Add a content-hash-validated, per-domain in-memory read cache for the 12 generic whole-body domains

## Context and Problem Statement

get_*/list_* MCP tool calls currently re-scan and fully re-parse an entire domain directory on every single invocation (general/tools/_doc_paths.py:find_doc_path_by_id, general/tools/_listing.py:build_summaries). ADR 33c5ab08-ff58-4c73-8c32-23abaf3838e3 deliberately rejected an in-memory id-to-document cache to guarantee correctness under concurrent hand-edits, so today every read pays full markdown-it tokenizing plus nested Pydantic validation cost, on every call, for every candidate file scanned. This is CPU-bound work that holds the GIL, so it serializes regardless of how many threads/cores are available -- and is the real cause behind GitHub issue #107's reported timeouts under parallel get_* calls. The literal ask in issue #107 ("use a thread pool with concurrent workers") does not address this: the installed MCP SDK already offloads every sync tool call to an anyio worker thread (anyio.to_thread.run_sync, CapacityLimiter(40)), so adding a second thread pool would not help CPU-bound, GIL-holding work. The question is: how do we eliminate the redundant re-parsing cost without reintroducing the staleness risk ADR 33c5ab08 was written to prevent?

## Decision Drivers

Eliminate redundant CPU-bound re-parsing on repeated get_*/list_* calls without reintroducing any risk of serving stale content after a concurrent hand-edit or LLM-driven edit; keep the fix process-local and simple (no cross-process cache, no new dependencies); fix the existing get_* matched-file double-parse bug (the id-lookup scan parses a file, discards the result, then the caller re-reads and re-parses the same file again) as a structural side effect rather than a separate patch; keep the change scoped to the 12 generic whole-body domains that already depend on the shared general package, leaving the (separately phased-out) ADR domain untouched.

## Considered Options

(1) Do nothing -- accept full re-parse cost on every call, per ADR 33c5ab08's original decision. (2) Add a literal thread pool per GitHub issue #107's literal wording. (3) A frontmatter-only fast-path parse for the id-lookup scan (skip body parsing when only routing by id). (4) A process-local, per-domain, content-hash-validated in-memory read cache (dict[Path, tuple[content_hash, result]]) that skips re-parsing when a file's current on-disk content hash matches the hash recorded at last read, reconciled against the live directory listing on every scan.

## Decision Outcome

Chosen option: (4), a process-local, per-domain, content-hash-validated in-memory read cache. Each of the 12 generic whole-body domains (req, uc, tsk, qa, prb, gol, rsk, dec, sop, feat, vcr, sysrs) gets its own module-level singleton cache instance -- mirroring the existing per-domain threading.Lock registries in each domain's _lock.py -- shaped as dict[Path, tuple[content_hash, result]], where result is either the successfully parsed document or the exception a prior parse attempt raised (failure caching: a hash match against a previously-failing entry re-raises the stored exception without re-invoking the parser; only a hash change triggers a fresh attempt, so a persistently malformed file is not re-parsed on every scan that touches it). The hash is computed with hashlib.blake2b over the file's full text on every access, before deciding whether to skip parsing. Both get_*'s find_doc_path_by_id scan and its final matched-file load, and list_*'s build_summaries read callback, route through the same per-domain cache instance and read_fn, so a file parsed once during a get_* call's scan is never parsed a second time within that same call -- this also fixes the existing matched-file double-parse bug as a structural consequence, with no change to find_doc_path_by_id's return type (still a bare Path) and therefore no change to the update/delete/set_status call sites that only ever wanted the path. Every write path (create_<domain>, and the generic update/set_status/set_classification tools) warms the cache entry for the file it just wrote by invoking the domain's cache-backed read_fn on that path once, immediately after the write succeeds. The generic delete tool invalidates the cache entry for the file it removes; set_feat_id moves the cache entry from the old path to the new one, but only after write_feat_file succeeds, never at the earlier folder-rename step, so a failure in between never leaves a cache entry addressing a file that was never written. Both get_*'s directory scan and list_* reconcile the cache against the current on-disk directory listing on every call, dropping any cached entry whose path no longer exists, so a file deleted outside specmgr's own tooling does not leak in memory indefinitely. Reconciliation with ADR 33c5ab08-ff58-4c73-8c32-23abaf3838e3: that ADR's invariant is "the filesystem is the sole source of truth"; this cache REFINES rather than violates that invariant. A stale entry is structurally impossible, because the content hash is re-validated on every access: any on-disk change (whether by an MCP tool, a human hand-edit, or an LLM-driven edit made outside this server) is always detected on the very next access to that path, and a cache hit only ever saves a redundant re-parse of byte-identical content -- it never serves content that does not match what is currently on disk. The filesystem remains the sole source of truth; the cache is purely a memoization of "we already validated that this exact byte sequence parses to this result," not a substitute read path. Explicitly out of scope: the ADR domain (models/adr/v1) itself is NOT wired into this cache mechanism. ADR is expected to be phased out later and does not justify its own independently-implemented cache module, since (unlike the 12 generic domains this decision covers) it has no dependency on the shared general package that hosts the new cache/lock/dispatch machinery; adr/tools/_io.py and adr/tools/_paths.py continue to re-read and re-parse on every call, unchanged, per ADR 33c5ab08. Lock ordering (pinned as a fixed rule, not merely a convention): the cache's own internal lock guards ONLY its dict get/set/pop operations -- it is never held across the file read or parse call itself, so concurrent reads of different files never block each other on the cache's own bookkeeping. This lock is ALWAYS the innermost lock acquired in any call stack: it is acquired strictly after any domain-level per-id lock (e.g. req_lock(id), or feat's fixed feat_create_lock() -> feat_lock(id) order that set_feat_id already documents and enforces -- feat_create_lock() outermost, feat_lock(id) nested inside it, never swapped), and it is never held while acquiring a domain lock. This introduces no lock-ordering rule inconsistent with any existing one in this codebase.

### Consequences

Positive: get_*/list_* calls against an unchanged file no longer pay repeated markdown-it/Pydantic parsing cost, directly addressing the CPU-bound bottleneck behind GitHub issue #107 without touching the MCP SDK's own (already adequate) thread-pooling. The existing get_* matched-file double-parse bug disappears as a structural consequence of sharing one cache between the id-lookup scan and the final matched-file load. Reconcile-on-scan closes the one real leak scenario (a file deleted outside specmgr's own tooling) without needing TTL/LRU eviction. Negative / trade-offs: one additional module-level singleton and lock per domain, requiring an explicit test-only reset/clear hook so tests do not leak cached entries across test cases within the same process; a persistently malformed file's exception object is now held in memory until its content changes; the cache remains process-local (no cross-process sharing), the same limitation the existing per-id threading.Lock registries already have; the ADR domain's own read path remains fully unoptimized, a deliberate and accepted scope exclusion given its expected phase-out. No TTL/LRU eviction and no stat() mtime/size fast path are implemented in this first version; measured memory footprint (parsing this repo's 32 real ADR documents, 208,057 raw bytes, occupies 386,761 bytes parsed -- a ~1.86x multiplier over raw text) shows this repo's entire current real corpus across the 12 in-scope domains would cost well under 1 MB fully cached, and even at 10x this codebase's own stated scale assumption ("dozens to low hundreds of files" per domain) the projected footprint is only on the order of 70-110 MB -- not a practical concern, so both omissions are deferred rather than blocking.
