# Multi-language artifact variants: directory layout, heading-mapping table, and language vocabulary

## Context and Problem Statement

GitHub issue #197 (https://github.com/dfch/biz.dfch.SpecMgr/issues/197), tracked as FEAT feat-197-i18n (`.specmgr/feat/feat-197-i18n/README.md`), asks for first-class multi-language support of the same artifact: every language variant of a document reuses the same `id` and the same document schema (frontmatter fields and body section structure), and only the free-form prose differs. English stays the default/primary language at its existing, unchanged location; other languages are added as `docs/{type}/{language}/` subfolders. The scope is the i18n-eligible whole-body domains `req`/`uc`/`tsk`/`qa`/`prb`/`gol`/`rsk`/`dec`/`sop`/`vcr`/`sysrs`; `feat` is permanently excluded (REQ-002) and `adr` is excluded (REQ-009).

Phase 100 of the feature (the design phase, the first of the plan) had to settle, before the implementation phases (110-150) begin: (a) the on-disk path/filename convention for a language variant -- the plan's working assumption (REQ-001: "exact same filename/id as its EN source") carries a subtlety that needs an explicit decision, because the existing flat naming `<type>-<id>-<slug>.md` derives the slug from `slugify(title)` in `general/tools/_doc_paths.py`, and a translated title would produce a different slug per language; (b) the per-language heading-mapping table (REQ-005) -- its format, storage location, and the exact algorithm by which a parser resolves a translated section heading back to its canonical English schema key. The shared `models/md` engine matches every section heading's text against the section class's effective `@alias` (LITERAL exact match, SPACE_SEPARATED class-name derivation, or REGEX `re.fullmatch`), so translated headings must resolve to the canonical key set without changing the engine's EN behavior; (c) the language-code vocabulary and where it is validated (REQ-008: the same path-injection/confinement discipline already applied to `id`, before any filesystem access); (d) the `list_<d>` semantics (single language per call vs. an "all languages" mode).

The feature's Design Notes additionally require explicit confirmation of facts about the existing machinery rather than assumptions: that `general/tools/_doc_paths.py`'s non-recursive `iter_doc_paths` glob keeps every EN-only consumer (each domain's `list_<d>`/`find_doc_path_by_id`, plus `list_references`, `find_related`/`find_similar_text`, `get_reference_diagram(_all)`) EN-only "for free" (REQ-013); that `DocCache`'s `Path`-keyed entries keep two languages of the same id non-colliding without any cache code change; that `feat/tools/_paths.py` and `feat/tools/_cache.py` need no change (REQ-002); and that non-`.md` sibling assets in a domain's flat directory (e.g. the `.pdf` files next to the `.md` files under `docs/sysrs`) stay out of the `{language}` convention. Task 100.150 of the plan further requires a per-domain inventory of every regex-locked English prose field in the i18n-eligible domains, each with a documented resolution (per-language template variant, or explicit English exemption).

This ADR records those decisions as the contract the implementation phases build on.

## Decision Drivers

- Zero-change principle on the EN path: `docs/{type}/` stays byte-identical, and every tool call with `language` omitted (or `"en"`) preserves today's exact behavior and output (REQ-001/REQ-006).
- Shared identity, encoded by location: the `id` is never language-qualified (REQ-003), and the frontmatter schema and body section structure are structurally identical across languages (REQ-004) -- so the variant's language must live in the file's location, not in the document's content.
- One canonical key set: regardless of the file's language, the parser resolves headings to the same canonical schema keys the EN parser uses (REQ-005), against the unchanged `models/md` engine.
- Path safety: a caller-supplied `language` value is validated before it becomes part of a resolved filesystem path, with the same path-injection/confinement discipline already applied to `id` (REQ-008, ACC-013).
- Closed-vocabulary/schema-constant tokens are never translated (REQ-010): frontmatter `status`/lifecycle words, RSK's TARA `Strategy` word and its `Probability`/`Impact` heading values, VCR's DTAIS method words and `Coverage` word, req's RFC-2119 `Level` words, cross-reference `<TAG>` tokens, timestamps, numbers, UUIDs. The mapping design must therefore map heading *text* only, and must leave those tokens canonical in the variant file itself.
- EN-only consumers stay untouched: `find_related`/`find_similar_text`/`list_references`/`get_reference_diagram(_all)` operate on EN content only (REQ-013) -- ideally a property of the directory layout, not of code changes in those tools.
- Minimal diff: the i18n-eligible domains all share `general/tools/_doc_paths.py` (flat `<type>-<id>-<slug>.md`, non-recursive `*.md` glob, id-scan resolution, stem-based `find_parse_failure`), the shared `models/md` parse engine, and `DocCache` (entries keyed by resolved `Path`) -- the design should ride on all of these, not re-derive them.
- Machine-checkable closedness: every data surface the design introduces (table contents, vocabulary, filenames) should be derivable or drift-testable against the domain models, so a later phase can pin it with tests.

## Considered Options

- Option 1: Encode the variant's language in the document (a `language` frontmatter field), keeping all languages flat under `docs/{type}/` with per-language filenames.
- Option 2: A per-language subfolder `docs/{type}/{language}/` with the basename derived from the variant's own (translated) title.
- Option 3 (chosen): A per-language subfolder `docs/{type}/{language}/` holding the variant under the EN source's exact basename, a per-language JSON heading-mapping table in shared package data applied by a pre-parse heading-normalization pass, and an ISO 639-1-shaped lowercase two-letter `language` vocabulary validated in `_path_safety` before any filesystem access.

## Decision Outcome

Option 3. The contract the implementation phases (110-150) build on:

1. **Path pattern.** The default language EN keeps exactly today's path `docs/{type}/<type>-<id>-<slug>.md` -- unchanged; both the omitted default and an explicit `language="en"` resolve to it, and EN is the only language without a subfolder. Every other validated language `L` stores its variants at `docs/{type}/{L}/<type>-<id>-<slug>.md`. Only `.md` files participate: the feature creates/reads `.md` files only, and non-`.md` sibling assets in a domain's flat directory (e.g. the `.pdf` next to the `.md` under `docs/sysrs`) are untouched and never moved into a `{language}` subfolder. The frontmatter is unchanged: a variant's language is encoded by its directory location only, so the frontmatter schema -- including the shared `id` (REQ-003) -- stays structurally identical across languages (REQ-004).

2. **Basename rule (the EN slug is the single filename authority).** A variant's basename is byte-identical to its EN source's basename; the slug always derives from the EN source's title (`slugify(EN title)`), never from the variant's own translated title. A non-default-language `create_<d>` therefore requires the EN source document (same `id`) to already exist on disk, and writes the variant into the `{language}` subfolder under that exact basename. The other write tools (`update`/`edit`/`set_status`/`set_classification`/`delete`) never re-derive a basename: they resolve the existing variant by id-scanning the language subfolder exactly like today's EN scan (`find_doc_path_by_id` on `docs/{type}/{L}/`). Consequences: (a) `find_parse_failure`'s stem matching (`-{id}-` in the stem / `{id}-` prefix) works unchanged for every language, since every language's file stem is the EN stem (confirmed); (b) the id-based scan still finds a hand-written variant under a different (translated-slug) basename, but such a file breaks the stem-based parse-failure probe -- the identical-basename convention is enforced at the one place where a variant filename is born (`create_<d>`) and recorded here, not re-enforced on every read (accepted trade-off); (c) translating or re-titling a document in one language never changes that variant's filename, and variants of one id are associated across languages by their shared stem.

3. **Heading-mapping table -- format and content.** One flat JSON object per language, mapping `<translated heading text> -> <canonical English heading text>`; keys and values are the heading's inline text without the leading `#` markers and without surrounding whitespace -- exactly the string the engine's `match_alias` sees. The canonical value is precisely the string the domain models' effective `@alias` expects for that heading: the LITERAL value, the SPACE_SEPARATED class-name derivation, or, for a fixed-text REGEX alias, the pattern with its regex escaping undone (e.g. PRB's `Question1` alias `What Is the Problem\?` has canonical text `What Is the Problem?`). The table's domain is closed and machine-derivable: exactly the fixed-text heading aliases used across the i18n-eligible domains -- every `MarkdownSection` alias that is LITERAL, SPACE_SEPARATED (implicit or explicit), or a REGEX carrying no free-text group. This covers every shared section heading (e.g. `## More Information`, `## Tags`, `## Source`, `## Updates`, `## Roles and Responsibilities`, the RASCI H3s, the cross-reference H3s, `#### Test Steps`) and PRB's seven fixed 5W2H question headings. Headings whose regex alias carries a free-text group hold NO table entry, and their schema-constant tokens are never translated (REQ-010): `dec`'s `Option {N}:`, `sop`'s `Step {N}:`, `vcr`'s `AC-{NNN} ({Method})` (the DTAIS method word), `uc`'s `Extension {N}.`/`Step {N}:`, every timestamp-led `Updates`/`Recent Updates` H3, and RSK's `Probability {1..5}`/`Impact {1..5}` must remain in canonical English form inside the variant file itself, while their free-text data (option name, step name, criterion text, update title) stays in the document's language and is accepted by the alias's own `.+` group in any language. The table maps heading text only -- never frontmatter values, never closed-vocabulary field values, never those tokens (REQ-010, ACC-012). A language with no table file is shape-valid but unusable: parsing or creating a variant under it fails with an actionable error naming the language before any parse/write (on a read, only after path resolution, so a missing file keeps the normal not-found semantics; on a write, as a pre-write guard, nothing written).

4. **Heading-mapping table -- storage location.** One JSON file per language in shared, cross-domain package data: `src/biz/dfch/specmgr/general/data/headings/<language>.json` -- not per-domain. Headings recur across four or more domains (the shared sections named in item 3), so a single per-language table keeps one canonical key set and one drift target, and REQ-005 asks for a per-language table. No file for `en` (EN is the canonical form itself). The loader (a) resolves lazily, once per process per language, via `importlib.resources` per the existing packaged-data precedent (`general/data/general_*.md`); (b) rejects a file whose values are not pairwise distinct -- two distinct canonical headings must never translate to the same string, since a document heading to that string would then be structurally ambiguous; (c) is pinned by a drift test (Phase 150) that derives the closed set of fixed-text headings from the domain models and asserts each language table covers exactly that set. The `pyproject.toml` package-data glob for `biz.dfch.specmgr.general` (currently `data/*.md`) extends to cover the JSON files (Phase 110 implementation detail).

5. **Resolution algorithm.** At each domain's text-to-model parse boundary (the `parse_<d>` model function -- the single choke point behind `get_<d>` non-raw reads, `list_<d>` rows, and every write tool's content validation), the effective language resolves its table: a tool's explicit `language` parameter, or, for a path-based `parse_<d>`, the language encoded by the path's position relative to the domain base (the flat EN directory means no table; a direct `{language}` subdirectory means that language, shape-validated). When a table exists, the mdformat-normalized body first passes a fence-aware, line-based heading-normalization pre-pass: each line matching `^#{1,6} ` outside a fenced code block (``` / ~~~) has its inline text looked up as `normalized = table.get(heading_text, heading_text)` and the line rewritten to `<hashes> <normalized>` when it differs; every other line, and every heading without an entry, stays byte-identical. The existing `models/md` engine then runs unchanged: `match_alias` sees canonical English text for every fixed heading, data-carrying regex headings match directly (their tokens are canonical in the file, their data matches `.+`), and the free-form H1 (alias `.+`) is unaffected. The parsed model therefore holds canonical heading text -- the structured form is the same canonical document the EN parser produces (ACC-011) and `str(doc)` renders canonical headings -- while the on-disk file keeps its translation: the write tools persist caller-supplied raw text byte-for-byte, and a `raw=True` read returns the on-disk text verbatim. A heading that is neither in the table nor alias-matching is an ordinary alias-mismatch parse error (channel and message unchanged). The generic disk-free `validate` tool gains no `language` parameter (REQ-006/REQ-007 enumerate `get_<d>`/`list_<d>` and the six write tools only) and therefore stays EN/canonical-only: it validates content whose headings are already canonical.

6. **Language vocabulary and validation.** `language` is an ISO 639-1-shaped lowercase two-letter code, validated by a new guard in `general/tools/_path_safety.py` (an `assert_language`-shaped function alongside `validate_id`) applied before any filesystem access, in the same pre-guard position as `id` (REQ-008, ACC-013): the value must be a `str` fullmatching `^[a-z]{2}$` (the shape subsumes the separator/traversal checks `assert_no_traversal` gives `id`; the guard is named for the value it protects). The set of accepted codes is OPEN at the guard level (any two-letter shape passes) -- the closed set is the table domain of items 3/4: codes without a table are rejected at parse/write time with an actionable error, which keeps the guard static and dependency-free while the language set grows by adding a JSON file. Every `language` parameter defaults to `"en"`; omitting it is byte-identical to today's behavior (REQ-006), and `"en"` may be passed explicitly, resolving to the flat `docs/{type}/` directory (item 1).

7. **`list_<d>` semantics.** Single language per call: `list_<d>()` (omitted) or `list_<d>(language="en")` is today's exact behavior (scans the flat `docs/{type}/`); `list_<d>(language="xx")` scans `docs/{type}/xx/` and lists only the `xx` variants that exist (ACC-007). There is deliberately NO "all languages" mode: `DocSummary`'s row shape carries no language column, and such a mode would repeat the same `id` across rows, changing the row contract for every consumer. Per-artifact language discovery is REQ-012's dedicated language-listing tool (Phase 140) instead, which reports the set of existing variant languages for a given `type`/`id` (always including `"en"` when the EN source exists, ACC-008).

8. **REQ-013 is a directory-layout property (confirmed design fact).** `general/tools/_doc_paths.py`'s `iter_doc_paths` is a non-recursive `base_dir.glob("*.md")` and never descends into `{language}` subfolders; every EN-only consumer builds on it -- each domain's `list_<d>`/`find_doc_path_by_id`, and `list_references`, `find_related`/`find_similar_text`, `get_reference_diagram(_all)` through the same domain readers -- so they continue to see exactly the flat EN files, with zero code change in those tools. The plan (Task 100.100/150.100) pins this as a regression test so a future switch to a recursive glob cannot silently break REQ-013/ACC-014.

9. **`DocCache`: no code change (confirmed design fact).** `DocCache` entries are keyed by the fully-resolved on-disk `Path` (`path.resolve()` at every public method), never by bare `id`; an EN file and each of its variants live at distinct paths and therefore already get independent, non-colliding cache entries, with the existing content-hash validation and reconcile/invalidate/move semantics unchanged. The plan's Tasks 120.110/125.120 are confirmation/test tasks, not `DocCache` code changes, unless implementation finds a real counterexample.

10. **`feat` and `adr` are unchanged (confirmed).** `feat` is permanently EN-only (REQ-002, ACC-002): its bespoke folder-per-document addressing (`feat/tools/_paths.py`: `<base>/<id>/README.md`, shortcut lookup, no flat `*.md` glob) and its clean/dirty `DocCache` pair (`feat/tools/_cache.py`) need no change -- the `{language}` convention cannot reach `feat`'s addressing, and no `feat` tool/resource/prompt gains a `language` parameter. `adr` is excluded (REQ-009, ACC-015): its separate `SPECMGR_ADR_DIR`/`docs/adr` base, its `<uuid>-<slug>.md` naming, and every ADR tool stay unchanged.

11. **Regex-locked prose inventory (Task 100.150, per domain).** A systematic search of the i18n-eligible domains' models and tools (`field_validator`/`model_validator`, `re.fullmatch`/`re.match` against field content -- closed-vocabulary tokens and heading structure excluded) found exactly ONE regex-locked English prose field: `prb`'s mandatory `problem_statement` lead paragraph (`prb/models/v1/body.py`: `_PROBLEM_STATEMENT_PATTERN`, the fixed template `"[Current state] is causing [specific issue], for [stakeholder] because [underlying cause]."`, enforced by `fullmatch` in a `field_validator`). Its resolution is **(b), an explicit exemption**: the field stays in canonical English in every language variant (the whole sentence, blanks included); the translation workflow (Phase 140) must not touch it, and drift detection (Phase 140) must ignore it. Rationale: resolution (a) -- a per-language template variant the validator also accepts -- would require threading the file's language into the Pydantic validator layer (the model does not know it today) plus a new pattern and error message per language, indefinitely, for a single sentence whose enforced structure is precisely the schema-constant kind REQ-010 keeps in English; (b) is a documented, zero-mechanism exemption. Every other regex-locked token in the domains is (i) closed vocabulary (req's `Level` RFC-2119 words, req/gol's numeric `Priority`, rsk's TARA `Strategy` word, vcr's `Coverage` word and DTAIS method words, sop's frontmatter lifecycle words, every domain's frontmatter `status`/`type`, qa's `**<d>.<NNNN>**: ` question-number prefix, tsk's `[ ]`/`[x]` checkbox markers), (ii) cross-reference structure (`<TAG> <uuid>: <title>`, free title data), (iii) heading text (items 3/5), (iv) language-neutral timestamps/numbers/UUIDs, or (v) the diagram-renderer-only patterns in `uc/models/v2/renderer.py` (`return|continue to step N`, `subordinate|superordinate|extension:` labels), which run on EN content only by REQ-013 and are unchanged. Per-domain outcome: req -- none; uc -- none; tsk -- none; qa -- none; prb -- `problem_statement`, resolution (b); gol -- none; rsk -- none; dec -- none; sop -- none; vcr -- none; sysrs -- none.

12. **Pilot domain.** `dec` is the pilot for the implementation phases (Phases 110-130) and for ACC-005/ACC-006/ACC-007 (Task 100.140, recorded in the plan): dispatch-only architecture (no per-domain `update_dec`/`set_status_dec`/`validate_dec` tools to special-case), a simple `models/md`-based body, and a small heading set.

### Consequences

- Good: the EN path and every omitted-`language` behavior stay byte-identical (zero-change principle); REQ-013/ACC-014 hold by directory layout alone, with zero code change in the EN-only consumers; the `models/md` engine is untouched (the pre-pass sits at the parse boundary); the basename rule keeps `find_parse_failure` working for every language; the table domain is closed and drift-testable against the models; the language set grows by adding one JSON file, with no code change and no guard change.
- Good: the EN source is the single filename authority -- translating or re-titling a document in one language never moves that variant's file, and variants of one id are trivially associated across languages by their shared stem.
- Bad: the EN source must exist before any non-EN variant can be created -- non-EN-first authoring is not supported (accepted: the feature is about variants of the same artifact, and REQ-011's translation workflow always starts from an existing source).
- Bad: every new language needs its heading table (JSON file + package-data glob + drift-test coverage) before any document under it can be parsed or written -- a one-time per-language cost; the loader's duplicate-value rejection additionally forces distinct translations for distinct canonical headings.
- Bad: one `prb` sentence (`problem_statement`) stays in English in every language (item 11's exemption) -- a small, documented blemish in otherwise fully translated documents.
- Bad: the pre-pass is a new text transform on every non-EN parse (fence-aware, byte-preserving for non-heading lines) and must be pinned by tests (Phase 150), including the fenced-code-block case.
- Bad: the identical-basename convention is enforced only at `create_<d>`; a hand-written variant under a non-EN slug is found by the id scan but breaks the stem-based `find_parse_failure` probe for its language (recorded trade-off, item 2(b)).

### Confirmation

To be confirmed during FEAT feat-197-i18n's implementation phases at the unit level (direct Python calls through the tools' own test modules): ACC-001 (per-domain path resolution, EN unchanged), ACC-003 (shared id), ACC-004/ACC-011 (translated headings resolve to the canonical schema keys; the translated document validates against its domain's exact EN schema), ACC-005/ACC-006/ACC-007 (pilot `dec` read/write/list semantics, all six write tools), ACC-008 (language listing includes `en`), ACC-012 (closed-vocabulary tokens stay canonical), ACC-013 (`language` path-injection payloads rejected by the guard before any filesystem access), ACC-014 (the EN-only consumers never resolve or index a `{language}` entry -- including the non-recursive-glob regression test), ACC-002/ACC-015 (no `language` parameter on any `feat`/`adr` surface).

## Pros and Cons of the Options

### Option 1: Encode the variant's language in the document (a `language` frontmatter field), all variants flat under `docs/{type}/` with per-language filenames

#### Pros

- No directory change; `iter_doc_paths` is untouched; the language is visible inside the parsed document's frontmatter.
- A per-language filename can carry the translated title (self-describing names in the target language).

#### Cons

- Violates REQ-001 (a variant is not under the "exact same filename/id as its EN source" -- same id, but a per-language filename) and REQ-004 (the frontmatter schema differs between languages: a `language` field on variants only).
- The flat `*.md` glob now sees every language of every id: `list_<d>`/`find_doc_path_by_id`/`list_references`/`find_related`/`get_reference_diagram(_all)` would all return duplicate ids or the wrong language unless every one of them filters on the frontmatter `language` -- REQ-013's EN-only behavior would need a code change in every consumer, and REQ-006's "omitting `language` preserves today's exact behavior" would stop being true (a variant appearing in a bare `list_<d>` is a behavior change).
- `find_parse_failure`'s stem matching would need per-language slug handling.

### Option 2: A per-language subfolder `docs/{type}/{language}/` with the basename derived from the variant's own (translated) title

#### Pros

- The subfolder gives the same directory-level EN separation as Option 3 (REQ-013 for free).
- No dependency on the EN source for the variant's filename; per-language names are self-describing in the target language.

#### Cons

- Violates REQ-001 directly: the variant no longer carries the "exact same filename" as its EN source. `slugify` is ASCII-lowercase-only, 60-char-truncated, with a `doc` fallback -- a German/CJK title produces a lossy or degenerate slug, so distinct titles can collide within one language subfolder.
- The cross-language association of one artifact's variants rests on directory position plus a name match that is no longer guaranteed: re-titling a translation moves the file, and the "same file identity across languages" invariant REQ-001 locks does not hold.

### Option 3: A per-language subfolder with the EN source's exact basename, a per-language JSON heading-mapping table, and an ISO 639-1-shaped language vocabulary validated in `_path_safety`

#### Pros

- Satisfies REQ-001 exactly (byte-identical basename, shared id); the EN source is the single filename authority (items 1/2).
- REQ-013/ACC-014 by directory layout, zero consumer code change (item 8); the EN path and every omitted-`language` behavior byte-identical (items 1/6/7).
- The `models/md` engine is untouched; the table is closed, per-language, drift-testable, and grows without a code change (items 3/4/6).
- `find_parse_failure`'s stem matching works unchanged for every language (item 2(a)).

#### Cons

- The EN source must exist before any variant can be created (non-EN-first authoring unsupported; accepted, item 2).
- Every new language needs its table file + package-data glob + drift-test coverage before any document under it can be parsed or written (item 4).
- A hand-written variant under a non-EN slug is found by the id scan but breaks the stem-based `find_parse_failure` probe (item 2(b)).
- The `prb` `problem_statement` exemption keeps one sentence English in every language (item 11).
