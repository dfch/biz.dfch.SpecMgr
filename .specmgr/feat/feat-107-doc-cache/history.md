#### 2026-09-11 12:30:00.000+02:00 - Phase 8 opened: REQ-012's "unique to feat" claim is false, the delete/scan race hits all 11 other domains too -- plan updated, no code changed

A further independent post-closeout review of the merged, `done` (Phases 1-7) implementation specifically re-examined REQ-012's claim that the class of race it fixed for `feat` (a lock-free `get_*`/`list_*` read observing a path that a concurrent write made disappear) was "unique to `feat`'s rename-based cache integration" and that "no other domain's write path ever makes an existing document's own path disappear out from under an in-flight, lock-free reader." Reproduced directly against a live checkout with two scripts (a monkeypatched `read_req` forcing the race deterministically, no mocks of `DocCache` itself): 1. `general/tools/_doc_paths.py::find_doc_path_by_id`'s id-lookup scan: materializing the directory listing, then deleting the first listed `req` file before the scan's per-path `read_fn(path)` call reaches it, raises an uncaught `FileNotFoundError` out of `find_doc_path_by_id` -- the skip-on-parse-failure clause there only catches `AssertionError`/`ValueError`/`yaml.YAMLError` (REQ-010), never `FileNotFoundError`. 2. `req/tools/_io.py::load_by_id`'s own second, independent `read_req(path)` call (the one performed immediately after `find_req_path` already resolved and read the same path once during its scan): patching `read_req` to raise `FileNotFoundError` only on its second invocation confirms this call site has **no** try/except at all -- the exception propagates straight out of `load_by_id` uncaught. All three are exactly the class of bug REQ-012 closed for `feat` alone (`find_feat_path_by_id`/`load_by_id`/`list_feat` all already catch this specific `FileNotFoundError`) -- it was never extended to the shared `general` module the other 11 domains route through, even though Phase 6 touched that exact module (REQ-010) for the analogous `yaml.YAMLError` fix in the same phase. #### 2026-09-10 20:00:00.000+02:00 - Phase 6 opened: post-closeout review found a hash/parse race, reopening the feature

An independent post-closeout review of PR #119 (the merged Phase 1-5 implementation) found that `general/tools/_doc_cache.py`'s `DocCache.read()` computes its content hash from one `path.read_text()` call, then calls `parse_fn(path)`, which every domain's `_parse` helper implements as its own second, independent `path.read_text()` call -- the two reads are not atomic, and a concurrent write (reads take no domain lock by design) racing between them can produce a cache entry whose stored hash does not correspond to its stored, parsed result. This is a real, if narrow, violation of the "a stale entry is structurally impossible" guarantee this feature and ADR bfd76370-b59b-4d65-b550-a969f6c93c9d both claim. The same review also found `DocCache.move()`'s "byte-identical content" rationale is factually wrong for its only caller (`set_feat_id` always changes `id`/`updated`), and two latent, currently-untriggered design risks: cache hits return the same shared mutable object every time (no domain model is `frozen=True`), and cache keys are unnormalized `Path` objects. Added REQ-007/008/009, ACC-009/010/011, and a new Phase 6 (Tasks 6.1-6.8) to fix all four findings; reverted frontmatter `status` from `done` to `progress`. No code changed yet -- this entry documents the finding and the remediation plan only.
