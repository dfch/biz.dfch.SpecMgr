# Round-Trip-Reduction Plan (feat-128, Task 110.100 / REQ-003 / ACC-003)

Issue #128 question 3: a plan so that agents use **fewer** round-trips for
create and update operations. This is the draft/rationale of that plan; the
actionable task list lives in the follow-up feature
`feat-189-reduce-agent-round-trips` (created in Task 110.110), whose Task
List is the change inventory below, phase-structured, and whose Acceptance
Criteria carry the measurable targets of this document.

## Goal

Fewer tool round-trips per successful create/update across the whole-body
domains, per REQ-003 -- explicitly **not** more schema queries. The
measurable targets (T1-T3, below) are stated against the Phase 100 baseline
(`round-trip-baseline.md`); a plan that "fixed" the schema-skip by making
agents fetch the schema more often would be wrong by definition, because
the baseline shows the fetch is expensive (2 hops + 12-53 KB on the
opencode host) and, in the observed runs, of low marginal value.

The design is constrained by the three Phase 100 findings:

1. The no-prompt (tool-direct) agents never fetched the schema (0/4 runs)
   and still succeeded in every cell except one closed-form rule they never
   saw -- prb's mandatory lead-sentence frame, which cost
   `prb-create-noprompt` one validation-failure -> retry cycle (+2 calls:
   7 total vs the 5-call minimum path). Their authoring reference was the
   `get_<d>_template`/`get_<d>_example` **tools** (1 hop each), which they
   used in all 4 create runs.
2. The prompt-driven create agents did fetch the schema (2/2) because their
   prompt told them to, but the prompt condition cost **more** round-trips,
   not fewer: tsk create 9 vs 5 (no prompt), prb create 9 vs 7 -- and one
   prb prompt attempt exceeded the 600 s timeout. The extra calls were the
   resource-discovery hop (`list_mcp_resources` + `read_mcp_resource` per
   resource, vs 1 hop for the equivalent tool), the todo list, and a `bash`
   date call. The schema itself was used to cross-check the prompt's own
   structure recap, not to learn anything new.
3. The prompt-driven update agents skipped their prompt's unconditional
   "Check the schema" step (0/2) -- a rational value judgment: for a local
   splice the raw body is already in context and `update` validates the
   result as a whole document anyway. Instructions alone do not produce the
   fetch (root-cause-analysis.md, ranked synthesis 3).

## Direction 1: increase schema discoverability / usage -- evaluated

The levers, each checked against the baseline:

1. **Tool-description pointers** (schema-audit gap 13; instruction gap 1).
   The `create_<d>`/`update`/`validate` tool descriptions are the only
   always-in-context metadata and are silent about the schema/template/
   example resources; the no-prompt runs made **zero** resource-layer calls
   -- the schema was not merely unfetched, it was unknown to exist. Adding
   a short clause naming `specmgr://<domain>/schema` (and `/template`,
   `/example`) is zero extra round-trips (it is metadata the agent already
   has) and is the only D1 lever that reaches the tool-direct flow at all.
   **Assessment: keep -- but only as a pointer, never as an imperative.**
   "Fetch the schema before authoring" would convert the fix into more
   round-trips (the prompt-create cells are the counterfactual: 9 calls);
   "the structure reference for this domain is X" preserves the agent's
   choice to skip a fetch it does not need.
2. **Usage-oriented resource metadata** (gap 11) and **prompt-metadata
   clauses** (gap 12). The 12 schema resource descriptions are
   provenance-oriented ("generated by `specmgr schema`, kept current by a
   pre-commit hook") and the 24 create/update prompt descriptions are
   schema-silent. Rewording costs nothing, but the no-prompt agents never
   entered the resource layer or the prompt listing at all, so metadata
   alone cannot fix discoverability -- it only helps once lever 1 makes
   the agent look. **Assessment: keep as support, low value alone.**
3. **1-hop schema access** (a new `get_<d>_schema` tool per domain;
   instruction gap 4). Would cut the observed 2-hop resource route to 1 hop
   and put the schema inside the 94-tool list the agent scans. **Assessment:
   reject.** (i) The observed success path needs no schema at all (0/4
   no-prompt fetches, all succeeded); 1-hop access buys a faster cross-check
   for a fetch the plan is trying to make unnecessary. (ii) The schema's
   machine-readable layer carries **zero** constraints (zero `enum`, only
   the two timestamp `pattern`s, `properties: {}` leaves) -- what the fetch
   returns is prose, and prose is exactly what the template already
   provides in 1 hop. (iii) +12 tools grows the always-in-context surface
   the agent must scan on every call. Revisit only if the Phase 130 re-run
   shows constraint-discovery schema fetches becoming frequent.
4. **Schema `enum`/`pattern` constraint additions from the gap list**
   (gaps 02-10). Making "confirm field names and constraints" true by
   actually emitting the closed sets (status vocabularies, req Level, rsk
   TARA/5x5, vcr DTAIS/AC-NNN, prb lead-sentence pattern, tsk checkbox
   pattern, qa question prefix). **Assessment: keep as second-order.** The
   value is realized only when a schema fetch happens -- under Direction 2
   that is the rare constraint-discovery case -- so this cannot be the
   primary lever, but a schema that claims to be "the structure reference"
   while hiding its own closed sets would leave levers 1-2 pointing at an
   artifact that still underdelivers. Scope rule (binding for the
   follow-up): emit **metadata only** (`json_schema_extra`), never
   `Literal`/`Field(pattern=)` -- see the Recommendation's tension note.
5. **Splitting the schema into an authoring view vs the current
   parser-internals-heavy payload** (gap 14; 12.3-51.8 KB, half of it
   `_value`/`get_extent`/`model_dump` mechanics). **Assessment: defer.**
   A generator-level refactor with no observed failure it fixes; with the
   schema demoted to rare constraint discovery the payload cost is paid
   rarely. Revisit if the re-run shows fetch cost (not fetch count) as a
   driver.

## Direction 2: reduce the *need* for the schema -- evaluated

1. **Fold the closed-form rules into the markdown-level artifacts agents
   already fetch** (template/example; instruction gap 3). The one observed
   failure -- prb's lead-sentence frame -- exists only in the schema prose
   (never fetched no-prompt) and the `create_prb` prompt body (never
   invoked no-prompt); the template/example show only *filled-in*
   instances, which the agent read as "write a natural sentence like this"
   and got wrong. The prb model permits exactly one leading HTML comment
   between the H1 and the lead sentence, so the exact bracketed frame
   fits the template without any model change. The tsk analogue is a
   comment that **actively induced a deviation** (the baseline agent
   prefixed the requested task texts with "Task 1:" because the template
   says "Number the tasks so that they are easier to track") -- rewording
   the comment removes an observed behavior side-effect. The remaining
   closed sets that show only a filled-in instance (req Level's single
   `MUST`, rsk's single `reduce`/`Probability 3`, qa's filled-in prefix)
   get the same one-line-comment treatment; the vcr template already
   spells DTAIS and the AC-NNN heading shape in prose (verified
   present, no-op for those), but the coverage set
   `full`/`partial`/`none` appears only as the filled-in `partial`
   instance -- fold the set in as a comment (see C12). **Assessment:
   primary lever** -- it puts the guidance in the artifact the agents
   demonstrably fetch, in 1 hop, at zero added round-trips.
2. **Context-sensitive update-prompt steps** (instruction gap 2). Replace
   the unconditional "Check the schema" step in the 12 update instructions
   with a conditional one: fetch only for whole-body rewrites or structural
   changes (add/remove/rename sections, edit closed-form content); skip it
   for local splices, where the raw body is already in context and `update`
   validates the whole result. This codifies the behavior the agents
   already rationally chose (0/2 skips) instead of prescribing a fetch and
   measuring the skip as non-compliance. **Assessment: primary lever** for
   the update side.
3. **Repoint the create-prompt steps to the 1-hop tools** (instruction gap
   4). The create instructions name the *resource* URIs
   (`specmgr://tsk/template`), which on the opencode host cost
   `list_mcp_resources` + `read_mcp_resource` = 2 hops -- the observed
   prompt-create runs paid exactly that, while the no-prompt runs used the
   `get_<d>_template`/`get_<d>_example` tools (1 hop) and succeeded.
   Naming the tools cuts 1-2 calls per prompt-driven create. The schema
   sentence in the same step becomes conditional (only on structural
   uncertainty or a validation error), per lever 2's logic. **Assessment:
   primary lever** for the prompt-create cost.
4. **Demote the schema to constraint discovery.** With 1-3 in place, the
   schema's role is: the place to go when a structural question or a
   validation error is unresolved -- not a mandatory pre-authoring fetch.
   The rich `validate` error channel already works (the baseline prb agent
   recovered from its error in +2 calls; feat-27's actionable errors are
   the safety net). **Keep it, do not re-plan it** -- the plan's job is to
   make the primary channel (template/example) complete enough that the
   safety net is rarely needed.

## Recommendation: Direction-2-first hybrid

**Recommendation:** reduce the *need* for the schema (Direction 2) as the
primary direction, kept honest by a minimal, non-prescriptive Direction-1
subset; reject the 1-hop `get_<d>_schema` tool; defer the payload split.

The evidence line that decides it: the prompt condition -- the one that
*actually makes agents use the schema* -- cost **more** round-trips
(tsk create 9 vs 5; prb create 9 vs 7), while the no-prompt agents' **only**
failure was the closed-form lead-sentence frame they never saw (+2 calls on
prb create), and every no-prompt run succeeded with zero schema fetches.
REQ-003 is therefore met by moving the guidance the no-prompt flow is
missing (closed-form rules) **into the artifacts it already fetches**, and
by making the guidance the flow does not need (the schema) **explicitly
optional** -- with the small D1 subset (pointer clauses in tool
descriptions, usage-oriented resource/prompt metadata, metadata-only schema
enrichment) keeping the schema *findable* for the constraint-discovery
cases without ever *prescribing* a fetch.

Priority order for the follow-up feature (one phase each):

- **P0 (Phase 100):** C1-C5 -- the observed failure fix and the observed
  cost drivers; data files only (templates, create/update instructions).
- **P1 (Phase 110):** C6-C12 -- the non-prescriptive D1 pointers
  (tool descriptions, resource metadata, prompt metadata) plus the
  remaining closed-form template folds and the vcr coverage-set fold.
- **P2 (Phase 120):** C13-C15 -- the metadata-only schema enrichment,
  regeneration + invariance tests, and the adr exclusion note.
- **Deferred:** gap 14 (authoring-view split), gap 03 (per-leaf content
  hints -- resolved by the C7 wording + demotion instead), gap 16's release
  cadence (out of scope; publishing is the release SOP's job).

## Measurable targets

Stated against the Phase 100 baseline (`round-trip-baseline.md`,
"What Phase 110 may use as the measurable ACC-003 baseline"): n=1 per cell,
pinned model `vllm-sys0-mtp-2/qwen3.8-27b-bf16-896k-mtp-2`, published
0.34.0 surface -- the baseline's own limitations carry over. Measurement =
re-running the Phase 100 methodology with the reproducible harness
(`evidence/harness/`: `run_all.sh`, `mcp_probe.py`, `parse_events.py`;
identical instruction strings from `evidence/instructions/`, seeds from
`evidence/seeds/`, 600 s timeout, retry-once protocol), with the two
recorded deviations: the server surface is the **worktree** (the changes
are not yet released; published-vs-worktree deltas are documented in
`schema-audit.md`), and **n>=3 per cell** (the baseline's limitation note
recommends exactly this to get a variance estimate). Each target holds only
if it is met in **all** n runs of the cell.

- **T1 -- create without prompt (both domains).** Baseline: tsk 5 calls
  (agent prefixed the requested task texts with "Task 1:" per the template
  comment); prb 7 calls **including** one validation-failure -> retry cycle
  (first `create_prb` rejected for the unseen lead-sentence frame; +2 calls
  over the minimum path). Target: tsk at most 5 calls **and** the checklist
  items carry the requested task texts verbatim; prb first-try
  `create_prb` success, at most 5 calls, 0 validation-failure retries,
  0 schema fetches. Measured
  by re-running `tsk-create-noprompt` and `prb-create-noprompt` (n>=3 each)
  and parsing the event streams with `parse_events.py`.
- **T2 -- create with prompt (both domains).** Baseline: tsk 9 calls, prb
  9 calls (formal retry; attempt 1 timed out at 600 s), each with 1 schema
  fetch paid on the 2-hop resource route. Target: at most 7 calls per
  successful create in both domains, 0 schema fetches (conditional step
  unused), 0 600 s timeouts. Measured by re-running
  `tsk-create-prompt`/`prb-create-prompt` (n>=3 each) with the prompts
  rendered out-of-band from the worktree server, as in the baseline.
- **T3 -- update (all four cells).** Baseline: tsk 5 (no prompt) / 6
  (prompt); prb 5 / 5; 0 schema fetches and 0 validation failures in every
  cell. Target: hold at or below the baseline call count per cell, 0 schema
  fetches for the local edits, 0 validation failures for closed-form rules.
  Measured by re-running the four update cells (n>=3 each) against
  freshly-seeded documents (same seeds, new UUIDs per the harness).

## What the follow-up feature must carry

`feat-189-reduce-agent-round-trips` (Task 110.110): Requirements traced to
C1-C15, Acceptance Criteria including T1-T3, Scope stating the
metadata-only (no parse/validation behavior change) constraint explicitly
-- with the enum-vs-validation-behavior tension flagged in its Design
Notes (a Pydantic `Literal`/`Field(pattern=)` would **change** validation
behavior; `json_schema_extra` does not, and every closed set in C13 was
verified code-enforced during the audit, so the metadata documents existing
behavior) -- Dependencies on this feature (feat-128) and GitHub issue
#189, and the phase-structured Task List (Phase 100 = P0, Phase 110 = P1,
Phase 120 = P2, Phase 130 = verification re-run checking T1-T3).
