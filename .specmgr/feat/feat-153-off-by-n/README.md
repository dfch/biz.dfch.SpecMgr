# Feature: Off-by-N line-offset corruption risk in the generic update tool

## Plan

### Overview

The generic `update` tool's line-range mode (`offset`/`limit`) addresses 1-based lines of the frontmatter-stripped body, sourced correctly only via `get_<d>(id, raw=True)`. GitHub issue #153 reports two independent gaps that let a wrong-but-in-bounds `offset` silently corrupt a document: (1) nothing warns that the on-disk file's YAML frontmatter block is variable-length, so computing a body-line offset as "raw file line number minus an assumed frontmatter length" is unsafe -- yet `feat`'s own AGENTS.md-sanctioned direct-file-editing workflow invites exactly that; and (2) `update` is "splice-then-validate-whole": a wrong offset that lands on a structurally similar line (e.g. a blank line instead of the intended list item) can still pass schema validation and is written with no feedback at all, leaving silent duplication/loss discoverable only by an unprompted manual re-read.

This feature closes issue #153 by adopting three of its four suggested fixes: (1) documenting the coordinate mismatch explicitly in `update`'s tool description and AGENTS.md's `feat` entry; (2) returning a before/after snippet of the touched region (bounded by the touched range, not the document size; the whole-body-equivalent `offset=1` + omitted-`limit` range returns `snippet=None`) on every successful `update` call, via a new `UpdateResult` wrapper return type; and (4) adding an opt-in `numbered` parameter to every `get_<d>(raw=True)` read so a caller can see 1-based body-line numbers without manually counting. The optional `dry_run` parameter (fix #3) is explicitly deferred -- not part of this feature.

Note that the snippet (fix #2) is detection, not prevention: since `dry_run` is deferred, a wrong `offset` is still written to disk before the caller ever sees the returned snippet. Recovery from a bad write is a follow-up manual `update` call, not an automatic rollback.

### Requirements

- REQ-001: `update`'s tool description/docstring and AGENTS.md's `feat` entry state explicitly that a raw on-disk `.md` file's line numbers are never the same as `update`'s `offset`/`limit` body-line coordinates -- the YAML frontmatter block is variable-length -- and that the only safe source of coordinates is `get_<d>(id, raw=True)`, never a raw file read minus an assumed constant.

- REQ-002: In range mode (`offset` given), `update` returns a new wrapper result type (`UpdateResult` or similar) carrying the existing per-domain `frontmatter` plus a `snippet`: the lines dropped (before) and inserted (after) by the splice, plus 2 lines of unchanged context immediately above and below the touched range. Before-lines are labeled with their original **pre-splice** 1-based body-line numbers (they no longer exist afterward, so no post-splice number applies to them); after-lines and context lines are labeled with their **post-splice** 1-based body-line numbers. When the number of removed lines (`limit`) differs from the number of inserted lines, the before- and after-line-number sequences are not guaranteed to be contiguous or to overlap -- this is expected and must not be "fixed" by re-numbering one side to match the other. The snippet is bounded by the touched range, not the document size: it contains exactly the dropped lines, the inserted lines, and up to 2 unchanged context lines per side, so a deliberately large range yields a proportionally large snippet (no hard cap with elision markers; see Explicitly Out Of Scope).

- REQ-003: In whole-body mode (no `offset`), **and** in the whole-body-equivalent range (`offset=1` with omitted `limit` -- `splice_body` documents that range as equivalent to the no-range mode, and the existing `test_update.py` test `test_offset_one_equals_whole_body_mode` pins that equivalence), `update` returns the same wrapper type with `snippet=None`, so the return shape is uniform across both modes and every whole-body domain.

- REQ-004: Every whole-body domain's `get_<d>` tool gains a new `numbered: bool = False` parameter, meaningful only combined with `raw=True`: when `True`, each line of the returned raw text is prefixed with its 1-based body-line number in `"<n>: "` form (mirroring this environment's own file-reading tool's convention); the default (`False`) preserves today's exact byte-verbatim `raw=True` output. When `numbered=True` is combined with `offset`/`limit` windowing, the printed numbers are the line's **absolute** position in the full body (matching `update`'s own coordinate space), starting at the **clamped** offset `max(1, k)` (a `k < 1` window starts at `1`; a `k > N` window is empty and prints no numbers) and never restarting at `1` within a valid window -- this is the entire point of the feature: a caller must be able to feed a number seen here straight back into `update`'s `offset`. Since feat-150 (PR #155, merged into upstream dev) gave every `get_<d>` tool a non-raising `ParseFailureResult` return for a document that exists on disk but fails to parse -- including for `raw=True` reads ("raw=True never returns a broken document's raw text") -- that channel takes precedence over numbering: a numbered read of a parse-failing document returns `ParseFailureResult`, never numbered text; `numbered` adds no new member to the (already-extended) `X | str | ParseFailureResult` return union.

- REQ-005: `numbered=True` combined with `raw=False` raises `ValueError` before any file access, mirroring the existing rule that `offset`/`limit` combined with `raw=False` already raises `ValueError`. Like the existing guard, this fires before the `load_by_id` attempt and the post-feat-150 parse-failure channel, so a misused argument reports `ValueError` even for a document that fails to parse.

- REQ-006: The tool descriptions for both `update` and every `get_<d>` explicitly warn that numbered output must never be fed back verbatim into `content` for `update`/`create_<d>` without first stripping the `"<n>: "` prefix from each line; numbered output is likewise never a valid `edit` `old_str` (it fails `edit`'s byte-exact match safely), which the warning may note in one clause.

- REQ-007: Both changes (the REQ-002/REQ-003 snippet and the REQ-004/REQ-005 `numbered` parameter) apply uniformly across all 12 whole-body domains (`req`/`uc`/`tsk`/`qa`/`prb`/`gol`/`rsk`/`dec`/`sop`/`feat`/`vcr`/`sysrs`); `adr` remains excluded, consistent with `update`'s existing scope.

- REQ-008: `server.py`'s module docstring (hand-maintained -- the `update` entry and the `get_<d>` entries; produced by no regeneration command), the regenerated `docs/MCP.md`, the regenerated `docs/api/`, `AGENTS.md`, all 13 prompt instruction files that narrate the "`get_<d>(raw=True)` -> compute offset -> `update`" workflow (the 12 per-domain `update_<d>` prompts' packaged data files, `<d>/data/<d>_update_instructions.md`, plus `qa`'s own `refine` prompt data file, `qa/data/qa_refine_instructions.md`), and `CHANGELOG.md` are updated to reflect the new `UpdateResult` return shape, the coordinate-mismatch warning, and the new `numbered` parameter.

- REQ-009: A new ADR is authored and accepted documenting that `update`'s return contract is revised from feature feat-69-update-context's "frontmatter-only" precedent to `frontmatter` + optional `snippet`, scoped to `update` alone -- `create_<d>`, `set_status`, and `set_classification` are unaffected and keep returning bare frontmatter. The ADR also records that `get_<d>`'s post-feat-150 `ParseFailureResult` channel is unaffected by this feature (a numbered read of a parse-failing document returns that channel, never numbered text). The ADR further records the snippet-size contract: the snippet is bounded by the touched range rather than hard-capped (the issue's "small regardless of document size" property is deliberately relaxed to "small for the localized edits that are the documented use case"), with the whole-body-equivalent `offset=1` + omitted-`limit` range returning `snippet=None`.

### Design Notes

The snippet-window helper lives alongside `body_text`/`splice_body`/`window_body` in `general/tools/_splice.py` (or a new sibling module, e.g. `_snippet.py`, if `_splice.py` grows too large) and stays doc-type-agnostic like its neighbors. It is computed **once**, in `update`'s shared public dispatcher, not duplicated into each of the 12 per-domain `_update_<d>` adapters: each adapter is extended to hand back the pre-splice body, the post-splice body, and the resolved `offset`/`limit` it used, and the dispatcher assembles the `UpdateResult` from that shared information. The dispatcher sets `snippet=None` for the whole-body-equivalent range (`offset=1` + omitted `limit`) in addition to whole-body mode, so that range never assembles a snippet.

Given the pre-splice body, the `offset`/`limit` coordinates, and the post-splice body, the helper computes: the *before* window (the `offset..offset+limit-1` lines as they existed pre-splice, empty for a pure insert/`limit=0`), the *after* window (the lines the fragment actually occupies in the spliced result), and up to 2 lines of unchanged context immediately above and below the touched range in the *post-splice* body (clamped at the start/end of the body, mirroring `window_body`'s own clamp-not-error convention).

Per REQ-002, before-lines are labeled with their **pre-splice** line numbers and after-/context-lines are labeled with their **post-splice** line numbers; the two numbering sequences are independent and need not be contiguous. A line-for-line replacement (1 line removed, 1 line inserted) happens to show the same number on both sides only by coincidence:

```
   3: ## Some Heading
-  4: (old line that was replaced)
+  4: (new line that replaces it)
   5: (unchanged context line)
```

A size-changing replacement (e.g. 1 line removed, 3 lines inserted) does not:

```
   3: ## Some Heading
-  4: (the single old line that was replaced)
+  4: (first new line)
+  5: (second new line)
+  6: (third new line)
   7: (unchanged context line -- was line 5 pre-splice, now line 7 post-splice)
```

The `-`/`+`/space marker column and the number alignment in these examples are illustrative, not a fixed format; Task 1.1 finalizes the exact snippet line format before ACC-002's tests are written.

`update`'s return type changes from the current per-domain `FooFrontmatter` union to a new `UpdateResult` wrapper (exact name TBD during implementation) exposing `frontmatter: FooFrontmatter` and `snippet: str | None` (populated in range mode, except the whole-body-equivalent `offset=1` + omitted-`limit` range, and `None` in whole-body mode); this is a deliberate, documented narrowing of feature feat-69-update-context's "frontmatter-only" precedent, scoped to `update` alone -- `create_<d>`, `set_status`, and `set_classification` keep returning bare frontmatter, unchanged. Because this reverses a repo-wide precedent for a generic tool used by all 12 whole-body domains, it is recorded in a new ADR (REQ-009) rather than only in this feature's own Decisions Made log.

The `numbered` parameter is implemented by extending `window_body` with a `numbered: bool = False` argument -- `window_body` already computes the clamped `start`, so the `f"{n}: "` prefix reuses that same clamped start directly and is added per returned line only when requested (mirroring the `<line>: <content>` convention this environment's own file-reading tool already uses), with `n` always the line's absolute position in the full body -- not a per-window restart -- so a number seen in a windowed, numbered read can be fed straight back into `update`'s `offset`. No change to `body_text`/`splice_body`, which stay numbering-agnostic since `update`'s range coordinates must keep addressing the *unprefixed* line count. Positioning after feat-150: each `get_<d>` now carries a parse-failure channel (a try/except around `load_by_id` that returns `ParseFailureResult`) ahead of the `if raw:` branch; the numbered wiring sits inside that branch, after the channel. Note also that the current no-window path returns `body_text(path)` directly, bypassing `window_body`. The wiring is pinned (third refinement pass): windowed reads go through the extended `window_body` (the new `numbered` argument numbers from its already-floored start), and the no-window raw path **keeps returning `body_text(path)` verbatim for `numbered=False`** (ACC-004 byte-identity for bodies with or without a trailing newline) and numbers that same text from line 1 when `numbered=True`. The "route every raw read through the extended `window_body`" option is rejected: `window_body` with its defaults is byte-equal to `body_text` *only for trailing-newline bodies* (its own docstring qualifies this), so routing the unnumbered no-window read through it could add a trailing newline.

While touching all 12 `get_<d>.py` files anyway, consider factoring the existing (already hand-duplicated 12x) "`offset`/`limit` combined with `raw=False` raises `ValueError`" guard together with the new "`numbered` combined with `raw=False` raises `ValueError`" guard into one shared helper, rather than hand-duplicating a second near-identical guard into all 12 files. This is an opportunistic improvement, not a hard requirement. After feat-150 each of the 12 files also carries the try/except parse-failure channel that must be preserved -- the shared-guard factoring is now more relevant, not less.

(2) The no-window `numbered=True` raw path is implemented as the single call `window_body(text, 1, None, numbered=True)` rather than a separate line-1 formatter: the contract requires that a `numbered=True` no-window read and a `numbered=True` whole-body-equivalent windowed read of the same body be byte-identical, and that identical output (including the single trailing `"\n"` normalization for no-trailing-newline bodies, which the contract explicitly requires for numbered output) then holds *by construction*; the `numbered=False` no-window path still returns `body_text(path)` verbatim as the Design Notes pinned, so ACC-004's byte-identity is untouched. Rejected alternative: a standalone public `number_lines` formatter in `_splice.py` -- it would duplicate the trailing-newline/clamping logic `window_body` already implements and leave the byte-identity property to be enforced by tests alone.

#### 2026-09-29T01:56:42.000Z - `UpdateResult`/`UpdateFrontmatter` exported from `general.models` lazily via PEP 562 (Phase 2, Task 2.2)

During Task 2.2 it turned out `general/models/__init__.py` cannot import `update_result` eagerly: every domain's `summary.py` re-enters `general.models` (`from ....general.models.summary import DocSummary`) while sibling domains' own `__init__` files may be mid-import -- e.g. `feat/models/v1/body.py` imports `tsk`'s models, and `tsk`'s package `__init__` pulls in the server's full domain-import list, leaving `feat.models.v1` partially initialized (reproduced: `ImportError: cannot import name 'FeatFrontmatter' from partially initialized module ...` when a test imports `adr.prompts.create_adr` first). #### 2026-09-28T18:33:46.000Z - Exact snippet line format and exact numbered line-prefix format finalized (Phase 1, Tasks 1.1/1.2)

Finalized the two remaining open format details from the Design Notes (whose `-`/`+`/space examples were explicitly "illustrative, not a fixed format"), so Phase 2's implementation and ACC-002/ACC-004's tests have a byte-exact contract. Both formats are one family: a snippet line is a 2-character marker prefix (`"- "`, `"+ "`, or `"  "`) prepended to exactly the line a `get_<d>(raw=True, numbered=True)` read prints for that number.
**Snippet line format (Task 1.1).** Each line of `update`'s `snippet` string is `<marker> <n>: <line text>`: `<marker>` is exactly one character -- `-` for a dropped line (labeled with its pre-splice 1-based body-line number), `+` for an inserted line (labeled with its post-splice number), and a single space for an unchanged context line (labeled with its post-splice number, context lines being taken from the post-splice body and clamped at the body's start/end, mirroring `window_body`); `<n>` is the plain decimal line number -- no zero padding, no fixed-width alignment (matching this environment's own file-reading tool's `<line>: <content>` convention and the `numbered` format below); the separator is exactly `": "` (colon + one space); `<line text>` is the line's verbatim text, so an empty body line renders as `<marker> <n>: ` with a trailing space -- no empty-line special case, and every snippet line matches the regex `^[+- ]\d+: ` for its prefix.
Line order within the snippet: context-above (up to 2 lines), the dropped lines (before window, empty for a pure insert / `limit=0`), the inserted lines (after window, empty for a pure delete / empty `content`), context-below (up to 2 lines). The snippet text is its lines joined with `"\n"` plus a single trailing `"\n"`, or `""` when it contains no lines at all (only a no-op splice on an empty body); `snippet` is `None` in exactly the two whole-body cases (no `offset`; `offset=1` + omitted `limit`), never in other range-mode calls.
Worked example (the size-changing case of the Design Notes -- `offset=4`, `limit=1` into a 6-line body whose line 2 is empty and whose lines 3--6 are `## Some Heading`, `(the single old line that was replaced)`, `(unchanged line)`, `(final line)`, the one line replaced by `first new line` / `second new line` / `third new line`): the snippet is exactly the 8-line string `"  2: \n  3: ## Some Heading\n- 4: (the single old line that was replaced)\n+ 4: first new line\n+ 5: second new line\n+ 6: third new line\n  7: (unchanged line)\n  8: (final line)\n"` -- note the empty context line at the top of that string: it is the five characters space, space, `2`, `:`, space (the 2-character marker prefix, the number, and the separator's trailing space), and the two lines numbered 4 exist in different numbering spaces (the expected pre-splice/post-splice split of REQ-002, not a defect); the line-for-line case (`limit=1` replaced by 1 line) is the same layout with one `+` line, and boundary clamping simply drops the missing context lines at the body's start/end (e.g. `offset=2` yields only one context-above line).
**Numbered line-prefix format (Task 1.2).** `get_<d>(raw=True, numbered=True)` prefixes every body line with exactly `f"{n}: {text}"` -- plain decimal, 1-based absolute body-line number, `": "` separator, verbatim line text (an empty line renders as `"<n>: "`, trailing space, no special case); non-empty numbered output ends with exactly one trailing `"\n"` regardless of whether the source body text had a trailing newline (so a `numbered=True` no-window read and a `numbered=True` whole-body-equivalent windowed read of the same body are byte-identical), and an empty window or empty body returns `""`; under `offset`/`limit` windowing the numbers start at the clamped offset `max(1, k)` (a `k < 1` window starts at 1; a `k > N` window is empty) and increment by 1 per line -- never restarting at 1 within a window, keeping numbered output in `update`'s own coordinate space (ACC-011); `numbered=False` remains byte-identical to today's `raw=True` output (ACC-004), including bodies without a trailing newline.
Both finalizations are recorded in the REQ-009 ADR (`19ff316b-cd11-41a7-a616-ffd84917da51`, Decision Outcome items 3 and 6) and feed Task 2.1/2.2 (snippet helper + `UpdateResult`), Task 3.1 (`window_body`'s `numbered` argument), and Task 5.1/5.2/5.3 (the tests that assert these exact strings).

#### 2026-09-28T16:36:41.000Z - Snippet-size contract and `numbered` wiring pinned

Resolved two open design questions from the third review pass: (1) the `update` snippet is bounded by the touched range -- the dropped lines, the inserted lines, and 2 unchanged context lines per side, with no hard cap or elision markers -- and the whole-body-equivalent range (`offset=1` with omitted `limit`) returns `snippet=None` exactly like whole-body mode, since `splice_body` documents that range as equivalent to the no-range mode (the existing `test_offset_one_equals_whole_body_mode` test pins the equivalence); this deliberately relaxes GitHub issue #153 fix #2's "small regardless of document size" property to "small for the localized edits that are the documented use case", and the relaxation is recorded in the REQ-009 ADR rather than only here; (2) the `numbered` parameter is wired per-branch in each `get_<d>`: windowed reads through `window_body` extended with a `numbered` argument (numbering from its already-floored start), the no-window raw path keeping `body_text(path)` verbatim for `numbered=False` (ACC-004 byte-identity) and numbering from line 1 for `numbered=True` -- rejecting the alternative of routing every raw read through `window_body`, whose defaults are byte-equal to `body_text` only for trailing-newline bodies.

#### 2026-09-26T13:00:00.000Z - Snippet numbering split, absolute numbered coordinates, and a new ADR

Resolved three open design questions from the refinement review: (1) the snippet's before-lines are labeled with their pre-splice line numbers and after-/context-lines with post-splice line numbers, independently and not guaranteed contiguous, rather than forcing a single "post-splice for everything" scheme that breaks down whenever a replacement changes the line count; (2) `numbered=True` combined with `offset`/`limit` windowing on `get_<d>(raw=True)` always reports absolute body-line numbers (matching `update`'s own coordinate space), never a 1-based restart within the returned window; (3) since this feature reverses feature feat-69-update-context's repo-wide "frontmatter-only" return precedent for a tool shared by all 12 whole-body domains, it is documented by a new ADR (REQ-009) rather than only in this feature's own Decisions Made log, matching the precedent feat-146-date-time set for a comparably broad change.
