# Feature: Fix placeholder timestamps and actionable HTML-token validation errors (#67, #70, #71)

## Plan

### Overview

This feature closes three interconnected GitHub issues discovered during dogfooding of the FEAT-drafting workflow: (1) issue #67 -- every domain's `#### {timestamp} - {title}` template/example placeholder entries (and some frontmatter `created`/`updated` placeholders) use a suspiciously round, all-zero time-of-day (`00:00:00.000Z`), which invites an agent or human to copy it verbatim into a real document instead of substituting the actual current timestamp; (2) issue #71, which generalizes #67 across every domain's templates/examples/schemas and additionally flags that a malformed `####` timestamp heading in `Updates`/`Decisions Made` (e.g. missing the required `yyyy-MM-dd HH:mm:ss.fff[+HH:mm|Z]` shape) fails whole-document validation with no diagnostic detail; and (3) issue #70, which shows that a bare `<word>`-shaped token outside backticks (parsed as raw HTML by the underlying markdown parser) bypasses the actionable-error path `feat-27-validation` introduced, surfacing only a generic, undiagnosable `Error executing tool`. A preliminary investigation (see Design Notes) found that issues #70 and #71 originate in genuinely separate code paths, and that a minimal reproduction of each against the current codebase already produces a well-formed, actionable `wrap_tool_errors` message rather than the bare failure the issues describe. Each error-message topic therefore needs its own confirm-the-gap-is-real / fix-if-so / regression-test phase, not a single shared fix.

### Requirements

- REQ-001: Investigate how the shared `models/md` parser and its `wrap_tool_errors` error-wrapping handle (a) bare `<word>`-shaped tokens outside backticks and (b) malformed `#### {timestamp} ...` headings in `Updates`/`Decisions Made`, including reproduction against a large real document and a check of whether MCP client/transport-side message handling could explain the reported bare-error symptom, before any implementation begins.
- REQ-002: Every domain's `*/data/*_template.md` and `*/data/*_example.md` file replaces round, all-zero placeholder timestamps (frontmatter `created`/`updated`, and `feat`'s body-level `#### {timestamp} - {title}` headings) with deliberately odd, non-round values in the `yyyy-MM-dd HH:mm:ss.fff[+HH:mm|Z]` format.
- REQ-003: For the bare `<word>`-shaped HTML-like token failure mode (#70): if Phase 1 confirms a real gap, the origin path in `models/md/_markdown.py` is fixed so it surfaces the same actionable detail (field path, line, cause/fix hint) `wrap_tool_errors` already provides for other structural failures; either way, an end-to-end regression test locks in the correct final behavior across affected domains.
- REQ-004: For the malformed-timestamp-heading failure mode (#71): if Phase 1 confirms a real gap, the origin path in `models/md/markdown_section.py`/`markdown_str.py`'s alias/`get_extent` matching is fixed so it surfaces the same actionable detail; either way, an end-to-end regression test locks in the correct final behavior across affected domains.
- REQ-005: Each topic (timestamp placeholders, bare HTML-token errors, malformed timestamp-heading errors) has its fix (if any) and its regression test delivered together in that topic's own phase, not split across separate global "fix everything" / "test everything" phases.

### Acceptance Criteria

- [ ] ACC-001: A repo-wide search for `00:00:00.000` (or equivalent round, all-zero time-of-day patterns) across every `*/data/*_template.md` and `*/data/*_example.md` returns zero matches.
- [ ] ACC-002: An end-to-end regression test with a bare `<word>` token outside backticks in a heading or list item, driven through `create_<d>`/`validate_<d>` for every affected domain, asserts the final `wrap_tool_errors`-enriched message is actionable (field path + line + cause/fix hint), not a bare `Error executing tool`.
- [ ] ACC-003: An end-to-end regression test with a `####` heading whose leading text is not a parseable timestamp, driven through `create_<d>`/`validate_<d>`/the generic `update` tool, asserts the same actionable-error detail, not a bare `Error executing tool`.
- [ ] ACC-004: Design Notes (or a follow-up DEC/ADR, if the investigation reveals architecture-level implications) documents the root cause of each topic, the large-document/MCP-client reproduction findings, and confirms no unintended side effects before any Phase 3/4 fix implementation starts.

### Design Notes

Preliminary research (2026-09-03, via a research agent, read-only, no code changed) into `models/md`, kept here so a future agent does not redo it:

- `wrap_tool_errors` (`models/md/_errors.py` ~lines 156-218) catches `ValidationError`/`yaml.YAMLError`/`AssertionError` and re-prefixes the message with domain/tool/channel context; any other exception type propagates untouched.
- Issue #70 (bare `<word>` parsed as raw HTML) originates in `models/md/_markdown.py::_assert_no_raw_html`/`parse()` (~lines 246-301), a tokenizer-level guard shared by every domain. Raises `AssertionError` with a fully-formed message (`_raw_html_message`).
- Issue #71 (malformed `#### {timestamp}` heading) originates in `models/md/markdown_section.py`/`markdown_str.py`'s `@alias`/`get_extent` heading-matching machinery (`process_list_field`, `_no_match_message`/`_leftover_text_message`) -- unrelated to the tokenizer. Also raises `AssertionError` with a fully-formed message.
- Both land in the *same* `except (AssertionError, ...)` branch of `wrap_tool_errors`, so the wrapping mechanism itself needs no change for either -- but the two failures are otherwise independent code paths, so any real fix is two separate changes, not one.
- A minimal, single-substitution repro of both cases against the shipped `feat_example.md`, run directly against the current `dev`-equivalent branch, **already produced a well-formed, actionable message** -- the bug as literally reported did not reproduce minimally. Phase 1 must retry against a larger real document (the ~150-line document mentioned in issue #70) and check MCP client/transport-side message handling before assuming a code fix is needed at all.
- No existing test drives either failure mode end-to-end through `create_<d>`/`validate_<d>`/`update` and asserts on the final `wrap_tool_errors` message: `tests/models/md/test_markdown_html_rejection.py` only exercises `parse()` directly with real closed tags (not a bare `<d>`-style token, and not through `wrap_tool_errors`); `tests/feat/models/v1/test_body.py::test_rejects_malformed_headings` only asserts the boolean `match_alias()` result, not the resulting exception/message. This is exactly the regression-test gap Phases 3/4 close.
- Direct experience from this feature's own drafting session: an `update` call adding a `### Decisions Made` section failed with a bare `Error executing tool` (no field/line/hint) when two of its three new `#### {timestamp} : {title}` entries were accidentally out of newest-first order due to a `+02:00`/`Z` offset arithmetic mistake -- i.e. a *third*, previously-undocumented case of this same "bare error, no diagnostic" symptom class, this time from the newest-first ordering validator rather than the tokenizer or alias-matching path. Worth folding into Phase 1's investigation as a third sub-case alongside #70/#71.

#### Phase 1 findings (2026-09-03) -- all four sub-topics: no gap found, already actionable

Executed against a `feat` document scaled to match issue #70's report (a 121-line real document -- this very feature's own body, saved verbatim as `/tmp/opencode/feat67/large_body.md` -- not a minimal 5-line fixture), through every layer from `Feature.from_text` up to a real MCP client over a real `stdio` transport (`mcp.client.stdio.stdio_client` + `mcp.ClientSession`, spawning `uv run --frozen --all-extras specmgr mcp` as a subprocess -- not an in-process shortcut). No code was changed; only disposable scratch scripts under `/tmp/opencode/feat67/` were used.

- **#70 (bare `<word>` HTML-like token) -- no gap found.** Injecting a bare, angle-bracketed placeholder token into a list-item paragraph of the 121-line document and running it through `Feature.from_text` directly, through `wrap_tool_errors`, through the in-process `validate_feat` tool function, and through `validate_feat` called by a real MCP client over real `stdio` transport all produced the identical, fully actionable message -- naming the token kind/content, the exact 1-based line (121), and both documented remedies (wrap in a code span, or write it as an HTML comment). No truncation, no generic-ization, at any layer, at this document scale.
- **#71 (malformed `#### {timestamp}` heading) -- no gap found.** Corrupting a real `#### 2026-09-03 11:52:07.318Z - ...` heading in the `Decisions Made` section of the same 121-line document (swapping the space separator for a `T`, i.e. `2026-09-03T11:52:07.318Z`) and running it the same four ways produced the identical actionable message every time, naming the class path (`Feature > Progress > DecisionsMade > DecisionEntry`), the expected regex, the exact 1-based line (`line 107`), and a snippet of the unmatched remaining text.
- **Newest-first-ordering case (the third sub-case from this feature's own drafting session) -- no gap found.** Reconstructed the exact reported scenario end-to-end: `create_feat` a scratch document via a real MCP client/transport call (`SPECMGR_FEAT_DIR` pointed at a throwaway temp dir), then `update` (`type="feat"`) to append a `### Decisions Made` section with 3 new entries where 2 of 3 are out of newest-first order due to a `+02:00`/`Z` offset arithmetic mistake (`09:52:07.318+02:00` precedes `10:41:29.955Z` once both are compared as aware datetimes). The tool call failed with a fully actionable `pydantic.ValidationError`, wrapped by `wrap_tool_errors`, naming the field (`DecisionsMade`) and both offending timestamps verbatim: `"Error executing tool update: 1 validation error for DecisionsMade\n  feat update (body): Assertion failed, DecisionsMade: entries must be newest-first; '2026-09-03 09:52:07.318+02:00' precedes '2026-09-03 10:41:29.955Z' ..."`. Root cause confirmed: `feat.models.v1.body.Updates._validate_newest_first`/`DecisionsMade._validate_newest_first` are plain `AssertionError`s raised from inside a `@model_validator(mode="after")`, so Pydantic wraps them into a `ValidationError` -- which is one of the three channels `wrap_tool_errors` already handles, and it does, correctly, every time this was tried.
- **MCP client/transport-side question -- no gap found; this is the most load-bearing finding.** Read `mcp/server/mcpserver/tools/base.py::Tool.run` (installed SDK, in `.venv`): any non-`MCPError` exception raised by the tool body is caught and re-raised as `raise ToolError(f"Error executing tool {self.name}: {e}") from e` -- i.e. it *prepends* `"Error executing tool {name}: "` to the **entire, untouched `str(e)`**, never truncates or discards it. One level up, `mcp/server/mcpserver/server.py::MCPServer._handle_call_tool` catches that (or any other) exception and returns `CallToolResult(content=[TextContent(type="text", text=str(e))], is_error=True)` -- again the full string, verbatim. A real `ClientSession.call_tool(...)` round-trip over a real `stdio` subprocess for all three sub-cases above confirmed the client-visible `result.content[0].text` is the complete, unabridged, actionable message (field path/line/cause-fix hint included) every time -- e.g. the #70 case above arrives at the client exactly as `"Error executing tool validate_feat: feat validate_feat (body): raw HTML is not permitted ... instead"`, not a bare `"Error executing tool validate_feat"`. **Conclusion: the installed `mcp` SDK (the version pinned in this repo's lockfile) does not truncate, swallow, or generic-ize tool exception messages anywhere in the call path, at any layer.** If a live agent session genuinely saw only a bare `"Error executing tool"` with no further detail, the cause is not in this repository's server-side code or in this SDK version -- candidates outside this investigation's reach include a different/older `mcp` client library version on the consuming side, a host application's own UI truncating a long error string for display, or a docstring/response-size limit unrelated to `wrap_tool_errors` itself (not confirmed; no evidence of any such limit was found in the code paths exercised here).
- **Verdict for Phases 3/4:** since Task 1.3's large-document repro and Task 1.4's MCP-transport check both come back "no gap found" for all three failure-message sub-cases (#70, #71, ordering), Phases 3 and 4 should be scoped down from "fix + test" to "regression test only" -- add the end-to-end fixtures ACC-002/ACC-003 already call for (locking in today's correct, actionable behavior so a future regression is caught), but skip Task 3.1/Task 4.1's conditional code fix, since its precondition ("Task 1.3/1.4 confirmed a real gap") was not met. No DEC/ADR is warranted -- there is no architecture-level finding here, just a confirmation that existing behavior is already correct.

#### Phase 1b (literal-repro deep dive) findings (2026-09-03) -- both #70 and #71: no gap found, confirmed with the EXACT literal reported input and call path

The orchestrator/user judged Phase 1's repro not literal enough (it injected a bare `<word>` token into a plain paragraph rather than the issue's literal heading text, and tested #71 with a corrupted time-separator rather than the issue's literal date-only-plus-parenthetical shape, and never drove #71 through the actual `update` line-range splice the report names). This sub-phase redid both repros with the exact literal inputs/call paths, using disposable scratch scripts under `/tmp/opencode/feat67b/` (no `src`/`tests` changes).

- **#70, root-cause analysis first.** Read `models/md/markdown_str.py::process_field`/`process_list_field` and `models/md/markdown_section.py::MarkdownSection.get_extent` closely: every `get_extent(text)` call (for both a `MarkdownSection` subclass and the base `MarkdownStr`) calls `parse(text)` on its *entire* `text` argument -- which, for the very first field of any container (`Feature.plan`, then `Feature.progress`, etc.), is the *entire not-yet-consumed remainder* of the document, not just that field's own eventual extent. Since the very first such call in the whole recursive descent always starts at `_offset = 0` (the root), `_assert_no_raw_html` (inside `parse()`) is guaranteed to encounter *any* raw-HTML-like token anywhere in the rest of the document on that very first call, with a correct, absolute line number -- regardless of how deep the token is nested, how far into the document it sits, or how large the document is. This is a structural property of the engine, not an accident of Phase 1's smaller fixture.
- **#70, empirical confirmation.** Built a realistic 175-line `feat` body (20 Task-List phases x 3 tasks each, an `Overview`/`Requirements`/`Scope`/`Design Notes` front section) containing the issue's literal bad heading, `#### Phase N: Per-domain create_<d> tools`, at the start (line 34), middle (line 88), and end (line 148) of the document, plus a variant with **two** simultaneous bad tokens (a second `<span>`-shaped token near the end). Ran all four variants through `Feature.from_text` directly, the in-process `validate_feat` tool function, and `validate_feat` called by a real `mcp.ClientSession` over a real `stdio` subprocess (`uv run --frozen --all-extras specmgr mcp`) -- 4 x 4 = 16 combinations. Every single one produced the identical, fully actionable message naming the *correct absolute* 1-based line (34/88/148, verified against the document's own real line numbering) and both fix hints; with two bad tokens present, the earlier (lower-line-number) one is reported, the later one is simply never reached (assertion fires first). Also tried the token embedded in a task item's own free-text description (not just a heading) -- same result. No bisection was ever needed at any document size/complexity tried; the very first call always already pinpoints the exact absolute line.
- **#71, exact literal repro.** Located the generic `update` tool's line-range splice (`general/tools/update.py::_update_feat` + `general/tools/_splice.py::splice_body`): it re-reads the on-disk body, splices the caller's fragment in at the given `offset`/`limit` textually, then calls `Feature.from_text(format_text(spliced))` inside the *same* `wrap_tool_errors(domain="feat", tool="update", channel=BODY_CHANNEL)` context manager whole-body mode uses -- i.e. "splice, then validate the whole spliced result" is real and exactly as documented, not a different, unwrapped code path. Created a scratch `feat` document via a real MCP client (`SPECMGR_FEAT_DIR` pointed at a throwaway temp dir), then called the generic `update` tool (`type="feat"`) with `offset`/`limit` coordinates that insert exactly `#### 2026-09-02 (Phase 1) - Some Title` (the issue's literal text: a date with no time-of-day at all, then a parenthetical, then ` - title`) as a new `### Decisions Made` entry, over the same real `stdio` transport. Result: `isError: True`, message `"Error executing tool update: feat update (body): Feature > Progress > DecisionsMade > DecisionEntry: expected list[DecisionEntry] (heading matching regex '...'), found no match; remaining text starts at line 47 ... and begins with: #### 2026-09-02 (Phase 1) - Some Title ..."` -- fully actionable (path, expected regex, line, snippet), not bare. Repeating the exact same literal heading through a whole-document `validate_feat`/`Feature.from_text` call (bypassing the splice entirely) produced the byte-identical message, confirming the malformed-heading failure mode is inherent to the heading shape itself (rejected by `process_list_field`'s "no further item found" loop-exit, which then finds it as leftover, unmatched text against `DecisionEntry`'s alias) and not specific to, or made worse by, the splice code path.
- **Verdict: no gap found for either #70 or #71, even reproducing the exact literal input and exact literal call path from both issue reports.** Neither the document scale, the token's nesting/position, the presence of multiple simultaneous structural violations, nor routing through the generic `update` tool's splice-then-validate-whole path changes the outcome: every attempt yields a fully actionable message at the MCP client boundary.
- **Best hypothesis for the discrepancy with the original reports.** `git log` shows the actionable-error mechanism (`wrap_tool_errors`, `feat-27-validation`) shipped in release `0.16.0` (2026-09-01), a full day before both issues were filed (2026-09-02); the `update` tool's own splice-then-wrap code (`feat-28`/`#55`, commit `a9dbe9c`) also predates both issue-filing timestamps. Both issues explicitly say they were found *while drafting* `feat-69-update-context`, whose own commit (`d678fb1`, "MCP write tools return frontmatter-only", `#75`) merged *after* both issues were filed -- so the reporting agent was very plausibly working against an in-progress, uncommitted, or mid-refactor working tree state of that very feature at the moment the bare error was seen, not any commit that exists (or ever existed) on `dev`/`main`. A second, independent possibility: the reporting agent's MCP client was a different process/install than this repo's dev worktree (e.g. a `uvx`-cached older release predating `0.16.0`, or a host application that itself truncates a long tool-error string for display) -- neither of which this investigation's reach can confirm or rule out from inside this repository. Either way, the current `dev` HEAD (and every commit at or after `0.16.0`) does not exhibit the reported bare-error symptom for either literal input.
