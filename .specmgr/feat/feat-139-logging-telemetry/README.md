# Feature: Logging and Telemetry for the SpecMgr MCP Server

## Plan

### Overview

Add opt-in structured logging and OpenTelemetry-based telemetry (metrics + tracing) to the specmgr MCP server, serving both local development debugging and production/operator observability, without ever writing to stdout under the default `stdio` transport. This formalizes GitHub issue #139 ("Add telemetry and logging") through the standard doc-driven pipeline: QA `40a17fb8-c069-4c38-a092-47912e1fa41d` (elicitation) -> REQ `bc356fc9-964a-4274-93ec-4627c5aeb2e5` (logging), REQ `dacd01f4-ffd8-4363-a20b-5ac1ce11eef2` (telemetry), and REQ `41444084-6821-426d-84a2-028a3f4fed0b` (status resource) -> ADR `fdbb6d22-278a-4ecf-b2f6-db208bc49fc6` (technology decision: stdlib `logging` + OpenTelemetry API/SDK, wired through a single `ServerMiddleware` appended to `mcp.middleware`) -> this feature folder. A second elicitation round refined the two original REQs (every MCP item, not tools only; id/type-only logging; an opt-in file sink; correlation ID on error responses only; MCP-specific metric naming; fail-open on a broken SDK middleware contract) and produced the third REQ. Per that same round's answer, three initial, partial-coverage VCRs (one per REQ, since a VCR's `## Verifies` is single-valued) were authored immediately in Phase 0 below, ahead of any implementation, and are extended phase-by-phase rather than written after the fact -- see `.specmgr/conventions.md`'s "Verification Case Records (VCR) -- Author Early, Extend as Implementation Lands" section for the general convention this follows. Before Phase 1 started, an implementation-readiness review (codebase research plus stakeholder decisions, see Progress below) refined several previously-unspecified design details -- static-config failure mode, logging/OTel interaction with code the MCP SDK already runs, redaction scope, and metric domain attribution -- into the Design Notes and Task List below. A second, plan-consistency review (see Progress below) then closed several gaps found between the Task List and the VCRs/REQs themselves -- a premature metrics claim in Phase 3, a missing OTLP-endpoint validation case, a missing telemetry-VCR acceptance criterion for the metrics themselves, and a naming ambiguity between "tool" metrics and the broadened "every MCP item" scope -- before any implementation started. A third, plan-fix review (Task 0.9, see Progress below) then verified the remaining technical claims directly against the installed SDK source and the current codebase and closed six further gaps that had survived the first two reviews: unfiltered `ServerMiddleware` method scope, resource `uri`-vs-`name` target extraction, missing server-startup wiring for the config/logging/OTel setup calls, an unachievable-as-worded universal title-redaction guarantee, an unspecified correlation-ID/span-ID reconciliation mechanism across Phases 3 and 4, and a domain-lock wait-time measurement detail -- still before any implementation started. A fourth review, prompted externally by the question of why real design errors kept surfacing on every pass, diagnosed the pattern as verification-by-reading rather than verification-by-doing, and appended a technical-spike-and-relocated-packaging task batch (Tasks 1a.1-1a.7) to Phase 1's own checklist (a literal new phase heading is not schema-valid, since phase headings require an integer number) so this work runs before Phase 2 and converts several remaining assumption-based OpenTelemetry SDK claims into empirically confirmed facts before more implementation code is written on top of them, alongside directly fixing a handful of independent gaps (env-var validation completeness, fail-open guard sequencing, an ACC-004/ACC-012 overlap, and DocCache/lock-refactor regression-test coverage) that did not require empirical confirmation -- see Progress below.

### Requirements

- REQ-001: REQ-bc356fc9-964a-4274-93ec-4627c5aeb2e5 (MCP Server Structured Logging) -- opt-in, correlation-ID-tagged, dual rich/JSON format logging of every MCP tool/resource/prompt invocation, never touching stdout.
- REQ-002: REQ-dacd01f4-ffd8-4363-a20b-5ac1ce11eef2 (MCP Server Telemetry (Metrics and Tracing)) -- opt-in tool-call latency/count/error metrics, doc-cache hit/miss rate, domain-lock wait time, and one distributed trace span per MCP tool/resource/prompt invocation correlated with the logging correlation ID.
- REQ-003: REQ-41444084-6821-426d-84a2-028a3f4fed0b (MCP Server Logging/Telemetry Status Resource) -- a read-only resource reporting current logging/telemetry enablement state as an extensible `list[str]`.

### Acceptance Criteria

- [ ] ACC-001: With both logging and telemetry left at their defaults (no `SPECMGR_LOG_*`/`SPECMGR_OTEL_*` env vars set), running `specmgr mcp` emits zero log records and zero telemetry, and writes nothing to stdout beyond the JSON-RPC channel.
- [ ] ACC-002: With `SPECMGR_LOG_ENABLED=true`, every MCP tool call (`tools/call`), resource read (`resources/read`), or prompt invocation (`prompts/get`) produces a start, completion (or error) log record on stderr, tagged with a per-invocation correlation ID, in the format selected by `SPECMGR_LOG_FORMAT` (`rich` or `json`); protocol-bookkeeping methods that also pass through the same middleware (`initialize`, `tools/list`, `resources/list`, `prompts/list`, `ping`, `notifications/*`) do not produce these records (see ACC-013).
- [ ] ACC-003: With `SPECMGR_OTEL_ENABLED=true`, every MCP tool call, resource read, or prompt invocation this feature's own middleware/meter observes (per ACC-002/ACC-013's method scope) has its call/error/latency metrics recorded for tool-call latency, tool-call counts by tool, error counts by exception type, the `feat-107` doc-cache hit/miss rate, and per-domain lock wait time; the correlation ID from ACC-002 matches the trace/span ID of the span the SDK's built-in `OpenTelemetryMiddleware` already creates for that same request (note: that SDK middleware spans every JSON-RPC method, including the protocol-bookkeeping ones ACC-013 excludes from logging/metrics -- this feature does not suppress or filter those pre-existing spans, only its own log records and metric increments). Regardless of which `SPECMGR_OTEL_EXPORTER` is configured (including the default `console`), enabling telemetry never writes any byte to stdout -- the console exporter's output is redirected to stderr (see Design Notes; Task 1a.2's spike, Phase 1).
- [ ] ACC-004: No log record that this feature's own code (middleware, meter, status resource, redaction filter) constructs ever carries a full document body, an absolute filesystem path, or a document/artifact title as a *structured* field value; free-text content reaching a log record (e.g. an exception's `str()`) is passed through a best-effort regex-based absolute-path scrub as a defense-in-depth backstop (see the Design Notes' "Redaction scope and limits" bullet for why a document/artifact *title* embedded in free text cannot be reliably detected this way, and for the narrow, message-text-only rewording of the specific existing exception classes verified to embed one). ACC-012 states the equivalent guarantee for span attributes; the two are deliberately split (logs vs. spans) rather than restated together, since they are verified by different mechanisms (a logging `Filter` vs. a `SpanProcessor`).
- [ ] ACC-005: `README.md` documents every new `SPECMGR_LOG_*`/`SPECMGR_OTEL_*` environment variable, its default, and how to enable logging/telemetry for local development vs. production.
- [ ] ACC-006: The standard pre-commit/CI quality gate (`ruff format`, `ruff check`, `vulture`, `pytest`, docs regen) passes after every phase below.
- [ ] ACC-007: The status resource (REQ-003) returns a `list[str]` accurately reflecting whether logging and telemetry are each currently enabled, reflecting the actual configuration in effect.
- [ ] ACC-008: A failing MCP tool/resource/prompt call's error response includes a correlation ID; a successful call's result never includes one.
- [ ] ACC-009: The file log sink honors its own on/off and filename environment variables (active only when `SPECMGR_LOG_ENABLED=true`), and always emits structured JSON regardless of the console format setting.
- [ ] ACC-010: An unreachable OTLP endpoint, or a broken `Server.middleware` contract, never breaks a tool call; each condition logs at most one stderr message per failure episode, never repeating while the condition persists.
- [ ] ACC-011: A static logging/telemetry misconfiguration (e.g. `SPECMGR_LOG_FILE_ENABLED=true` with `SPECMGR_LOG_FILE_PATH` unset/blank, `SPECMGR_OTEL_EXPORTER=otlp` with `SPECMGR_OTEL_ENDPOINT` unset/blank, an unrecognized `SPECMGR_LOG_FORMAT`/`SPECMGR_OTEL_EXPORTER`/`SPECMGR_LOG_LEVEL` value, or a boolean-flag env var -- `SPECMGR_LOG_ENABLED`, `SPECMGR_LOG_FILE_ENABLED`, `SPECMGR_OTEL_ENABLED` -- set to anything other than `true`/`false` case-insensitively) fails closed: `specmgr mcp` refuses to start with a clear error, rather than silently disabling the misconfigured piece.
- [ ] ACC-012: No span attribute this feature's own code sets, on any span (including ones the SDK's built-in `OpenTelemetryMiddleware` creates), ever carries a full document body, an absolute filesystem path, or a document/artifact title as a *structured* attribute value; the global `SpanProcessor` additionally runs the same best-effort regex-based absolute-path scrub as ACC-004 against every span's attributes and exception-event message text, and the specific existing exception classes verified to embed a title/path in their `str()` message (enumerated in Task 6.7) have that message text reworded so their `record_exception`/`set_status(str(e))` payload no longer carries it -- this is the achievable, defense-in-depth guarantee this feature provides; see the Design Notes for why an unconditional, universal guarantee against *any* free-text title leaking through an as-yet-unaudited exception message is not something a generic filter can make.
- [ ] ACC-013: This feature's own logging, correlation-ID assignment, and metric increments engage only for `tools/call`, `resources/read`, and `prompts/get` requests; `initialize`, `tools/list`, `resources/list`, `prompts/list`, `ping`, and `notifications/*` (which also flow through the same `ServerMiddleware` chain, per the installed SDK's documented behavior) are observed by the middleware but produce no log record, no correlation ID, and no metric increment.

### Scope

#### Included

- A new top-level `src/biz/dfch/specmgr/telemetry/` package (config parsing, logging setup, the `ServerMiddleware` implementation, and the OpenTelemetry SDK bootstrap).
- Structured logging: dual rich (local dev) / JSON (production) format, gated by `SPECMGR_LOG_ENABLED`/`SPECMGR_LOG_LEVEL`/`SPECMGR_LOG_FORMAT`, covering every MCP tool call, resource read, and prompt invocation (`tools/call`/`resources/read`/`prompts/get`) -- not every JSON-RPC method the shared middleware chain happens to see (ACC-013).
- A method-name filter in the middleware (`ctx.method in {"tools/call", "resources/read", "prompts/get"}`) gating which requests produce a log record, a correlation ID, or a metric increment, since `Server.middleware` wraps every inbound JSON-RPC request/notification (`initialize`, `*/list`, `ping`, `notifications/*` included), not only item invocations.
- An opt-in file log sink, off by default, its own on/off sub-switch layered under `SPECMGR_LOG_ENABLED`, its own configurable filename, always emitting structured JSON regardless of the console format setting.
- A per-tool-call correlation ID, generated once per invocation by the middleware, included in every related log record and, when telemetry is enabled, matching the active span's trace/span ID; included in a client-visible error response, but never in a successful result.
- OpenTelemetry metrics: tool-call latency histogram, tool-call counts by tool/domain, error counts by exception type, `feat-107` doc-cache hit/miss rate, and per-domain lock wait/contention time, named using an MCP-specific scheme (e.g. `mcp.tool.duration`, `mcp.tool.name`, `mcp.domain`, `mcp.item.type`) rather than the raw OpenTelemetry RPC semantic-convention names.
- OpenTelemetry tracing: activating the MCP SDK's existing built-in `OpenTelemetryMiddleware` (which spans every JSON-RPC method, always -- this feature does not change what gets a span, only what gets logged/counted, per ACC-013), with always-on (100%) sampling and no sample-rate configuration.
- A read-only status resource (REQ-003) returning a `list[str]` reporting current logging/telemetry enablement state.
- A redaction safeguard, achievable and best-effort rather than an unconditional universal guarantee (see the Design Notes' "Redaction scope and limits" bullet): (a) this feature's own code (middleware, meter, status resource) never attaches a full document body, an absolute filesystem path, or a document/artifact title as a *structured* log/span/metric attribute; (b) a global, `TracerProvider`-level `SpanProcessor` for spans (covering the SDK's own built-in `OpenTelemetryMiddleware` spans too) plus a logging `Filter` attached to every specmgr-installed `Handler` (console/stderr and the opt-in file sink alike) additionally run a regex-based absolute-path scrub against free-text content (log messages, exception `str()`, span exception events) reaching those handlers/spans regardless of originating logger; (c) the specific existing exception classes verified (Task 6.7) to embed a document/artifact title in their message text have that message text reworded to omit it, since no generic filter can reliably detect free-form title text.
- Graceful, fail-open degradation for *runtime* observability failures only (an unreachable OTLP endpoint, a broken `Server.middleware` contract): never breaks a tool call, and never spams stderr. A *static* logging/telemetry misconfiguration (an invalid or incomplete `SPECMGR_LOG_*`/`SPECMGR_OTEL_*` combination, discoverable at startup) fails closed instead -- see the new "Observability Degrades Gracefully, Application Logic Never Does" convention in `.specmgr/conventions.md`.
- Three initial, partial-coverage VCRs (one per REQ above), authored in Phase 0, extended phase-by-phase as implementation lands.
- `README.md` documentation of every new environment variable.

#### Explicitly Out Of Scope

- Propagating the correlation ID any further than a client-visible error response (e.g. into successful results, or into the MCP SDK's per-tool `Context` object).
- Any change to the existing exception-raising error-handling convention -- when an exception is raised, its type, and its being raised rather than swallowed -- (`XNotFoundError`, `DeleteError`, ...); logging/telemetry observes these, it does not replace them. **Narrow carve-out (Task 6.7):** the *message text* of the specific, enumerated exception classes verified to embed a document/artifact title or an absolute path (e.g. `UcParseError` and sibling `*ParseError` classes' `f"...{node.title!r}"` messages, `DeleteError`'s `f"failed to delete {path}: {ex}"`) is reworded to drop that content -- this changes only the string passed to the exception constructor, never the exception's type, its raise condition, or whether it propagates.
- Suppressing, filtering, or otherwise changing which JSON-RPC methods receive a span from the MCP SDK's own built-in `OpenTelemetryMiddleware` -- that middleware spans every method (`initialize`, `*/list`, `ping`, `notifications/*` included) today, independent of this feature, and this feature's Phase 6 redaction safeguard scrubs the *content* of those spans without changing *which* requests get one. Only this feature's own logging/correlation-ID/metric-increment behavior is scoped down to actual item invocations (ACC-013).
- Building a dashboard, alerting rules, or any specific backend deployment (Grafana/Prometheus/Jaeger/etc.) -- only the exporter configuration surface (`console`/`otlp`) is in scope.
- A configurable trace sample rate -- always-on (100%) sampling is accepted for this feature; revisit only if real-world overhead becomes a problem.
- The deferred ADR `3bf0326f-065a-424c-a2b9-87e5d5bcfa99` MCP-singleton extraction into its own module -- this feature instruments `mcp` where it is constructed today in `server.py`.
- An upper version bound on the `mcp` dependency (e.g. `mcp>=2.0.0,<3.0.0`) -- left at `mcp>=2.0.0`; the Task 4.4 compatibility test plus the runtime fail-open behavior are relied on instead to catch a breaking SDK change, rather than a version ceiling.

### Design Notes

- **Package location**: new top-level `telemetry/` package (not a document domain, so it does not fit the domain-first `<domain>/tools` convention; mirrors `models/` as shared infrastructure). Proposed modules: `telemetry/config.py` (env var parsing), `telemetry/logging.py` (formatter + setup, building on `mcp.server.mcpserver.utilities.logging.configure_logging`), `telemetry/middleware.py` (the `ServerMiddleware` implementation: correlation ID, latency timing, call/error counters, correlation-ID-on-error attachment), `telemetry/otel.py` (OpenTelemetry SDK bootstrap: `TracerProvider`/`MeterProvider` + exporter, fail-open handling), `telemetry/redact.py` (the body/path/title redaction safeguard: a logging `Filter` plus a global `SpanProcessor`).
- **Environment variables** (all default to "disabled"/safe; the `SPECMGR_*` prefix follows the existing convention, but note the codebase has no prior boolean-flag or enum-valued `SPECMGR_*` env var to also mirror for `true`/`false` spelling or case-sensitivity -- every existing `SPECMGR_*_DIR` var is a bare path string, not a flag/enum; `telemetry/config.py` (Task 1.1) defines its own accepted spellings, e.g. exact-match `"true"`/`"false"` case-insensitively, and documents them in `README.md` (Task 8.1) since there is no precedent to silently inherit): `SPECMGR_LOG_ENABLED` (`true`/`false`, default `false`); `SPECMGR_LOG_LEVEL` (default `INFO`); `SPECMGR_LOG_FORMAT` (`rich`|`json`, default `rich`); `SPECMGR_LOG_FILE_ENABLED` (`true`/`false`, default `false`, only takes effect when `SPECMGR_LOG_ENABLED=true`); `SPECMGR_LOG_FILE_PATH` (file path for the JSON-only file sink, required only when the file sink is enabled); `SPECMGR_OTEL_ENABLED` (`true`/`false`, default `false`); `SPECMGR_OTEL_EXPORTER` (`console`|`otlp`, default `console`); `SPECMGR_OTEL_ENDPOINT` (OTLP endpoint URL; required and must be non-blank when `SPECMGR_OTEL_EXPORTER=otlp`, fails closed otherwise -- mirroring the file-sink path requirement below). This task also validates `SPECMGR_LOG_LEVEL` against Python's standard logging level names (case-insensitively) and every boolean-flag var above against the exact-match `"true"`/`"false"` closed set (case-insensitively) -- both fail closed on any other value, exactly like the `SPECMGR_LOG_FORMAT`/`SPECMGR_OTEL_EXPORTER` closed-set validation already described above, rather than being silently ignored or defaulted.
- **Static config validation fails closed**: `telemetry/config.py` raises immediately (e.g. `ValueError`) when parsing an invalid/incomplete combination -- `SPECMGR_LOG_FILE_ENABLED=true` without a non-blank `SPECMGR_LOG_FILE_PATH`, `SPECMGR_OTEL_EXPORTER=otlp` without a non-blank `SPECMGR_OTEL_ENDPOINT`, or an `SPECMGR_LOG_FORMAT`/`SPECMGR_OTEL_EXPORTER` value outside its closed set -- so `specmgr mcp` refuses to start rather than silently running with a half-broken sink. This validation is unconditional: it fires regardless of whether `SPECMGR_LOG_ENABLED`/`SPECMGR_OTEL_ENABLED` are themselves `true`, since a nonsensical combination is rejected outright rather than silently tolerated just because it happens to be currently inert. This mirrors how every other `SPECMGR_*` environment variable in this codebase is already treated, and is the static-misconfiguration counterpart to the *runtime* fail-open policy below; see `.specmgr/conventions.md`'s new "Observability Degrades Gracefully, Application Logic Never Does" section for the general rule this follows (ACC-011).
- **Tool-call instrumentation mechanism**: a single `ServerMiddleware` appended to `mcp.middleware` in `server.py`, right where `mcp = MCPServer(...)` is constructed -- no edits to any of the ~100+ existing `@mcp.tool()`/`@mcp.resource()`/`@mcp.prompt()` functions (confirmed feasible via research into the installed `mcp==2.0.0` SDK: `Server.middleware` is a live, appendable list, and the SDK's own built-in `OpenTelemetryMiddleware` in `mcp/server/_otel.py` is a ready-made template for span creation, exception tagging, and `error.type` recording).
- **`ServerMiddleware` wraps every JSON-RPC method, not only item invocations -- the middleware must filter**: confirmed via the installed SDK's `ServerMiddleware` protocol docstring (`mcp/server/context.py`): it "wraps every inbound request and notification" -- `initialize`, `tools/list`, `resources/list`, `prompts/list`, `ping`, `notifications/cancelled`, `notifications/initialized`, etc. -- not only `tools/call`/`resources/read`/`prompts/get`. Task 3.1's middleware must check `ctx.method` and only emit a log record / assign a correlation ID / increment a metric when it is one of `{"tools/call", "resources/read", "prompts/get"}` (ACC-013); the other methods pass through `call_next(ctx)` unobserved by this feature's own code. This is independent of the SDK's own built-in `OpenTelemetryMiddleware`, which keeps spanning every method regardless (out of this feature's control, and out of scope to change -- see Explicitly Out Of Scope).
- **Per-method target extraction differs -- resources are keyed by `uri`, not `name`**: confirmed via `mcp/server/_otel.py`, the SDK's own `OpenTelemetryMiddleware` only reads `ctx.params.get("name")` for `tools/call` and `prompts/get`; it has no `resources/read` branch, because a resource invocation identifies its target via `ctx.params["uri"]`. Task 3.1's id/type-only logging and Task 5.1's `mcp.domain` mapping must both branch on `ctx.method` to pick the right params key (`name` for tools/prompts, `uri` for resources) rather than assuming a single `name`-shaped extraction works for all three.
- **Wiring the Phase 1/2/4 setup calls into the actual startup path**: `commands/mcp.py`'s `mcp` command imports `server.py` lazily inside the command function (`from ..server import mcp as mcp_server`), which is what first executes `server.py`'s module body -- the same point where `mcp = MCPServer(...)` is constructed and where Task 3.2 appends the middleware. `telemetry/config.py`'s validation (Task 1.6), `telemetry/logging.py`'s setup (Task 2.5), and `telemetry/otel.py`'s bootstrap (Task 4.9) must all be called unconditionally at that same module-level point (not left as library functions nobody calls), in that order (config validated first, since a bad config must fail closed before anything else runs; then logging, so early log records are correctly formatted; then OTel, then the middleware), for ACC-001/ACC-011 to actually hold at `specmgr mcp` startup rather than only in unit tests that call these functions directly. This desired call order (config, then logging, then OTel, then the middleware append) spans three phases (1, 2, 4) plus the append itself (Phase 3, earlier) -- Task 3.2's append necessarily lands before Task 4.9's OTel-bootstrap call exists yet, so Task 4.9 must insert its call *above* the already-existing Task 3.2 line in `server.py` (reordering, not merely appending) once Phase 4 lands, and Task 4.9's own description is written to make that explicit rather than assume the desired order is already in place. Phase 1's Task 1a.1 additionally moves the `opentelemetry-sdk` dependency this whole chain needs to before Phase 2, rather than leaving it until Phase 7, so Phase 4's `telemetry/otel.py` has something importable to configure by the time Task 4.1 is written.
- **`MCPServer.__init__` already calls `configure_logging()` unconditionally today**: it installs a stderr `RichHandler` on the root logger at the default `INFO` level the moment `mcp = MCPServer(...)` runs in `server.py`, before any of this feature's code executes. Confirmed via research that, in this default configuration, the SDK itself emits **zero** stderr output during a normal stdio session (every non-DEBUG SDK log call is gated behind an abnormal/error condition; the two unconditional calls are DEBUG-level and suppressed by the INFO default) -- so ACC-001's "zero log records by default" baseline holds without this feature needing to actively suppress anything. However, `telemetry/logging.py`'s own setup (Phase 2, once `SPECMGR_LOG_ENABLED=true`) must not be a silent no-op against the handlers `configure_logging()` already installed -- `logging.basicConfig()` is a no-op if handlers already exist -- so it must explicitly reconfigure (e.g. `force=True`, or replace/clear the existing handler set) rather than assume a clean slate.
- **Metric/span naming scheme**: MCP-specific names (`mcp.tool.duration`, `mcp.tool.call.count`, `mcp.tool.error.count`, `mcp.cache.hit`/`mcp.cache.miss`, `mcp.lock.wait_time`, with attributes `mcp.tool.name`/`mcp.domain`) rather than the literal OpenTelemetry RPC semantic-convention names (e.g. `rpc.server.duration`), since MCP has no registered `rpc.system` value and resource/prompt calls do not map cleanly onto RPC semantics; follows the spirit (structured names, standard units, histogram buckets), not the letter, of the OTel semantic conventions. Since this requirement explicitly covers every MCP item (tools, resources, and prompts), not tools only, every metric/span additionally carries an `mcp.item.type` attribute (`tool`/`resource`/`prompt`) alongside `mcp.tool.name`/`mcp.domain`, so a resource or prompt invocation recorded under the `mcp.tool.*` metric namespace is not mistaken for a literal tool call.
- **`mcp.domain` attribution**: no tool/resource/prompt-name -> domain mapping exists anywhere in the codebase today. The generic dispatch tools (`update`/`set_status`/`set_classification`/`delete`/`validate`) carry the domain directly in their own `type` argument (from `ctx.params["arguments"]`); domain-specific tools (e.g. `create_req`, `get_req`) map to a domain by their name/module; resources map to a domain (or no domain) by their `uri` (e.g. `specmgr://req/...` vs. the no-domain `specmgr://version`), not by a `name` argument, per the per-method target-extraction bullet above; some resources/prompts have no domain concept at all. Phase 5 needs an explicit, small mapping table/function in `telemetry/` deriving `mcp.domain` from the invocation's method plus the appropriate per-method key (tool/prompt `name`, resource `uri`) and, where present, its `type` argument -- this table does not exist yet and is new design work, not a refactor of an existing mechanism.
- **Correlation ID exposure and its Phase 3/Phase 4 reconciliation**: generated once per invocation by the middleware; included in every related log record and, when telemetry is enabled, tied to the active span's trace/span ID; included in a client-visible error response so an operator/agent can quote it back for log lookup, but never included in a successful result. Concretely, so that Task 3.1 (Phase 3, before any OTel/span concept exists) and Task 4.2 (Phase 4, "tie" the ID to the span) do not each independently generate an unrelated value that can never actually "match" (ACC-003): the correlation-ID helper always first checks for a current, recording OpenTelemetry span (`trace.get_current_span()`); when one exists (`SPECMGR_OTEL_ENABLED=true`, and the SDK's built-in `OpenTelemetryMiddleware` -- which runs outside/before this feature's own middleware in the chain, confirmed via `MCPServer.middleware`'s "outermost-first" ordering -- has already started that request's span by the time this feature's own middleware runs), the correlation ID *is* that span's trace ID (hex-formatted); otherwise (telemetry disabled) it falls back to a freshly generated `uuid4().hex`. Task 3.1 implements this helper directly (it degrades to the `uuid4()` branch until Phase 4 exists); Task 4.2 is therefore not new "tying" logic grafted on afterwards, only the test/confirmation that the span-ID branch engages once telemetry is enabled.
- **Phase 3/Phase 5 division of labor for counters**: Phase 3's middleware (Task 3.1) only generates the correlation ID and emits log records; it does not create or increment any OTel counter/histogram itself, since no `MeterProvider` exists until Phase 4 (Task 4.1) configures one. All counter/histogram creation and incrementing (call counts, error-type counts, latency) is Task 5.2/5.3's responsibility, once the Task 5.1 domain mapping exists -- Phase 3's task description was reworded to stop describing metrics work two phases early.
- **Fail-open policy (runtime failures only)**: both the OTLP-exporter-unreachable case and a broken `Server.middleware` contract (a future SDK upgrade) must never break a tool call -- the server keeps operating normally, logging/telemetry disable themselves (fully or partially) with at most one stderr warning per failure episode, and a further single message is only emitted after a subsequent reconnect-then-drop cycle, never repeating while the condition persists. This is distinct from the static-config-validation rule above, which fails closed instead. **Implementation risk flagged, resolved by a spike**: the OpenTelemetry Python SDK's own batch exporters/processors typically log an export failure on every failed export cycle via their own logger namespace (not just once), so achieving "at most one message per failure episode" requires a custom `logging.Filter` with episode-tracking state attached to the exporter's own logger name (or a thin wrapper around the exporter that tracks first-failure/recovery transitions itself); Task 1a.4 (Phase 1) spikes the SDK's actual per-attempt-vs-per-cycle logging behavior ahead of time (see Decisions Made), and Phase 4's Task 4.5 implements de-duplication against that confirmed behavior rather than an assumption. This work was moved from an earlier draft's Phase 5 into Phase 4, since it is squarely about the OTel exporter/SDK bootstrap Phase 4 already owns, not about the domain-level metrics instrumentation Phase 5 covers. Task 3.2 (Phase 3) additionally wraps its own middleware-append call in a minimal version of this same fail-open policy from the moment it lands, so the append itself can never crash `specmgr mcp` even before this phase's full policy exists; Task 4.3 upgrades that minimal guard into the complete behavior described above, rather than adding an unrelated, independent one.
- **Doc-cache hit/miss counters**: add counters directly to the shared `general/tools/_doc_cache.py`'s `DocCache` class (instruments all 12 per-domain caches at once) plus a `stats()` accessor the OTel meter reads. Since these are 12 independent per-domain singleton instances, not one shared instance, a single meter callback cannot discover them on its own -- Task 5.4 also adds a small registry (a module-level list/dict of live `DocCache` instances, populated at each domain's own cache-module import time) the callback iterates to attribute `mcp.cache.hit`/`mcp.cache.miss` per `mcp.domain`; this registry is new design work, not part of the existing `DocCache` mechanism.
- **Domain-lock wait time**: add one new, shared timing helper in `telemetry/` (e.g. `record_lock_wait(domain, duration)`) and call it from each of the 13 `<domain>/tools/_lock.py` files' `_lock_for`/`<domain>_lock` context manager, rather than re-implementing the timing/recording logic independently 13 times -- this is what actually mirrors the `feat-99-list-item` "one shared helper, many wiring sites" precedent (a single shared implementation, many call sites), not 13 independent implementations of the same logic. **Implementation detail confirmed against the current code** (e.g. `req/tools/_lock.py`'s `req_lock`): every `<domain>_lock` context manager today is `lock = _lock_for(id_); with lock: yield`, which times *acquire-plus-hold*, not *wait*, if wrapped naively. Recording actual wait time requires each of the 13 context managers to change to an explicit `start = time.monotonic(); lock.acquire(); record_lock_wait(domain, time.monotonic() - start); try: yield finally: lock.release()` shape (or equivalent), not just calling the new helper somewhere inside the existing `with lock:` block. Because this changes the acquire/release control flow of 13 concurrency-critical context managers, not just their timing, Task 5.6 must also assert every refactored context manager still releases its lock on every exit path -- including when the caller's `yield`-wrapped body raises -- as a regression check independent of the new timing metric itself.
- **Redaction scope and limits (revised -- an unconditional "never, under any configuration" guarantee for free-text titles is not achievable)**: Phase 4's tracing does **not** create a new span in this feature's own middleware -- it only configures a `TracerProvider`/exporter so the SDK's already-present, built-in `OpenTelemetryMiddleware` starts actually exporting the spans it has always been (inertly) creating. That means essentially all trace spans, including `span.record_exception(e)`/`span.set_status(str(e))` on every exception, come from SDK-owned code, not this feature's own. Per stakeholder decision, Phase 6 implements a **global, `TracerProvider`-level `SpanProcessor`** (`on_end` hook, or equivalent) that scrubs every span the process creates -- including the SDK's built-in middleware's spans -- not only a filter local to this feature's own code (ACC-012), and the logging-side redaction `Filter` is attached directly to every specmgr-installed `Handler` (both the console/stderr handler and the opt-in file-sink handler from Phase 2), so it scrubs every `LogRecord` reaching those handlers regardless of which logger emitted it -- not only records whose logger name happens to be under `biz.dfch.specmgr`. This matters because `SPECMGR_LOG_ENABLED=true` reconfigures the root logger, so third-party and MCP-SDK-internal loggers also emit through the same handlers once logging is enabled; scoping the filter to only specmgr's own logger namespace would leave that other output unredacted.
  **However**, this scrubbing has a real, verified limit that the original "no log record or span attribute ever contains ... a title" wording did not acknowledge. Absolute filesystem paths have a structural signature a regex can target (with known false-positive/negative risk, e.g. paths containing spaces, or non-POSIX/non-Windows-shaped strings). A document/artifact **title** does not: it is arbitrary free text with no distinguishing shape, so a generic `Filter`/`SpanProcessor` operating on an already-rendered string cannot know that a given substring *is* "the title" as opposed to any other quoted text. This is not hypothetical -- grepping the codebase confirms concrete existing call sites that already embed exactly this content in an exception's `str()` message, which the SDK's `record_exception(e)`/`set_status(str(e))` calls capture verbatim: `uc/models/v1/parser.py`'s `UcParseError(f"unrecognized H2 heading {node.title!r}")` (and its sibling `*ParseError` call sites using `node.title`/`child.title`), and `general/tools/delete.py`'s `DeleteError(f"failed to delete {path}: {ex}")` (`path` is an absolute `Path`). Redaction therefore has two distinct components, not one: (1) a *structured*-attribute guarantee -- this feature's own code (the middleware, the meter, the status resource) never attaches a full body/path/title as a dedicated attribute value, which is fully achievable since this feature controls what it names and sets; and (2) a *free-text* backstop -- the regex-based absolute-path scrub described above, plus a narrow, message-text-only rewording (Task 6.7) of the specific, already-enumerated exception classes verified to embed a title, carved out of the Explicitly-Out-Of-Scope exception-handling-convention exclusion (see Scope). ACC-004/ACC-012/ACC-013 above and the VCR acceptance criteria they back (VCR `0a1c2f63...` AC-003, VCR `54fd355f...` AC-007) are worded to match this achievable, two-component guarantee rather than an unconditional universal one. Whether component (2)'s `SpanProcessor` can actually mutate an already-recorded span's attributes/exception-event text via public `opentelemetry-sdk` API, or must rely on undocumented internals, is confirmed empirically by Task 1a.3's spike (Phase 1; see Decisions Made) before Task 6.1 is implemented against it.
- **Status resource**: a read-only MCP resource (candidate URI `specmgr://telemetry/status`) returning a `list[str]` describing current logging/telemetry enablement state, reading the same parsed config as the middleware; since `telemetry/` is shared infrastructure rather than a document domain, register it from a small `general/resources/` module (mirroring the existing `specmgr://version` precedent) rather than inventing a new domain-first location.
- **VCR maintenance**: each of Phases 2 through 6 below ends with a task extending the relevant initial VCR(s) (created in Phase 0) with concrete test references for whatever acceptance criteria that phase just made verifiable, per `.specmgr/conventions.md`'s VCR-early convention; Phase 9 confirms every VCR has reached `## Coverage: full`. Phase 6 extends **both** the logging VCR (log-record redaction) and the telemetry VCR (span redaction, via AC-007, already added to the VCR during the pre-Phase-1 implementation-readiness review) given the widened redaction scope above. Phase 5 similarly adds a new telemetry-VCR acceptance criterion (AC-008, added during the later plan-consistency review) for the metrics themselves being recorded with correct values/attributes -- a REQ `dacd01f4-ffd8-4363-a20b-5ac1ce11eef2` clause no acceptance criterion covered until that review, since the initial Phase-0 VCR draft predates any metrics design.
- **Risk flagged in the ADR**: `Server.middleware` is documented as a provisional API in the installed SDK ("signature and semantics change ... before v2 final") -- Phase 4 adds a dedicated compatibility test (Task 4.4) with two jobs: (a) a canary assertion pinning today's `Server.middleware`/`ServerMiddleware.__call__` shape, so a future `mcp` upgrade that changes either trips this test in CI before runtime fail-open ever needs to engage, and (b) a simulated-incompatibility assertion that the fail-open behavior actually engages when that contract is broken -- so a breaking SDK change is caught loudly (via the test) while the running server itself degrades quietly (via the fail-open policy). No upper version bound is added to the `mcp` dependency to further mitigate this (see Explicitly Out Of Scope) -- the compatibility test and the runtime fail-open policy are considered sufficient.

#### 2026-09-19 16:12:00.000Z - Title redaction is a best-effort, two-component guarantee, not an unconditional universal one

After confirming that real, existing exception messages in the codebase already embed a document/artifact title (`UcParseError`) or an absolute path (`DeleteError`) verbatim, and that a generic post-hoc filter cannot reliably detect free-form title text (unlike a path, which at least has a regex-matchable shape), the redaction guarantee was split into two components instead of left as a single unconditional claim: (1) this feature's own code never attaches a body/path/title as a *structured* attribute -- fully achievable, since this feature controls what it names/sets; (2) a regex-based path scrub plus a narrow, message-text-only rewording of the specific enumerated exception classes (Task 6.7) serves as the free-text backstop. This is the more honest contract to test against and ship, rather than an "under any configuration" wording the implementation could never fully satisfy.

#### 2026-09-19 16:11:00.000Z - ServerMiddleware's method scope must be filtered explicitly, not assumed to already match "item invocation"

Confirmed against the installed SDK source that `Server.middleware`/`ServerMiddleware` -- this feature's single instrumentation point -- wraps every inbound JSON-RPC request and notification, not only `tools/call`/`resources/read`/`prompts/get`. Rather than let logging, correlation-ID assignment, and metric counters silently fire on `initialize`/`*/list`/`ping`/`notifications/*` too, the middleware now explicitly filters on `ctx.method`, and this scope is called out as its own acceptance criterion (ACC-013) so it is independently testable and cannot regress unnoticed.

#### 2026-09-19 15:32:00.000Z - Metrics-correctness VCR gap closed with a new AC instead of folded into an existing one

#### 2026-09-19 14:20:00.000Z - Redaction widened to a global SpanProcessor after a follow-up clarification

Initially decided to scope the redaction safeguard to only this feature's own middleware/meter attributes. A follow-up clarification established that Phase 4's tracing activates the SDK's own built-in `OpenTelemetryMiddleware` rather than creating a new span of this feature's own -- meaning essentially all trace spans, including raw exception messages via `record_exception`/`set_status(str(e))`, are SDK-owned. Given that framing, the stakeholder reversed the initial answer: Phase 6 now implements a global, `TracerProvider`-level `SpanProcessor` scrubbing every span in the process (including the SDK's built-in middleware's spans), the only way to actually satisfy REQ `dacd01f4-ffd8-4363-a20b-5ac1ce11eef2`'s "never attaching ... to any span" wording. The logging-side `Filter` stays scoped to specmgr's own log records, since those are entirely this feature's own creation.

#### 2026-09-19 13:29:00.000Z - Author VCR early, extend phase-by-phase; not after implementation

Per the stakeholder's explicit instruction, VCRs for this feature's REQs are authored as soon as the REQs are finalized (Phase 0), scoped to whatever is genuinely verifiable from each REQ's specified contract alone (`## Coverage: partial`), and are then extended -- not rewritten -- at the end of each implementation phase that makes further criteria concretely verifiable. This avoids both a purely ceremonial post-implementation VCR (describing whatever got built) and a purely aspirational pre-implementation one (never updated once code exists); it also surfaces a design/implementation deviation immediately, at the cheapest point to fix it. This practice is generalized into `.specmgr/conventions.md` for future features, not left as a one-off decision scoped to this feature alone.
