# Feature: Logging and Telemetry for the SpecMgr MCP Server

## Plan

### Overview

Add opt-in structured logging and OpenTelemetry-based telemetry (metrics + tracing) to the specmgr MCP server, serving both local development debugging and production/operator observability, without ever writing to stdout under the default `stdio` transport. This formalizes GitHub issue #139 ("Add telemetry and logging") through the standard doc-driven pipeline: QA `40a17fb8-c069-4c38-a092-47912e1fa41d` (elicitation) -> REQ `bc356fc9-964a-4274-93ec-4627c5aeb2e5` (logging), REQ `dacd01f4-ffd8-4363-a20b-5ac1ce11eef2` (telemetry), and REQ `41444084-6821-426d-84a2-028a3f4fed0b` (status resource) -> ADR `fdbb6d22-278a-4ecf-b2f6-db208bc49fc6` (technology decision: stdlib `logging` + OpenTelemetry API/SDK, wired through a single `ServerMiddleware` appended to `mcp.middleware`) -> this feature folder. A second elicitation round refined the two original REQs (every MCP item, not tools only; id/type-only logging; an opt-in file sink; correlation ID on error responses only; MCP-specific metric naming; fail-open on a broken SDK middleware contract) and produced the third REQ. Per that same round's answer, three initial, partial-coverage VCRs (one per REQ, since a VCR's `## Verifies` is single-valued) were authored immediately in Phase 0 below, ahead of any implementation, and are extended phase-by-phase rather than written after the fact -- see `.specmgr/conventions.md`'s "Verification Case Records (VCR) -- Author Early, Extend as Implementation Lands" section for the general convention this follows. Before Phase 1 started, an implementation-readiness review (codebase research plus stakeholder decisions, see Progress below) refined several previously-unspecified design details -- static-config failure mode, logging/OTel interaction with code the MCP SDK already runs, redaction scope, and metric domain attribution -- into the Design Notes and Task List below. A second, plan-consistency review (see Progress below) then closed several gaps found between the Task List and the VCRs/REQs themselves -- a premature metrics claim in Phase 3, a missing OTLP-endpoint validation case, a missing telemetry-VCR acceptance criterion for the metrics themselves, and a naming ambiguity between "tool" metrics and the broadened "every MCP item" scope -- before any implementation started. A third, plan-fix review (Task 0.9, see Progress below) then verified the remaining technical claims directly against the installed SDK source and the current codebase and closed six further gaps that had survived the first two reviews: unfiltered `ServerMiddleware` method scope, resource `uri`-vs-`name` target extraction, missing server-startup wiring for the config/logging/OTel setup calls, an unachievable-as-worded universal title-redaction guarantee, an unspecified correlation-ID/span-ID reconciliation mechanism across Phases 3 and 4, and a domain-lock wait-time measurement detail -- still before any implementation started. A fourth review, prompted externally by the question of why real design errors kept surfacing on every pass, diagnosed the pattern as verification-by-reading rather than verification-by-doing, and appended a technical-spike-and-relocated-packaging task batch (Tasks 1a.1-1a.7) to Phase 1's own checklist (a literal new phase heading is not schema-valid, since phase headings require an integer number) so this work runs before Phase 2 and converts several remaining assumption-based OpenTelemetry SDK claims into empirically confirmed facts before more implementation code is written on top of them, alongside directly fixing a handful of independent gaps (env-var validation completeness, fail-open guard sequencing, an ACC-004/ACC-012 overlap, and DocCache/lock-refactor regression-test coverage) that did not require empirical confirmation -- see Progress below. After the Phase 1a spike batch completed, a fifth, post-exploration re-evaluation pass re-verified the plan against the installed `mcp==2.0.0` SDK's actual request/error wire model (not only its middleware surface) and filled in the remaining implementation-level details the exploration enabled -- the per-method error-channel model (tool exceptions arrive at the middleware as `isError` *results*, not raised exceptions), the correlation-ID attachment mechanisms, the formatter-level scrub application point, the OTel bootstrap pins (`BatchSpanProcessor`, lifespan shutdown hook, proxy-tracer ordering), the `DocCache` registry shape, the lock-helper import safety, the pinned status-resource URI/format, the CLI fail-closed error surface, and the Task 6.7 rewording census (uc titles mandatory, ADR titles excluded as an accepted residual gap, paths scrub-covered) -- all recorded in the Design Notes/Task List/ACCs above and in the Progress section below.

### Requirements

- REQ-001: REQ-bc356fc9-964a-4274-93ec-4627c5aeb2e5 (MCP Server Structured Logging) -- opt-in, correlation-ID-tagged, dual rich/JSON format logging of every MCP tool/resource/prompt invocation, never touching stdout.
- REQ-002: REQ-dacd01f4-ffd8-4363-a20b-5ac1ce11eef2 (MCP Server Telemetry (Metrics and Tracing)) -- opt-in tool-call latency/count/error metrics, doc-cache hit/miss rate, domain-lock wait time, and one distributed trace span per MCP tool/resource/prompt invocation correlated with the logging correlation ID.
- REQ-003: REQ-41444084-6821-426d-84a2-028a3f4fed0b (MCP Server Logging/Telemetry Status Resource) -- a read-only resource reporting current logging/telemetry enablement state as an extensible `list[str]`.

### Acceptance Criteria

- [ ] ACC-001: With both logging and telemetry left at their defaults (no `SPECMGR_LOG_*`/`SPECMGR_OTEL_*` env vars set), running `specmgr mcp` emits zero log records and zero telemetry, and writes nothing to stdout beyond the JSON-RPC channel.
- [ ] ACC-002: With `SPECMGR_LOG_ENABLED=true`, every MCP tool call (`tools/call`), resource read (`resources/read`), or prompt invocation (`prompts/get`) produces a start, completion (or error) log record on stderr, tagged with a per-invocation correlation ID, in the format selected by `SPECMGR_LOG_FORMAT` (`rich` or `json`); protocol-bookkeeping methods that also pass through the same middleware (`initialize`, `tools/list`, `resources/list`, `prompts/list`, `ping`, `notifications/*`) do not produce these records (see ACC-013).
- [ ] ACC-003: With `SPECMGR_OTEL_ENABLED=true`, every MCP tool call, resource read, or prompt invocation this feature's own middleware/meter observes (per ACC-002/ACC-013's method scope) has its call/error/latency metrics recorded for tool-call latency, tool-call counts by tool, error counts by the per-channel error-type signal (the exception type where observable at the middleware layer, the SDK's own `tool_error` value for `tools/call` error results, the JSON-RPC error code for SDK-wrapped errors -- see the Design Notes' "Per-method error channels" bullet), the `feat-107` doc-cache hit/miss rate, and per-domain lock wait time; the correlation ID from ACC-002 matches the trace ID of the span the SDK's built-in `OpenTelemetryMiddleware` already creates for that same request (note: that SDK middleware spans every JSON-RPC method, including the protocol-bookkeeping ones ACC-013 excludes from logging/metrics -- this feature does not suppress or filter those pre-existing spans, only its own log records and metric increments). Regardless of which `SPECMGR_OTEL_EXPORTER` is configured (including the default `console`), enabling telemetry never writes any byte to stdout -- the console exporter's output is redirected to stderr (see Design Notes; Task 1a.2's spike, Phase 1).
- [ ] ACC-004: No log record that this feature's own code (middleware, meter, status resource, redaction filter) constructs ever carries a full document body, an absolute filesystem path, or a document/artifact title as a *structured* field value; free-text content reaching a log record (e.g. an exception's `str()`) is passed through a best-effort regex-based absolute-path scrub as a defense-in-depth backstop (see the Design Notes' "Redaction scope and limits" bullet for why a document/artifact *title* embedded in free text cannot be reliably detected this way, and for the narrow, message-text-only rewording of the title-embedding exception call sites verified in non-deprecated domains -- the deprecated ADR domain's title sites are an accepted residual gap, see the Design Notes' "Redaction scope and limits" bullet). ACC-012 states the equivalent guarantee for span attributes; the two are deliberately split (logs vs. spans) rather than restated together, since they are verified by different mechanisms (a formatter-level scrub vs. a `SpanProcessor`).
- [ ] ACC-005: `README.md` documents every new `SPECMGR_LOG_*`/`SPECMGR_OTEL_*` environment variable, its default, and how to enable logging/telemetry for local development vs. production.
- [ ] ACC-006: The standard pre-commit/CI quality gate (`ruff format`, `ruff check`, `vulture`, `pytest`, docs regen) passes after every phase below.
- [ ] ACC-007: The status resource (REQ-003) returns a `list[str]` accurately reflecting whether logging and telemetry are each currently enabled, reflecting the actual configuration in effect.
- [ ] ACC-008: With logging or telemetry enabled, a failing MCP tool/resource/prompt call's error response includes a correlation ID (attached via the tool error result's `_meta` field and via the JSON-RPC error's `data` field -- see the Design Notes' "Per-method error channels" bullet); a successful call's result never includes one. With both features disabled (the default) the middleware is a pure pass-through: no correlation ID is attached and the error response is unchanged (see the Design Notes' "Middleware enablement gating" bullet).
- [ ] ACC-009: The file log sink honors its own on/off and filename environment variables (active only when `SPECMGR_LOG_ENABLED=true`), and always emits structured JSON regardless of the console format setting.
- [ ] ACC-010: An unreachable OTLP endpoint, or a broken `Server.middleware` contract, never breaks a tool call; each condition logs at most one stderr message per failure episode, never repeating while the condition persists.
- [ ] ACC-011: A static logging/telemetry misconfiguration (e.g. `SPECMGR_LOG_FILE_ENABLED=true` with `SPECMGR_LOG_FILE_PATH` unset/blank, `SPECMGR_OTEL_EXPORTER=otlp` with `SPECMGR_OTEL_ENDPOINT` unset/blank, an unrecognized `SPECMGR_LOG_FORMAT`/`SPECMGR_OTEL_EXPORTER`/`SPECMGR_LOG_LEVEL` value, or a boolean-flag env var -- `SPECMGR_LOG_ENABLED`, `SPECMGR_LOG_FILE_ENABLED`, `SPECMGR_OTEL_ENABLED` -- set to anything other than `true`/`false` case-insensitively) fails closed: `specmgr mcp` refuses to start with a clear error, rather than silently disabling the misconfigured piece.
- [ ] ACC-012: No span attribute this feature's own code sets, on any span (including ones the SDK's built-in `OpenTelemetryMiddleware` creates), ever carries a full document body, an absolute filesystem path, or a document/artifact title as a *structured* attribute value; the global `SpanProcessor` additionally runs the same best-effort regex-based absolute-path scrub as ACC-004 against every span's attributes and exception-event message text, and the title-embedding exception call sites in non-deprecated domains (enumerated in Task 6.7: the 13 `UcParseError` sites mandatory, the deprecated ADR domain's 9 title sites an accepted residual gap, and the ~25 path-embedding sites scrub-covered and optionally reworded) have that message text reworded so their `record_exception`/`set_status(str(e))` payload no longer carries it -- this is the achievable, defense-in-depth guarantee this feature provides; see the Design Notes for why an unconditional, universal guarantee against *any* free-text title leaking through an as-yet-unaudited exception message is not something a generic filter can make.
- [ ] ACC-013: This feature's own logging, correlation-ID assignment, and metric increments engage only for `tools/call`, `resources/read`, and `prompts/get` requests; `initialize`, `tools/list`, `resources/list`, `prompts/list`, `ping`, and `notifications/*` (which also flow through the same `ServerMiddleware` chain, per the installed SDK's documented behavior) are observed by the middleware but produce no log record, no correlation ID, and no metric increment.

### Scope

#### Included

- A new top-level `src/biz/dfch/specmgr/telemetry/` package (config parsing, logging setup, the `ServerMiddleware` implementation, and the OpenTelemetry SDK bootstrap).
- Structured logging: dual rich (local dev) / JSON (production) format, gated by `SPECMGR_LOG_ENABLED`/`SPECMGR_LOG_LEVEL`/`SPECMGR_LOG_FORMAT`, covering every MCP tool call, resource read, and prompt invocation (`tools/call`/`resources/read`/`prompts/get`) -- not every JSON-RPC method the shared middleware chain happens to see (ACC-013).
- A method-name filter in the middleware (`ctx.method in {"tools/call", "resources/read", "prompts/get"}`) gating which requests produce a log record, a correlation ID, or a metric increment, since `Server.middleware` wraps every inbound JSON-RPC request/notification (`initialize`, `*/list`, `ping`, `notifications/*` included), not only item invocations.
- An opt-in file log sink, off by default, its own on/off sub-switch layered under `SPECMGR_LOG_ENABLED`, its own configurable filename, always emitting structured JSON regardless of the console format setting.
- A per-tool-call correlation ID, generated once per invocation by the middleware, included in every related log record and, when telemetry is enabled, matching the active span's trace ID; included in a client-visible error response (only when at least one of logging/telemetry is enabled; in the default both-off config the middleware is a pure pass-through and attaches nothing), but never in a successful result.
- OpenTelemetry metrics: tool-call latency histogram, tool-call counts by tool/domain, error counts by exception type, `feat-107` doc-cache hit/miss rate, and per-domain lock wait/contention time, named using an MCP-specific scheme (e.g. `mcp.tool.duration`, `mcp.tool.name`, `mcp.domain`, `mcp.item.type`) rather than the raw OpenTelemetry RPC semantic-convention names.
- OpenTelemetry tracing: activating the MCP SDK's existing built-in `OpenTelemetryMiddleware` (which spans every JSON-RPC method, always -- this feature does not change what gets a span, only what gets logged/counted, per ACC-013), with always-on (100%) sampling and no sample-rate configuration.
- A read-only status resource (REQ-003) returning a `list[str]` reporting current logging/telemetry enablement state.
- A redaction safeguard, achievable and best-effort rather than an unconditional universal guarantee (see the Design Notes' "Redaction scope and limits" bullet): (a) this feature's own code (middleware, meter, status resource) never attaches a full document body, an absolute filesystem path, or a document/artifact title as a *structured* log/span/metric attribute; (b) a global, `TracerProvider`-level `SpanProcessor` for spans (covering the SDK's own built-in `OpenTelemetryMiddleware` spans too) plus a scrubbing formatter hook in every specmgr-installed `Handler` (console/stderr and the opt-in file sink alike) additionally run a regex-based absolute-path scrub against the free-text content reaching those handlers/spans (log messages, exception `str()` and tracebacks, span exception events) regardless of originating logger; (c) the title-embedding exception call sites verified in non-deprecated domains (Task 6.7's mandatory rewording set -- today the 13 `UcParseError` sites in `uc/models/v1/parser.py`; the deprecated ADR domain's 9 title sites are an explicitly accepted residual gap, and the ~25 path-embedding sites are scrub-covered and optionally reworded) have that message text reworded to omit it, since no generic filter can reliably detect free-form title text.
- Graceful, fail-open degradation for *runtime* observability failures only (an unreachable OTLP endpoint, a broken `Server.middleware` contract): never breaks a tool call, and never spams stderr. A *static* logging/telemetry misconfiguration (an invalid or incomplete `SPECMGR_LOG_*`/`SPECMGR_OTEL_*` combination, discoverable at startup) fails closed instead -- see the new "Observability Degrades Gracefully, Application Logic Never Does" convention in `.specmgr/conventions.md`.
- Three initial, partial-coverage VCRs (one per REQ above), authored in Phase 0, extended phase-by-phase as implementation lands.
- `README.md` documentation of every new environment variable.

#### Explicitly Out Of Scope

- Propagating the correlation ID any further than a client-visible error response (e.g. into successful results, or into the MCP SDK's per-tool `Context` object).
- Any change to the existing exception-raising error-handling convention -- when an exception is raised, its type, and its being raised rather than swallowed -- (`XNotFoundError`, `DeleteError`, ...); logging/telemetry observes these, it does not replace them. **Narrow carve-out (Task 6.7):** the *message text* of the title-embedding exception call sites in non-deprecated domains (the verified set: `UcParseError`'s `f"...{node.title!r}"`/`f"...{child.title!r}"` messages in `uc/models/v1/parser.py` -- 13 sites) is reworded to drop the title -- this changes only the string passed to the exception constructor, never the exception's type, its raise condition, or whether it propagates. The deprecated ADR domain's 9 title-embedding sites (`models/adr/v1/parser.py`'s `AdrParseError` x8, `models/adr/v1/mutations.py`'s `AdrOptionNotFoundError` x1) are explicitly excluded from that rewording as an accepted residual gap (the domain is planned for phase-out, mirroring its `feat-107` cache exclusion), and the path-embedding sites (e.g. `DeleteError`'s `f"failed to delete {path}: {ex}"`, the 12 domains' `<domain>/tools/_io.py` `*NotFoundError` messages, `feat/tools/_paths.py`) are covered by the regex scrub and optionally reworded.
- Suppressing, filtering, or otherwise changing which JSON-RPC methods receive a span from the MCP SDK's own built-in `OpenTelemetryMiddleware` -- that middleware spans every method (`initialize`, `*/list`, `ping`, `notifications/*` included) today, independent of this feature, and this feature's Phase 6 redaction safeguard scrubs the *content* of those spans without changing *which* requests get one. Only this feature's own logging/correlation-ID/metric-increment behavior is scoped down to actual item invocations (ACC-013).
- Building a dashboard, alerting rules, or any specific backend deployment (Grafana/Prometheus/Jaeger/etc.) -- only the exporter configuration surface (`console`/`otlp`) is in scope.
- A configurable trace sample rate -- always-on (100%) sampling is accepted for this feature; revisit only if real-world overhead becomes a problem.
- The deferred ADR `3bf0326f-065a-424c-a2b9-87e5d5bcfa99` MCP-singleton extraction into its own module -- this feature instruments `mcp` where it is constructed today in `server.py`.
- An upper version bound on the `mcp` dependency (e.g. `mcp>=2.0.0,<3.0.0`) -- left at `mcp>=2.0.0`; the Task 4.4 compatibility test plus the runtime fail-open behavior are relied on instead to catch a breaking SDK change, rather than a version ceiling.

### Design Notes

- **Package location**: new top-level `telemetry/` package (not a document domain, so it does not fit the domain-first `<domain>/tools` convention; mirrors `models/` as shared infrastructure). Proposed modules: `telemetry/config.py` (env var parsing), `telemetry/logging.py` (formatter + setup, building on `mcp.server.mcpserver.utilities.logging.configure_logging`), `telemetry/middleware.py` (the `ServerMiddleware` implementation: correlation ID, latency timing, call/error counters, correlation-ID-on-error attachment), `telemetry/otel.py` (OpenTelemetry SDK bootstrap: `TracerProvider`/`MeterProvider` + exporter, fail-open handling), `telemetry/redact.py` (the body/path/title redaction safeguard: a scrubbing formatter hook for the log handlers plus a global `SpanProcessor`).
- **Environment variables** (all default to "disabled"/safe; the `SPECMGR_*` prefix follows the existing convention; note the codebase's only enum-valued `SPECMGR_*` precedent, `SPECMGR_MCP_TRANSPORT` (`stdio`/`sse`/`streamable-http`, `commands/mcp.py`), is case-insensitive and *permissively* falls back to `stdio` for unrecognized values -- the new vars deliberately diverge from that permissiveness, and there is no boolean-flag precedent at all: `telemetry/config.py` (Task 1.1) defines its own accepted spellings -- exact-match `"true"`/`"false"` case-insensitively for the boolean flags, closed sets for `SPECMGR_LOG_FORMAT`/`SPECMGR_OTEL_EXPORTER`, and exactly the five named levels for `SPECMGR_LOG_LEVEL` (see below) -- and documents them in `README.md` (Task 8.1)): `SPECMGR_LOG_ENABLED` (`true`/`false`, default `false`); `SPECMGR_LOG_LEVEL` (`DEBUG`|`INFO`|`WARNING`|`ERROR`|`CRITICAL`, case-insensitive, default `INFO`); `SPECMGR_LOG_FORMAT` (`rich`|`json`, default `rich`); `SPECMGR_LOG_FILE_ENABLED` (`true`/`false`, default `false`, only takes effect when `SPECMGR_LOG_ENABLED=true`); `SPECMGR_LOG_FILE_PATH` (file path for the JSON-only file sink, required only when the file sink is enabled); `SPECMGR_OTEL_ENABLED` (`true`/`false`, default `false`); `SPECMGR_OTEL_EXPORTER` (`console`|`otlp`, default `console`); `SPECMGR_OTEL_ENDPOINT` (OTLP **base URL**; required and must be non-blank when `SPECMGR_OTEL_EXPORTER=otlp`, fails closed otherwise -- mirroring the file-sink path requirement below; per Task 1a.1's confirmed exporter choice, the OTLP/HTTP exporter consumes this base URL natively and appends the spec-mandated `/v1/traces` and `/v1/metrics` paths itself). This task also validates `SPECMGR_LOG_LEVEL` against the five named levels above (case-insensitively -- the same literal set the SDK's own `configure_logging()` accepts) and every boolean-flag var above against the exact-match `"true"`/`"false"` closed set (case-insensitively) -- both fail closed on any other value, exactly like the `SPECMGR_LOG_FORMAT`/`SPECMGR_OTEL_EXPORTER` closed-set validation already described above, rather than being silently ignored or defaulted.
- **Static config validation fails closed**: `telemetry/config.py` raises immediately (e.g. `ValueError`) when parsing an invalid/incomplete combination -- `SPECMGR_LOG_FILE_ENABLED=true` without a non-blank `SPECMGR_LOG_FILE_PATH`, `SPECMGR_OTEL_EXPORTER=otlp` without a non-blank `SPECMGR_OTEL_ENDPOINT`, or an `SPECMGR_LOG_FORMAT`/`SPECMGR_OTEL_EXPORTER` value outside its closed set -- so `specmgr mcp` refuses to start rather than silently running with a half-broken sink. This validation is unconditional: it fires regardless of whether `SPECMGR_LOG_ENABLED`/`SPECMGR_OTEL_ENABLED` are themselves `true`, since a nonsensical combination is rejected outright rather than silently tolerated just because it happens to be currently inert. This mirrors how every other `SPECMGR_*` environment variable in this codebase is already treated, and is the static-misconfiguration counterpart to the *runtime* fail-open policy below; see `.specmgr/conventions.md`'s new "Observability Degrades Gracefully, Application Logic Never Does" section for the general rule this follows (ACC-011).
- **Tool-call instrumentation mechanism**: a single `ServerMiddleware` appended to `mcp.middleware` in `server.py`, right where `mcp = MCPServer(...)` is constructed -- no edits to any of the ~100+ existing `@mcp.tool()`/`@mcp.resource()`/`@mcp.prompt()` functions (confirmed feasible via research into the installed `mcp==2.0.0` SDK: `Server.middleware` is a live, appendable list, and the SDK's own built-in `OpenTelemetryMiddleware` in `mcp/server/_otel.py` is a ready-made template for span creation, exception tagging, and `error.type` recording).
- **`ServerMiddleware` wraps every JSON-RPC method, not only item invocations -- the middleware must filter**: confirmed via the installed SDK's `ServerMiddleware` protocol docstring (`mcp/server/context.py`): it "wraps every inbound request and notification" -- `initialize`, `tools/list`, `resources/list`, `prompts/list`, `ping`, `notifications/cancelled`, `notifications/initialized`, etc. -- not only `tools/call`/`resources/read`/`prompts/get`. Task 3.1's middleware must check `ctx.method` and only emit a log record / assign a correlation ID / increment a metric when it is one of `{"tools/call", "resources/read", "prompts/get"}` (ACC-013); the other methods pass through `call_next(ctx)` unobserved by this feature's own code. This is independent of the SDK's own built-in `OpenTelemetryMiddleware`, which keeps spanning every method regardless (out of this feature's control, and out of scope to change -- see Explicitly Out Of Scope).
- **Per-method target extraction differs -- resources are keyed by `uri`, not `name`**: confirmed via `mcp/server/_otel.py`, the SDK's own `OpenTelemetryMiddleware` only reads `ctx.params.get("name")` for `tools/call` and `prompts/get`; it has no `resources/read` branch, because a resource invocation identifies its target via `ctx.params["uri"]`. Task 3.1's id/type-only logging and Task 5.1's `mcp.domain` mapping must both branch on `ctx.method` to pick the right params key (`name` for tools/prompts, `uri` for resources) rather than assuming a single `name`-shaped extraction works for all three.
- **Per-method error channels differ -- the middleware must handle three shapes** (verified against the installed `mcp==2.0.0` SDK source in this re-evaluation: `mcp/server/mcpserver/server.py`'s `_handle_call_tool`/`_handle_read_resource`/`_handle_get_prompt` and `mcp/server/runner.py`'s `modern_error_data`/`on_request` error mapping): for `tools/call`, every non-`MCPError` exception raised by a tool function is converted by the SDK *before* the middleware sees it -- `except Exception as e: return CallToolResult(content=[TextContent(str(e))], is_error=True)` -- i.e. a JSON-RPC *success* envelope whose dumped wire dict carries `isError: true` (camelCase alias; the middleware observes the serialized dict, not the model), so no exception object is available at the middleware layer for tools; for `resources/read`, the SDK's own `ResourceNotFoundError`/`ResourceError` are wrapped as `MCPError` (carrying the SDK's own `data={"uri": ...}`) and other exceptions propagate raw; for `prompts/get` nothing is converted, raw exceptions propagate; and at the dispatcher, an `MCPError` keeps its own `ErrorData` (incl. `data`), a `ValidationError` maps to `INVALID_PARAMS` with empty `data`, and any other exception maps to a generic `INTERNAL_ERROR`/"Internal server error" **without a data field** (plus an SDK-side `logger.exception` under `mcp.server.runner`). Task 3.1 must therefore detect a `tools/call` failure from the post-`call_next` result dict (`isError: true`) as well as from the exception path (the tool error record's text comes from the result's content, i.e. the SDK's `str(e)`); Task 3.3 attaches the correlation ID per channel: (a) `tools/call` error result -- merge `"_meta": {"correlationId": ...}` into the result dict (verified: `CallToolResult.meta` dumps as `_meta`); (b) `MCPError` on any of the three methods -- merge `correlationId` into `e.error.data`, preserving the SDK's own `uri` entry; (c) raw exception/`ValidationError` on any of the three methods -- convert to a wire-identical `MCPError` (same code/message the dispatcher would otherwise produce, plus the `data` carrying the correlation ID) and re-raise, so ACC-008 holds universally; the accepted side effect is that the SDK's own server-side `logger.exception` of that traceback is replaced by this feature's own error log record, which carries the correlation ID anyway. Task 5.3's error-type counter likewise uses the per-channel signal observable at the middleware layer: `tool_error` (the SDK's own value for the `isError` result shape) for `tools/call` error results, the `MCPError`'s JSON-RPC error code for wrapped errors, and `type(exc).__qualname__` for raw exceptions -- which satisfies REQ `dacd01f4-ffd8-4363-a20b-5ac1ce11eef2`'s "error counts by exception type" clause without changing the REQ text.

- **Metric/span naming scheme**: MCP-specific names (`mcp.tool.duration`, `mcp.tool.call.count`, `mcp.tool.error.count`, `mcp.cache.hit`/`mcp.cache.miss`, `mcp.lock.wait_time`, with attributes `mcp.tool.name`/`mcp.domain`) rather than the literal OpenTelemetry RPC semantic-convention names (e.g. `rpc.server.duration`), since MCP has no registered `rpc.system` value and resource/prompt calls do not map cleanly onto RPC semantics; follows the spirit (structured names, standard units, histogram buckets), not the letter, of the OTel semantic conventions. - **`mcp.domain` attribution**: no tool/resource/prompt-name -> domain mapping exists anywhere in the codebase today. The generic dispatch tools (`update`/`set_status`/`set_classification`/`delete`/`validate`) carry the domain directly in their own `type` argument (from `ctx.params["arguments"]`); domain-specific tools (e.g. `create_req`, `get_req`) map to a domain by their name/module; resources map to a domain (or no domain) by their `uri` (e.g. `specmgr://req/...` vs. the no-domain `specmgr://version`), not by a `name` argument, per the per-method target-extraction bullet above; some resources/prompts have no domain concept at all. Phase 5 needs an explicit, small mapping table/function in `telemetry/` deriving `mcp.domain` from the invocation's method plus the appropriate per-method key (tool/prompt `name`, resource `uri`) and, where present, its `type` argument -- this table does not exist yet and is new design work, not a refactor of an existing mechanism.
- **Correlation ID exposure and its Phase 3/Phase 4 reconciliation**: generated once per invocation by the middleware; included in every related log record and, when telemetry is enabled, tied to the active span's trace/span ID; included in a client-visible error response so an operator/agent can quote it back for log lookup, but never included in a successful result. Concretely, so that Task 3.1 (Phase 3, before any OTel/span concept exists) and Task 4.2 (Phase 4, "tie" the ID to the span) do not each independently generate an unrelated value that can never actually "match" (ACC-003): the correlation-ID helper always first checks for a current, recording OpenTelemetry span (`trace.get_current_span()`); when one exists (`SPECMGR_OTEL_ENABLED=true`, and the SDK's built-in `OpenTelemetryMiddleware` -- which runs outside/before this feature's own middleware in the chain, confirmed via `MCPServer.middleware`'s "outermost-first" ordering -- has already started that request's span by the time this feature's own middleware runs), the correlation ID *is* that span's trace ID (hex-formatted); otherwise (telemetry disabled) it falls back to a freshly generated `uuid4().hex`. Task 3.1 implements this helper directly (it degrades to the `uuid4()` branch until Phase 4 exists); Task 4.2 is therefore not new "tying" logic grafted on afterwards, only the test/confirmation that the span-ID branch engages once telemetry is enabled.
- **Middleware enablement gating (pure pass-through when both features are off)**: the middleware's observability behavior -- correlation-ID generation, start/completion/error log records, metric increments, and (critically) Task 3.3's raw-exception-to-`MCPError` conversion and error-response correlation-ID attachment -- engages only when at least one of `SPECMGR_LOG_ENABLED` / `SPECMGR_OTEL_ENABLED` is `true`. When both are `false` (the default), the middleware is a pure pass-through for *every* method, including the three invocations: it adds no correlation ID to any response and performs no exception conversion, so the default config's error handling is byte-for-byte the SDK's own -- in particular the dispatcher's stderr `logger.exception` of a raw exception (under `mcp.server.runner`) is *not* suppressed by this feature (Task 3.3's stated "accepted side effect" of replacing that traceback log only applies when this feature's own error record is actually emitted, i.e. when logging is enabled). Metrics are already a no-op when disabled (Task 5.2); this note extends the same gating to the correlation-ID and error-conversion paths, which ACC-008 / Task 3.1 / Task 3.3 otherwise describe unconditionally. This preserves the ADR's "fully opt-in, off by default" driver and ACC-001's zero-change default baseline.
- **Phase 3/Phase 5 division of labor for counters**: Phase 3's middleware (Task 3.1) only generates the correlation ID and emits log records; it does not create or increment any OTel counter/histogram itself, since no `MeterProvider` exists until Phase 4 (Task 4.1) configures one. All counter/histogram creation and incrementing (call counts, error-type counts, latency) is Task 5.2/5.3's responsibility, once the Task 5.1 domain mapping exists -- Phase 3's task description was reworded to stop describing metrics work two phases early.
- **OTel bootstrap pins (Task 4.1, from the Phase 1a findings plus this re-evaluation's verification)**: the `TracerProvider` uses a **`BatchSpanProcessor`**, not a `SimpleSpanProcessor` -- with a simple processor, an unreachable OTLP endpoint would block each span's `end()` synchronously for the exporter's timeout (10 s production default, per Task 1a.4), stalling every tool call in a way the fail-open design does not cover; the batch path's background failure is exactly what Task 4.5's wrapper de-duplicates. The `MeterProvider` uses the **`PeriodicExportingMetricReader`** (default 60 s interval). The OTLP exporters are constructed as `OTLPSpanExporter(endpoint=...)`/`OTLPMetricExporter(endpoint=...)` with the `SPECMGR_OTEL_ENDPOINT` base URL as-is, and the Task 4.5 wrapper is applied to both. Both providers are shut down at process exit -- `TracerProvider.shutdown()`/`MeterProvider.shutdown()` (the latter performs the final metric collection Task 1a.2 found reaches real stdout after serving ends without the `out=sys.stderr` redirection) -- hooked into `server.py`'s existing `_lifespan` placeholder (its post-`yield` section), which today is a no-op. Note for Task 4.2: `mcp/shared/_otel.py` fetches its tracer (`get_tracer("mcp-python-sdk")`) at module-import time, before any provider exists -- verified against the installed API in this re-evaluation that such a tracer is a proxy that resolves the provider set *later* (a span started through it still lands in the later-configured provider), so the prescribed module-scope order (import `mcp` -> construct `MCPServer` -> bootstrap) works; Task 4.2's confirmation test must use that real import order, not the spike's pre-import provider installation. Histograms use unit `ms` with explicit bucket advice (`mcp.tool.duration`: 5, 10, 25, 50, 100, 250, 500, 1000, 2500, 5000, 10000; `mcp.lock.wait_time`: 1, 5, 10, 25, 50, 100, 250, 500). The `Meter` is fetched once at bootstrap (`metrics.get_meter("specmgr")`) into a module-level slot; the middleware's increments are slot-guarded (a `None` slot is a no-op, consistent with the Phase 3/Phase 5 division-of-labor bullet above). The stdout-safety requirement (ACC-001/ACC-003, Task 4.10) is specific to the **stdio** transport, where stdout is the JSON-RPC channel; `specmgr mcp` also serves `sse` and `streamable-http` (see `README.md`'s flags table), where stdout is not the protocol channel -- the `out=sys.stderr` redirection applies uniformly regardless.
- **Fail-open policy (runtime failures only)**: both the OTLP-exporter-unreachable case and a broken `Server.middleware` contract (a future SDK upgrade) must never break a tool call -- the server keeps operating normally, logging/telemetry disable themselves (fully or partially) with at most one stderr warning per failure episode, and a further single message is only emitted after a subsequent reconnect-then-drop cycle, never repeating while the condition persists. This is distinct from the static-config-validation rule above, which fails closed instead. **Implementation risk flagged, confirmed by spike**: Task 1a.4 (Phase 1; see Decisions Made) confirmed the installed 1.44.0 SDK's actual failure-logging behavior: the HTTP OTLP exporters log **per failed attempt within an export cycle, plus one final error per cycle** (with the production-default 10 s exporter timeout: 3x WARNING `Transient error ... retrying in N.NNs.` + 1x ERROR `Failed to export span/metrics batch due to timeout, max retries or shutdown.` = 4 lines per failed cycle), and the cycles repeat every `schedule_delay_millis`/`export_interval_millis` for as long as telemetry data keeps flowing -- all under the exporters' own module loggers (`opentelemetry.exporter.otlp.proto.http.trace_exporter` / `...metric_exporter`); the exporters return `FAILURE` without raising, so the SDK's own exception-logging paths (incl. `opentelemetry.sdk._shared_internal`'s built-in 20-second `DuplicateFilter`) never fire for an unreachable endpoint, and no SDK-provided episode de-duplication exists. Because the SDK logs no success at all, recovery is not observable from the log stream: achieving "at most one message per failure episode" therefore requires a thin wrapper around the configured OTLP exporter that tracks first-failure/recovery transitions itself (suppressing the exporters' own loggers while active) -- a bare `logging.Filter` on those logger names cannot do it. Phase 4's Task 4.5 implements de-duplication against that confirmed behavior. This work was moved from an earlier draft's Phase 5 into Phase 4, since it is squarely about the OTel exporter/SDK bootstrap Phase 4 already owns, not about the domain-level metrics instrumentation Phase 5 covers. Task 3.2 (Phase 3) additionally wraps its own middleware-append call in a minimal version of this same fail-open policy from the moment it lands, so the append itself can never crash `specmgr mcp` even before this phase's full policy exists; Task 4.3 upgrades that minimal guard into the complete behavior described above, rather than adding an unrelated, independent one.
- **Doc-cache hit/miss counters**: add counters directly to the shared `general/tools/_doc_cache.py`'s `DocCache` class (instruments all 12 per-domain caches at once) plus a `stats()` accessor the OTel meter reads. Since these are 12 independent per-domain singleton instances, not one shared instance, a single meter callback cannot discover them on its own -- Task 5.4 also adds a small registry (a module-level list/dict of live `DocCache` instances, populated at each domain's own cache-module import time) the callback iterates to attribute `mcp.cache.hit`/`mcp.cache.miss` per `mcp.domain`; this registry is new design work, not part of the existing `DocCache` mechanism. Task 1a.5's spike confirmed the observable-instrument mechanics Task 5.4 assumes, against the installed SDK 1.44.0 (see Decisions Made): callbacks are registered at instrument creation time (`meter.create_observable_counter(name, callbacks=[...])` -- the SDK instrument class has no public `add_callback`), are invoked only at collection/export time (never at registration), must return an iterable of `Observation` (the older `result(Observation)` callable protocol is gone in this version), and the returned values reflect the stand-in's state at collection time, with per-domain attribute series kept distinct and the default reader temporality CUMULATIVE (an unchanged collection re-reports the same cumulative value rather than drifting; DELTA only if explicitly requested via `preferred_temporality`, which must be keyed by the SDK's internal instrument classes). - **Domain-lock wait time**: add one new, shared timing helper in `telemetry/` (e.g. `record_lock_wait(domain, duration)`) and call it from each of the 13 `<domain>/tools/_lock.py` files' `_lock_for`/`<domain>_lock` context manager, rather than re-implementing the timing/recording logic independently 13 times -- this is what actually mirrors the `feat-99-list-item` "one shared helper, many wiring sites" precedent (a single shared implementation, many call sites), not 13 independent implementations of the same logic. **Implementation detail confirmed against the current code** (e.g. `req/tools/_lock.py`'s `req_lock`): every `<domain>_lock` context manager today is `lock = _lock_for(id_); with lock: yield`, which times *acquire-plus-hold*, not *wait*, if wrapped naively. Because this changes the acquire/release control flow of 13 concurrency-critical context managers, not just their timing, Task 5.6 must also assert every refactored context manager still releases its lock on every exit path -- including when the caller's `yield`-wrapped body raises -- as a regression check independent of the new timing metric itself. - **Redaction scope and limits (revised -- an unconditional "never, under any configuration" guarantee for free-text titles is not achievable)**: Phase 4's tracing does **not** create a new span in this feature's own middleware -- it only configures a `TracerProvider`/exporter so the SDK's already-present, built-in `OpenTelemetryMiddleware` starts actually exporting the spans it has always been (inertly) creating. That means essentially all trace spans, including `span.record_exception(e)`/`span.set_status(str(e))` on every exception, come from SDK-owned code, not this feature's own. Per stakeholder decision, Phase 6 implements a **global, `TracerProvider`-level `SpanProcessor`** (`on_end` hook; per Task 1a.3's confirmed finding -- the hook receives a `ReadableSpan` with no public mutation API, and the SDK locks the span's attribute container at `end()`, so the scrub must replace the span's private `_attributes` container and the exception `Event`'s private `_attributes` container with scrubbed copies, see Decisions Made) that scrubs every span the process creates -- including the SDK's built-in middleware's spans -- not only a filter local to this feature's own code (ACC-012), and the logging-side redaction runs inside every specmgr-installed `Handler`'s own formatter (both the console/stderr handler and the opt-in file-sink handler from Phase 2), so it scrubs every rendered record reaching those handlers regardless of which logger emitted it -- not only records whose logger name happens to be under `biz.dfch.specmgr` (application point pinned in this re-evaluation: **formatter level on the final rendered string**, because a handler-attached `logging.Filter` sees `LogRecord.msg`/`args`/`exc_info` but not the `exc_text` the formatter renders afterwards, and tracebacks embed absolute file paths; concretely, the JSON `Formatter` (console JSON + file sink) and a `RichHandler` subclass for the rich console format each pass their rendered output through the same scrub function). This matters because `SPECMGR_LOG_ENABLED=true` reconfigures the root logger, so third-party and MCP-SDK-internal loggers also emit through the same handlers once logging is enabled; scoping the filter to only specmgr's own logger namespace would leave that other output unredacted.
  **However**, this scrubbing has a real, verified limit that the original "no log record or span attribute ever contains ... a title" wording did not acknowledge. Absolute filesystem paths have a structural signature a regex can target (with known false-positive/negative risk, e.g. paths containing spaces, or non-POSIX/non-Windows-shaped strings). A document/artifact **title** does not: it is arbitrary free text with no distinguishing shape, so a generic `Filter`/`SpanProcessor` operating on an already-rendered string cannot know that a given substring *is* "the title" as opposed to any other quoted text. This is not hypothetical -- grepping the codebase confirms concrete existing call sites that already embed exactly this content in an exception's `str()` message, which the SDK's `record_exception(e)`/`set_status(str(e))` calls capture verbatim: `uc/models/v1/parser.py`'s `UcParseError(f"unrecognized H2 heading {node.title!r}")` (and its sibling `*ParseError` call sites using `node.title`/`child.title`), and `general/tools/delete.py`'s `DeleteError(f"failed to delete {path}: {ex}")` (`path` is an absolute `Path`). Redaction therefore has two distinct components, not one: (1) a *structured*-attribute guarantee -- this feature's own code (the middleware, the meter, the status resource) never attaches a full body/path/title as a dedicated attribute value, which is fully achievable since this feature controls what it names and sets; and (2) a *free-text* backstop -- the regex-based absolute-path scrub described above, plus a narrow, message-text-only rewording (Task 6.7) of the title-embedding exception call sites in **non-deprecated domains** (the verified mandatory set today: the 13 `UcParseError` sites in `uc/models/v1/parser.py`), carved out of the Explicitly-Out-Of-Scope exception-handling-convention exclusion (see Scope). The deprecated **ADR domain's 9 title-embedding sites** (`models/adr/v1/parser.py`'s `AdrParseError` x8 and `models/adr/v1/mutations.py`'s `AdrOptionNotFoundError` x1) are **explicitly excluded** from that rewording as an accepted residual gap -- the ADR domain is planned for phase-out (mirroring its exclusion from the `feat-107` cache), so its parse-error messages can still carry a title into free-text log/span content, and the path scrub still applies to them; path-embedding sites (`DeleteError`, the 12 domains' `<domain>/tools/_io.py` `*NotFoundError`-style messages, `feat/tools/_paths.py` -- ~25 verified sites) are scrub-covered in logs/spans and optionally reworded, since absolute paths are already disclosed client-side by the existing `specmgr://config` resource. ACC-004/ACC-012/ACC-013 above and the VCR acceptance criteria they back (VCR `0a1c2f63...` AC-003, VCR `54fd355f...` AC-007) are worded to match this achievable, two-component guarantee rather than an unconditional universal one. Task 1a.3's spike (Phase 1; see Decisions Made) answered the open question whether component (2)'s `SpanProcessor` can actually mutate an already-recorded span's attributes/exception-event text via public `opentelemetry-sdk` API, or must rely on undocumented internals: it cannot via public API (the `on_end` hook receives a `ReadableSpan` with no `set_attribute`, the span's `BoundedAttributes` is locked immutable at `end()`, and event `BoundedAttributes` are immutable from construction), so Task 6.1 is written against the confirmed private-container-replacement mechanism and its fragility notes (Task 6.3 therefore also adds a Task 4.4-style canary test asserting those private containers exist and the replacement is visible end-to-end on the installed SDK, so the fragility fails loudly in CI rather than silently leaking).

#### 2026-09-21 15:13:45.639Z - Phase 2 implementation pins: the rich format's `render_message` seam, the `exc_info`-derived `exception` field, and the file sink's append mode

Three implementation-level decisions from Task 2.1, each serving (not contradicting) the plan's pinned record shape: (1) **The rich format appends its structured fields in a `SpecmgrRichHandler.render_message` override, not a `format()` override**: rich's `RichHandler.emit` funnels both the plain-message path and the `rich_tracebacks` exception path through `render_message(record, message)` as the single message-text point, whereas `format()`'s output is discarded for exception records when `rich_tracebacks` is on (the SDK's own construction enables it) -- a `format()`-only override would silently drop the structured fields from exactly the error records that matter most; `render_message` is therefore the rich-format seam the Task 6.2 scrub hooks onto, next to `JsonFormatter.format` for the JSON path. (2) **The `exception` field is derived from the record's standard `exc_info` when no explicit `exception` extra is present**: the pinned shape says `exception` arrives as an `extra=` kwarg (Phase 3's middleware), but the SDK's own `logger.exception` records use the standard mechanism -- deriving `{type, message, traceback}` from `exc_info` keeps the pinned shape for those records instead of silently dropping their traceback; an explicit `exception` extra always wins when present, and a record carrying neither renders the field absent (the "emit only what is present" rule). The rich format renders the field as `Type: message` only, since `rich_tracebacks` already displays the `exc_info` traceback separately. (3) **The file sink opens in append mode (`mode="a"`) so a server restart does not truncate the previous session's records** -- the plan pins the sink's on/off gating and JSON-only output (ACC-009) but not its open mode.

#### 2026-09-21 07:55:43.000Z - Middleware is a pure pass-through when both features are off (enablement gating pinned)

The final pre-implementation review found that the plan gated metrics (Task 5.2, "no-op when disabled") and log records (`SPECMGR_LOG_ENABLED`) but never stated that the middleware's correlation-ID generation, error-response attachment, and Task 3.3's raw-exception-to-`MCPError` conversion are gated on enablement.
