# Feature: list_feat Cold-Scan Timeout

## Plan

### Overview

The `list_feat` MCP tool intermittently fails with `MCP error -32001: Request timed out` (GitHub issue #187). Reproduced in-session on 2026-10-03 (two consecutive `list_feat` calls against this worktree both timed out) and re-reproduced in-session on 2026-10-04 (the first call eventually returned, two subsequent concurrent calls timed out). The quantified root cause: `list_feat` performs a lock-free, full-directory sweep that fully parses every `<base>/*/README.md` on a cold cache (`python-frontmatter`/PyYAML frontmatter, pure-Python `markdown_it("commonmark")` body tokenizing, nested Pydantic validation) -- 348.6 s measured over this repo's 70-folder / 3.95 MB corpus at measurement time (2026-10-03; 71 folders / ~4.07 MB of READMEs at refinement time 2026-10-04), at roughly 10-13 KB/s on large READMEs (a single 146 KB README takes 24.0 s). The MCP client (OpenCode 1.18.34) gives up far earlier, and the server process the published `uvx biz-dfch-specmgr[mcp, similarity]` entry point starts is fresh per client session, so the process-local content-hash cache added by feat-107-doc-cache (issue #107, the same timeout symptom) never helps a session's first call. The warm floor -- full read plus blake2b content hash of the entire corpus with no parsing -- is 0.007 s, proving the parses, not the I/O, are the bottleneck. The design (settled with the maintainer 2026-10-03, refined 2026-10-04) is two-stage: (1) the request path never runs a full body parse -- `list_feat` resolves every folder from one file read plus a clean-cache peek (a valid full-parse entry or none, never parses), falling back to a fast frontmatter-level read (the same `parse_frontmatter` call `parse_feat` makes, plus the existing `first_h1` line scan) with an inline fallback for any path the warmup has not yet reached, so the very first call already returns the complete directory (`total` correct from call one) in well under any client request timeout, with zero full markdown-it/Pydantic body parses on the request path for any file, healthy or defective; (2) at MCP server startup, a crash-contained background warmup thread -- restructured by the 2026-10-04 refinement from the similarity-only thread the lifespan previously started (the hook was not a no-op: it already ran feat-134's similarity warmup, which full-parses every whole-body domain's corpus for embedding without warming the doc cache) into a single unified `specmgr-startup-warmup` daemon thread -- runs three phases in order: a frontmatter phase (every live `*/README.md` into a second, hash-validated, frontmatter-stage "dirty" `DocCache` instance, under a second for this corpus), a sequential full-parse phase (every path through the existing cache-backed `read_feat`, roughly 348 s for this corpus, in the background and off the request path), and then the unchanged feat-134 similarity warmup body -- so `list_feat`'s output converges to today's full-fidelity output within minutes of session start under a three-tier failure-visibility contract (frontmatter-level failures byte-identical to `get_feat` from call one; H1-level failures flagged from call one with dirty-stage text, converging byte-identical; body-level failures the documented transient), and `get_feat` calls additionally hit pre-parsed, warm documents. Per-phase opt-out flags (`SPECMGR_FEAT_WARMUP_DISABLED` for the feat phases, the existing `SPECMGR_SIMILARITY_DISABLED` for the similarity phase; no thread at all when both are set) and the deferred parse-dedup follow-up (O3) are recorded in the Design Notes and the ADR. Neither stage weakens ADR 33c5ab08-ff58-4c73-8c32-23abaf3838e3's "filesystem is the sole source of truth" invariant: every cached value is content-hash-validated on every access.

### Requirements

- REQ-001: The first `list_feat` call from a fresh server process (empty caches) over this repo's `.specmgr/feat` corpus (70 folders / 3.95 MB at the 2026-10-03 measurement, 348.6 s full-parse sweep measured pre-fix; the corpus grows over time) must return a complete page -- `total` equal to the on-disk folder count -- in under 5 s wall time, with zero full markdown-it/Pydantic body parses on the request path for any file (healthy, H1-defective, or body-defective alike -- the request path is frontmatter-plus-H1-scan only, so the bound is independent of corpus shape).

- REQ-002: The same bound must hold regardless of how far the background warmup (REQ-007) has progressed: any folder not yet in the frontmatter stage is resolved by the request path's own inline frontmatter read, so the entry count never lags the directory (what converges over time is each entry's validation depth, not its presence).

- REQ-003: The request path's per-file summary derivation must be bounded by the file's frontmatter and H1 -- the dirty stage's payload -- never by the body, so `list_feat`'s cost does not grow with corpus body size (ADR bfd76370's full cache only memoizes repeats within one process and cannot bound a first call; the dirty stage is what bounds it).

- REQ-004: Failure visibility must converge to today's exact output under a three-tier contract (the 2026-10-04 refinement, Option A): tier 1 (frontmatter-level -- malformed or missing YAML frontmatter, frontmatter schema violations) must appear as `<failed to parse>` rows with `error` text byte-identical to `get_feat`'s from the very first call, because the dirty stage runs the exact same `parse_frontmatter(text, FeatFrontmatter, domain="feat", stringify_metadata=...)` call `parse_feat` makes, so these errors are identical by construction; tier 2 (H1-level -- a missing `# Feature:` H1, or an H1 failing the `^Feature: .+$` alias check) must appear as `<failed to parse>` rows from the very first call (the dirty stage detects both cheaply via the existing `first_h1` line scan plus the alias regex) with a dirty-stage-specific `error` text that converges to byte-identical to today's full-parse sweep once the warmup's clean stage has passed them -- byte-identity from call one is deliberately sacrificed for these shapes, because their full-parse error text references the markdown-it-normalized body and cannot be produced without a full body parse; tier 3 (body-level -- everything deeper, including all folders that currently fail a full parse in this repo, 6 as of 2026-10-04: FEAT feat-5-md-model-parser (legacy Requirements shape), FEAT feat-29-dec-source-roles (missing Task List), FEAT feat-50-confluence (legacy task-item shape), FEAT feat-132-prb-update (legacy Updates timestamp form), FEAT feat-177-list-ref-feat (raw HTML inline token), FEAT feat-180-updates (stray list marker inside an UpdateEntry's content)) must appear as `<failed to parse>` rows with `error` text byte-identical to today's full-parse sweep once the warmup's clean stage has passed them; during the warmup window, a document with a broken body but well-formed frontmatter and H1 transiently appears healthy (the documented dirty-stage limitation, recorded in the ADR), and `get_feat` remains the full-fidelity authority throughout (it full-parses on demand, warmed or not), so a dirty-stage `list_feat` row may under-report a tier-3 defect during the window only.

- REQ-005: The paging contract is unchanged (ADR ec9f5262-9912-49d0-903f-fcfb54f28c13): `list_feat` scans the live directory on every call, materializes the complete list before paginating, and `total` always reflects the whole directory; `error_count` converges monotonically (non-decreasing) toward today's full-parse value as the warmup completes -- a row converges when its file has passed the clean stage, which happens for (a) the warmup's startup directory snapshot, (b) a tool-written file via the two-stage write-path warming, and (c) any file on its next on-demand clean read (e.g. a `get_feat`), so a folder created by hand edit after the snapshot converges at its first on-demand read, not earlier (the round-2 G2).

- REQ-006: `get_feat`'s contract is unchanged: it returns the fully parsed document, or `ParseFailureResult` for a document that exists but fails to parse, with its `raw`/`numbered`/`offset`/`limit` semantics intact -- the only difference is that warmed documents are served from a pre-parsed cache hit instead of an on-demand parse.

- REQ-007: The warmup must run as a daemon background thread started at MCP server startup (the lifespan hook in `server.py`), restructured by the 2026-10-04 refinement from the similarity-only thread it previously started (the hook was not a no-op -- it already called feat-134's `start_similarity_warmup`) into a single unified `specmgr-startup-warmup` thread running three phases in order: (1) a feat frontmatter phase (every live `*/README.md` read through the dirty-stage cache, under a second for this corpus), (2) a feat sequential full-parse phase (every path through the existing cache-backed `read_feat`, one after another, ~348 s for this corpus, in the background), and (3) the unchanged feat-134 similarity warmup body (`warmup_similarity_cache()` invoked inline); phase gating is per-phase -- `SPECMGR_FEAT_WARMUP_DISABLED` (new presence flag, default absent = feat phases run) gates phases 1-2, the existing `SPECMGR_SIMILARITY_DISABLED` gates phase 3, and when both flags are set no thread is started at all (a no-op, and the server runs exactly as before any warmup); the thread must be crash-contained: an unexpected per-file exception (e.g. a file vanishing mid-warmup, an `OSError`) is logged via the standard `logging` module (named thread, the feat-134 `specmgr-similarity-warmup` precedent: an unexpected per-file exception at WARNING with the path and `exc_info`, a phase start/finish at INFO -- the round-2 I2) and swallowed, never propagates out of the thread, and never prevents the server from serving or the warmup from reaching later files; parse failures (the three cacheable channels) are the normal, cacheable outcome and are stored like today; the feat phases must also be callable outside the lifespan -- `warmup_feat_caches()` is a plain, synchronously runnable function the thread body calls, returning a small per-phase summary (paths warmed, parse failures stored) for the phase-finish log line and the test assertions (the round-2 I4), so tests can drive the phases directly (the 2026-10-04 G2 testability decision).

- REQ-008: The dirty stage must be hash-validated exactly like the clean stage: a feat-local second `DocCache` instance (the same class, the same innermost-lock-ordering rule, the same reconcile/invalidate/move semantics) keyed by content hash, so an on-disk edit between the warmup's frontmatter phase and a `list_feat` call re-reads that file's frontmatter -- a stale summary is structurally impossible, mirroring ADR 33c5ab08's invariant at the frontmatter level; the dirty stage must store parse failures with the same `CACHEABLE_ERROR_TYPES` + fresh-exception reconstruction semantics as the clean stage (byte-stable `error` text across repeated calls), and its `parse_fn` must be exactly the two-step frontmatter derivation: the same `parse_frontmatter(text, FeatFrontmatter, domain="feat", stringify_metadata=...)` call `parse_feat` makes (so tier-1 error text is byte-identical by construction), followed by the existing `general.tools._similarity_text.first_h1` line scan plus the `^Feature: .+$` alias check (so tier-2 defects are detected cheaply without any markdown parsing).

### Design Notes

Measurements (2026-10-03, this worktree, `uv run --frozen python`): the cold full-parse sweep of all 70 READMEs -- exactly what `list_feat`'s cold path does today -- took 348.6 s, at roughly 10-13 KB/s on large files (slowest: feat-6-requirement-artifact 146 KB / 24.0 s, feat-32-sysrs 243 KB / 19.5 s); the warm floor (full read plus blake2b over the entire corpus, no parsing) is 0.007 s; a frontmatter-only sweep (read plus PyYAML frontmatter parse plus H1 line scan, no body parse) completes in well under 1 s for the whole corpus; the then-current full-parse failure set -- what today's `list_feat` reports as `error_count` -- was 5 of 70 folders: FEAT feat-5-md-model-parser (legacy Requirements shape), FEAT feat-29-dec-source-roles (missing Task List), FEAT feat-50-confluence (legacy task-item shape), FEAT feat-132-prb-update (legacy Updates timestamp form), FEAT feat-177-list-ref-feat (raw HTML inline token); all five had valid frontmatter and H1. The host has 120 cores, but the sweep is GIL-bound pure-Python parsing, so core count does not help today's serial code. Re-measured at the 2026-10-04 refinement: the corpus had grown to 71 folders (including this feature's own, created after the measurement) / 4,073,256 bytes of READMEs (~4.07 MB), and the full-parse failure set had grown to 6 -- the new sixth is FEAT feat-180-updates (a stray `- ` list marker inside an UpdateEntry's content: "text left over" at normalized body line 293; its frontmatter and H1 are valid, so it is a tier-3 body-level case). Issue #187 was also re-reproduced in-session on 2026-10-04: the first `list_feat` eventually returned, and two subsequent concurrent calls both timed out with `-32001` -- evidence the timeout is not first-call-only, consistent with the coexisting similarity warmup (below) holding the GIL against a cold request-path sweep.

The chosen design (settled with the maintainer 2026-10-03, refined 2026-10-04) is a two-stage cache plus a startup warmup. Stage 1 ("dirty"): a feat-local second `DocCache` instance whose `parse_fn` is the frontmatter-only read (the same `parse_frontmatter(text, FeatFrontmatter, domain="feat", stringify_metadata=...)` call `parse_feat` makes -- so tier-1 error text is byte-identical by construction -- plus the existing `general.tools._similarity_text.first_h1` line scan, a fence-aware plain scan already proven equivalent to markdown-it's `h1` extraction for parsed documents, plus the `^Feature: .+$` alias check on the scanned title), producing a small, frozen frontmatter-summary payload (the sources of the summary fields: `id`/`status` from the frontmatter, `title` from the H1, `ref`/`path` from the folder). It is hash-validated exactly like the existing full cache and stores failures with the same cacheable-error + fresh-exception semantics, so an on-disk edit re-reads that file's frontmatter; a stale summary is structurally impossible. Stage 2 ("clean"): the existing `DocCache` full-parse cache, unchanged. `list_feat`'s request path (feat-local, the generic `build_summaries` left untouched for the other 11 domains) resolves each folder by one file read plus `clean.peek_preloaded` (a valid full-parse entry -- document or cacheable failure -- or `None`, never parses), falling back to `dirty.read_preloaded` (which on a miss runs the cheap frontmatter derivation and populates the dirty stage -- the inline fallback), and builds each summary from whichever stage answered, per the three-tier contract (REQ-004): a clean success yields today's exact row, a clean failure yields a byte-identical failed row (the stored exception is reconstructed message-identical by the clean stage's own feat-162 fresh-exception semantics), a dirty success yields the frontmatter-derived row (correct `id`/`title`/`status`/`ref`/`path`; a tier-3 body failure not yet visible -- the documented transient), and a dirty failure yields a tier-1 or tier-2 failed row. Because the live directory scan always enumerates every folder and the dirty fallback covers any path the warmup has not reached, `total` is complete from call one: what improves as the warmup progresses is each entry's validation depth, not the entry count. The single-read-per-folder shape (passing the already-read text to both cache queries) follows the feat-107 Phase 6 TOCTOU standard: the exact text that gets hashed is the exact text that gets parsed, with zero intervening file I/O, so no new double-read race is introduced (a bare `peek(path)` plus the existing `read` would have re-read each cold folder and re-opened that race class).

The warmup (2026-10-04 refinement, O2) is a single unified daemon thread `specmgr-startup-warmup` started from `server.py`'s lifespan hook -- which was NOT a no-op: it already called feat-134's `start_similarity_warmup`, whose `warmup_similarity_cache` body walks every whole-body domain and, per candidate, runs the domain's own full text parser (the registry's `parse_text` adapter; for `feat` that is `parse_feat`) directly on the file text the embedding cache itself read and hashed -- without ever warming the `DocCache` (the embedding cache stores `(hash, vector, SimilarityText)` -- title/id/status plus the embedding text, not the parsed document -- and in an mcp-only install without the `similarity` extra it is empty by construction). Both caches compute the identical `blake2b(text.encode("utf-8")).digest()` over the full file text, so their hash values are directly comparable (the seam the deferred O3 dedup will use). The unified thread runs, in order: (1) the feat frontmatter phase (every live `*/README.md` through the dirty stage, under a second for this corpus -- so `list_feat` is fast from within a second of session start), (2) the feat sequential full-parse phase through the existing `read_feat` (~348 s for this corpus, in the background, off the request path), and (3) the unchanged `warmup_similarity_cache()` body inline. Phase gating is per-phase: the new `SPECMGR_FEAT_WARMUP_DISABLED` presence flag gates phases 1-2, the existing `SPECMGR_SIMILARITY_DISABLED` gates phase 3, and when both are set no thread is started at all (a no-op invariant the lifespan unit test asserts). `start_similarity_warmup` is replaced by a single `start_startup_warmup()` spawner (kept function-level-imported from `_lifespan`, the existing import shape -- no circular import: the spawner's `feat.tools` import resolves after `server`'s `mcp` object exists). Per the G2 decision, the feat phases live in `warmup_feat_caches()`, a plain, synchronously runnable function the thread body and the tests both call. The thread is crash-contained: per file, parse failures (the three cacheable channels) are the normal, cacheable outcome (both caches already store them and re-serve message-identical equivalents on hit -- feat-107's REQ-011 and feat-162), and any unexpected error (a file vanishing mid-warmup, an `OSError`) is logged via the standard `logging` module (named thread, the feat-134 precedent) and skipped, never killing the thread. The warmup enumerates a startup snapshot of the directory; correctness never depends on it reaching every folder -- REQ-002's inline fallback covers folders created after the snapshot, and the write paths warm both stages for tool-created folders (ACC-005's sub-case). Side benefit: `get_feat` calls during and after the warmup hit pre-parsed full documents, so an agent that lists and then reads a feature pays no parsing at all in the common case.

GIL contention (refined 2026-10-04): with the unified thread, at most one heavy background thread runs at any time during the warmup window (the pre-refinement reading had two in parallel), so concurrent `get_*`/`list_*` requests share CPU with the feat phases and then with the similarity phase, never with both. Total parse CPU is unchanged versus today for any session that uses the feat tools: in an mcp-only install a used session parses the feat corpus once per process either way (today on the request path, now in the background) -- a session that never touches a feat document now pays one background sweep it would not have paid today (bounded by the same ~348 s, daemon-only, and exactly what `SPECMGR_FEAT_WARMUP_DISABLED` opts out of -- the round-2 D2); in a similarity install the duplicate feat parse already exists today (the similarity warmup parses the feat corpus in the background AND the first `list_feat` parses it again on the request path) -- O2 only relocates the second parse and serializes the two phases. The one behavioral concession: in a similarity install the similarity warm state now arrives after the feat phases (delayed ~348 s on this corpus), so a `find_related`/`find_similar_text` call inside that window pays its demand-path cost (cold parse + embed + first-session model load) on the request path -- an exposure that exists today in every mcp-only install, and a lower-contention one than today's parallel setup during the same window. The default remains "always run" (unless `SPECMGR_FEAT_WARMUP_DISABLED` is set); request-preemptive pausing (the warmup idles while a tool call is in flight) is a GIL-contention refinement the Phase 100 ADR decides on or defers.

The three-tier failure-visibility contract (2026-10-04 refinement, Option A): the pre-refinement REQ-004 claimed missing-H1 failures would be byte-identical to `get_feat` from call one, which contradicted REQ-001's zero-full-parses claim, because the full-parse error text for a missing H1 is built from the markdown-it-normalized body ("...remaining text starts at line N of the normalized body (M line(s)) and begins with: ...") and cannot be produced without running `format_text` -- a full body parse. Option A reclassifies H1-level failures (missing H1, or H1 failing the `^Feature: .+$` alias check) as tier 2: flagged from call one (the dirty stage detects both cheaply) with a dirty-stage-specific `error` text, converging to byte-identical once the clean stage passes the file -- keeping the 5 s bound and the zero-full-parses guarantee unconditional and corpus-shape-independent. Option B (a dirty-stage full-parse fallback for H1-defect files) was rejected: it makes the 5 s bound corpus-shape-dependent (a 146 KB README with a missing H1 costs ~24 s to full-parse on the request path -- the very exposure #187 fixes) and reintroduces GIL contention for exactly the files a broken corpus contains. Tier 1 (malformed YAML, frontmatter schema violations) needs no fallback: both stages run the identical `parse_frontmatter` call pre-body, so these are byte-identical from call one by construction. The three tiers also time-qualify the list/get error byte-identity property (ADR 9080b37c, feat-162) for `feat` during the tier-2/tier-3 window (and permanently under `SPECMGR_FEAT_WARMUP_DISABLED`): `get_feat` remains the full-fidelity authority, and every user-facing text asserting the property unconditionally is on the doc-update scope (Task 110.140, the round-2 G1).

Testability (2026-10-04 refinement, G2): the ACC-001..005 suite is in-process -- `SPECMGR_FEAT_DIR` pointed at a fixture corpus deterministically generated at setup time into a per-test temp directory by a tests-space helper (no committed fixture bytes, never co-located with the live `.specmgr/feat` corpus, generation cost excluded from ACC-001's timing assertion -- the round-2 G3; the isolation pattern feat-134's `SimilarityTestCase` already establishes, including its `seed_feat` helper), both feat cache stages reset per test (`reset_feat_cache()` plus the new dirty-stage reset -- note the existing `tests/feat/` suite isolates by a fresh temp `SPECMGR_FEAT_DIR` per test rather than calling the reset, so the reset discipline is specific to the new in-process suite), the warmup driven by calling `warmup_feat_caches()` (and the spawner) directly and synchronously rather than through a real server, and ACC-001's "zero full body parses on the request path" proven by a parse-count seam on the clean-stage `parse_fn` (which the request path must never invoke; the warmup invokes it by design). The lifespan gets a unit test for the startup wiring (thread started, per-phase flag gating, both-flags-set => no thread) built on the same fixture (the round-2 G4: `SPECMGR_FEAT_DIR`/`SPECMGR_DOCS_DIR` patched to temp dirs, both feat cache stages reset, and `SPECMGR_FEAT_WARMUP_DISABLED` saved/restored alongside the existing `SPECMGR_SIMILARITY_DISABLED` restore -- otherwise the feat full-parse phase would walk the real 71-folder corpus in the test process and the `join(timeout=15)`-based assertions would break, since the similarity phase only starts after the feat phases). A real subprocess `specmgr mcp` server in CI was considered and rejected: the repo has no MCP-client test harness (every existing test calls tool functions in-process), pytest-xdist would multiply the spawn cost, and the child's lifespan inherits the similarity warmup unless `SPECMGR_SIMILARITY_DISABLED=1` is set in the child's environment (with CI's `--all-extras` install that means model load/download in a test child -- a flakiness vector). The true fresh-process end-to-end proof remains ACC-006: one-shot, manual, recorded in `### Updates`, not asserted in CI.

Options evaluated and rejected or deferred: (1) a pure frontmatter-only request path with no warmup -- simplest, but body-level failures would then never be visible in the listing (the legacy folders, and every future hand-edit breakage, would silently become healthy rows, regressing the `repair` skill's list-based discovery); subsumed by the two-stage design, which keeps it as the request path and adds the warmup for full fidelity. (2) A `stat()` (mtime/size) pre-check in the cache -- trims the warm path only (already 0.007 s) and does nothing for the cold sweep; explicitly deferred by feat-107. (3) A process-pool-parallelized cold sweep -- 348.6 s / N is still ~45 s at N=8, above typical client timeouts on small machines, adds pickling/error-channel complexity, and stays unbounded as the corpus grows. (4) A lazy per-page sweep -- breaks ADR ec9f5262's materialize-then-paginate contract. (5) A persisted/disk-backed warm cache -- carries the warm state across restarts, but a fresh checkout still pays one full cold sweep, and it adds serialization/invalidation/concurrency concerns; a deferred complement, not the primary fix. (6) A free-threaded (no-GIL) CPython 3.13t/3.14t runtime with explicit thread fan-out -- on this 120-core host it would bound wall time by the largest single file (24.0 s), but on a typical 4-8 core laptop it still lands at 44-87 s with no bound as the corpus grows; it is blocked today by pydantic-core (Rust, 2.46.4) lacking free-threaded support -- a hard dependency blocker to re-verify before any investment; and it is a deployment/runtime decision for every consumer, not a fix in this repo. Deferred on maintainer direction ("stay away from Py 3.14 for now", 2026-10-03). (7) A startup frontmatter-only warmup without the full-parse phase -- half of the chosen design; alone it would leave body failures permanently invisible (the same defect as option 1), so it ships as the first phase of the full warmup, not as a separate option. (8) Parallel feat + similarity warmup threads (the pre-refinement reading of the design, which misread the lifespan as a no-op) -- rejected at the 2026-10-04 refinement: two GIL-heavy background threads plus requests during the warmup window, nondeterministic phase ordering, and no benefit over the unified thread; subsumed by O2. (9) Full parse-dedup between the similarity warmup and the doc cache inside this feature (the O3 option: the similarity `embed_fn` consulting the `DocCache` by content hash -- possible because both caches hash identically -- with the `_EmbedFn` signature gaining the path) -- deferred to a separate follow-up feat: it is a feat-134 regression surface (`_EmbedFn` signature, per-domain lookup adapters, embedding-cache tests) that does not belong in the #187 fix, which stands on its own (the request path never full-parses regardless); this feature provides its `DocCache`-side enablers (`peek_preloaded`/`read_preloaded`), and the follow-up would additionally fix the `find_*` demand-path cold parse (a latent sibling of #187).

#### 2026-10-03T20:09:42.529Z - Settled the two-stage design with a startup warmup, with the maintainer

The maintainer proposed, and the discussion settled on, a startup-warming design: at MCP startup, all FEAT frontmatters are read into the doc cache first (the "dirty" stage), then all FEAT documents are sequentially fully read and parsed into the cache (the "clean" stage), and `list_feat` at any time serves what the cache holds. Refined during the discussion: (1) `list_feat`'s request path carries an inline frontmatter fallback for any not-yet-warmed path, so `total` is complete from call one -- what improves over time is each entry's validation depth, not the entry count; (2) dirty/clean is realized as a second, hash-validated, feat-local `DocCache` instance alongside the existing full cache, not as a flag; (3) the warmup thread is crash-contained (unexpected per-file errors go to stderr and never kill the thread); (4) body-level failure rows converge to byte-identical output with today's sweep once the clean stage passes them (the five currently-failing folders included), while frontmatter-level failures are flagged from call one. Free-threaded Python (3.13t/3.14t) was considered and deferred on maintainer direction (pydantic-core has no free-threaded build; machine-dependent worst case).
