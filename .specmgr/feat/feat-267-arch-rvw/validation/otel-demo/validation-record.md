# Phase 120 Validation Run 4: OpenTelemetry Demo (distributed cloud-native platform)

Task 120.100, validation run 4. The OpenTelemetry Demo ("Astronomy Shop") stands for the class "distributed cloud-native platform" of QA 0.0340. Validation of the Architecture Model (TXT 30983f27, Draft 0.5) and the checklist matrix (TXT 23ded6d8, Draft 0.12) against it. This is a validation of the catalogue, not a review of the demo. Ratings appear where they test a catalogue rule. The demo is a demonstration system, and its own requirements call it "production-lite". What it lacks as a production system is recorded as a finding about evidence and outcome. It is not a reason to skip a cell.

## 1. Scope

- System: OpenTelemetry Demo, `open-telemetry/opentelemetry-demo` branch `main`, commit `fc7f2a68` (2026-11-21). Latest release 3.1.0 (2026-09-18). Kubernetes deployment: `open-telemetry/opentelemetry-helm-charts` `main` commit `5e7ca838`, chart `charts/opentelemetry-demo` 0.42.7 (appVersion 3.1.0).
- Architecture class: distributed cloud-native platform. About 20 application services in 12 languages (legend of architecture.md), gRPC (`pb/demo.proto`) and HTTP between them, one Kafka topic (`orders`), PostgreSQL, Valkey, flagd for fault injection, an OpenTelemetry Collector with Jaeger, Prometheus, OpenSearch and Grafana. Docker Compose in layers (`compose.yaml` core, `compose.full.yaml` Kafka and consumers, `compose.observability.yaml`, `compose.agent.yaml`) and the Helm chart.
- Review type used for the test: pre-release (baseline `main` as the candidate for the next release). Minimum evidence: Documented for design criteria, Demonstrated for practice criteria.
- Safety gate: not safety relevant. Justification: a demonstration web shop. Payment, shipping and email are simulated, it controls no equipment, and no decision with a safety consequence depends on its output.
- Evidence sources (all read with `gh api` at the commits above): README.md, AGENTS.md, `.env`, `compose*.yaml`, `pb/demo.proto`, `src/checkout/main.go`, `src/checkout/kafka/producer.go`, `src/accounting/Consumer.cs`, `src/fraud-detection/.../main.kt`, `src/flagd/demo.flagd.json`, `src/otel-collector/otelcol-config*.yml`, `src/frontend-proxy/envoy.tmpl.yaml`, `src/postgresql/init.sql`, `test/telemetry/README.md`, `.github/workflows/run-telemetry-tests.yml`, Helm `values.yaml`, `Chart.yaml`, `templates/_objects.tpl`. The architecture docs are not in the demo repository: `open-telemetry/opentelemetry.io` `content/en/docs/demo/architecture.md` and `requirements/{architecture,system}.md` (branch `main`, read 2026-11-22).
- Model: `workspace.dsl` in this folder (1109 lines, generated by a script in the session scratchpad, not kept). 32 containers, 4 actors and external systems, 86 relationships, one Kubernetes deployment environment with 32 deployment nodes (cluster, 30 workloads, LLM endpoint). Checked with the Structurizr MCP: `validate` OK on the first run. The check ran on the file text with the leading whitespace removed (the DSL ignores indentation; the text is 45 KB). `inspect` reports two errors:
  - `The software system "Astronomy Shop" has containers, but is missing documentation.`
  - `The software system "Astronomy Shop" has containers, but is missing decisions.`

## 4. Worked example VP06 x RE applied

This is the first run where these criteria bite. Results are recorded as perspectives: the system-level rating on the deployment node "Kubernetes cluster", node-level results on the pods of checkout, frontend-proxy, kafka, astronomy-db, valkey-cart and jaeger.

| Criterion | Applicability | Evidence | Outcome | Rating |
|-----------|---------------|----------|---------|--------|
| VP06-RE-090 Targets | Applicable | Missing: no availability or recovery target in the repo, in opentelemetry.io `docs/demo/requirements/` or in the chart (searched) | empty | Unassessable |
| VP06-RE-100 Single points of failure | Applicable | Sufficient: Helm `values.yaml` (Documented, Author). `default.replicas: 1`, no component overrides it; Kafka `KAFKA_CONTROLLER_QUORUM_VOTERS 1@kafka:9093`. The replica check is a grep over the values, repeatable (Demonstrated, Tool) | Unsatisfactory: every node, including the only ingress, the only order orchestrator, the only broker and the only database, has no redundant counterpart | Unsatisfactory |
| VP06-RE-110 Failure domains | Applicable | Sufficient: `default.schedulingRules.affinity: {}`, no topology spread, no PodDisruptionBudget, `_objects.tpl` renders only `Deployment`, `Service`, `Ingress` | Unsatisfactory: no redundant instance exists to place; placement is left to the scheduler | Unsatisfactory |
| VP06-RE-120 Detection and failover | Applicable | Sufficient: compose has health checks for most services; Helm values set no `livenessProbe` or `readinessProbe` for any component (grep) | Unsatisfactory: under Helm, Kubernetes restarts a pod only when its process exits (Inferred, platform default); no failover with one replica | Unsatisfactory |
| VP06-RE-130 Recovery of state and data | Applicable | Sufficient: astronomy-db, kafka, valkey-cart are Deployments with no PersistentVolumeClaim in the templates (Inferred from `_objects.tpl`); Jaeger `storage.type: memory`; OpenSearch `persistence.enabled: false` | Unsatisfactory: orders in astronomy-db and in the topic are lost when a pod moves; no backup design | Unsatisfactory |

| VP06-RE-150 Failure tests (practice) | Applicable | Insufficient: 21 fault flags (Documented) and `run-telemetry-tests.yml` on every PR (Pipeline), but the tests check that telemetry arrives (`test/telemetry/README.md`), not recovery | empty | Unassessable |

## 5. Findings for the catalogue

| ID | Finding | Proposal | Affects |
|----|---------|----------|---------|
| C-01 | V-03 confirmed and refined. With the class "distributed platform" every RE cell applies, and no tailoring justification was needed. But the class does not say what the system is for. The demo is "production-lite" by its own requirements, so seven RE ratings against production expectations read as harsh, although they are correct | Add to section 3 next to the system class: the intended operating profile (production, production-lite, demonstration, prototype). It does not change a rating. It is the context for the final evaluation (section 7.1: "knock-out criteria depend on the environment") | Checklist sections 3, 5.2 (with V-03) |
| C-02 | VP06-RE-100 asks "what happens to the stated availability target". Without a target (RE-090 Unassessable) the second half cannot be answered, but the first half (which nodes have no redundant counterpart) is fully answerable and Tool-checkable | Split the question: (a) list the nodes and shared services without a redundant counterpart, (b) their effect on the target. Rate (a) alone when the target is missing, and link the finding to RE-090 | Checklist section 10, VP06-RE-100 |
| C-03 | In run 1 VP06-RE-110 was Inapplicable because there is no redundancy by design. Here the same reasoning would hide the main gap: a platform that can run on many nodes, with no redundancy at all | Rule: RE-110 is Inapplicable only when the scope has exactly one failure domain by design. Missing redundancy on a multi-node platform is Unsatisfactory. The Architecture Model 8.3 needs a convention for placement that the configuration leaves open: today `failure.domain.host` cannot be set on a pod, because no value is known, and values must not be empty | Checklist section 10 VP06-RE-110; Architecture Model 8.3 |
| C-04 | Two deployment descriptors (Docker Compose, Helm) with different health behaviour: compose defines health checks, the chart defines no probes. The model holds one environment. A reviewer who models only one sees only half. Open: the flag `failedReadinessProbe` acts on a cart readiness probe that the Helm values do not define | Rule for VP06: every shipped deployment descriptor is a separate deployment environment in the model, or the scope names the one that is reviewed | Checklist section 3 (scope baseline), Architecture Model 8.1 VP06 |
| C-05 | V-07 confirmed on a second system. The search for targets covered the repo, the external requirements pages and the chart. It found nothing, and RE-090 ends Unassessable although the answer ("no target exists") is certain. The same holds for PE: no latency or throughput target | Apply the V-07 rule: a complete search that finds nothing is Evidence Sufficient, Outcome Unsatisfactory | Checklist section 7.1 (V-07) |
| C-06 | V-02 refined. For inter-process concurrency the dynamic view works: order, the failure point (charge before ship) and parallel consumers are visible, and nested parallel blocks validate. Not visible: synchronous wait on an async producer, `RequiredAcks NoResponse` ("may swallow failed messages", `producer.go`), consumer group semantics, auto commit, the missing compensation after a shipping failure. VP04 x RE is a P cell without criteria, and the main reliability gap of the system is there | Section 8.1: VP04 "partial for inter-process message flow, none for threads, delivery guarantees and compensation". Write VP04 x RE criteria: delivery guarantee per channel, idempotency of consumers (accounting is idempotent: duplicate order skipped on a unique-key violation), compensation of a multi-step flow, timeouts per call | Architecture Model 8.1 (V-02); matrix VP04 x RE |
| C-07 | VP06-RE-150 separates fault injection from failure tests correctly. The demo has 21 fault flags (paymentUnreachable, kafkaConsumerDead, cartFailure, ...) that exist to show telemetry, and a PR pipeline that tests telemetry. Neither is a recovery test result | Keep. Add to the expected evidence of RE-150: "a fault injection capability is not a test result" | Checklist section 10 VP06-RE-150 |
| C-08 | V-08 tested. For a distributed platform, scalability by instances is the right concern, so VP06 x FL as P fits, unlike specmgr. But the carrier "instance count" shows the configured default (1), not the capacity to scale: the stateless services could run with more replicas, the Kafka broker, astronomy-db and valkey-cart could not without redesign | V-08 is class-dependent (supports V-03 default tailoring per class). Architecture Model 8.2 FL: the instance count is the configured state; a scaling property (for example `scaling.mode` stateless or stateful, `scaling.max`) is needed. Key to be confirmed | Architecture Model 8.2, 8.3 (with V-08) |
| C-09 | VP07: the demo ships observability, and the model can show it as containers and relationships (collector, four backends, OpAMP, scrape relationships). But telemetry edges are ordinary relationships. They swamp the functional container view (21 OTLP edges). The run used an element tag and a filtered view | Architecture Model 8.1 VP07: "monitoring design partial: containers plus a relationship tag for telemetry flows (key to be confirmed), excluded from VP02 views". Health checks and alert rules stay text | Architecture Model 8.1, 8.3 |
| C-10 | CO and the evidence policy: the architecture document lives in another repository (opentelemetry.io) and is out of date: it names recommendation as Python, the code is Java with Spring Boot 4 (`.chloggen/1368-...yaml`). The rule "current against the review baseline" (section 7.1) caught it, but the catalogue does not say how to baseline evidence from a second repository | Section 8.2 provenance: evidence from outside the reviewed repository carries its own repository, commit or date, and is checked against the code baseline before use | Checklist section 8.2 |
| C-11 | SE: trust boundaries. The convention allows one `trust.boundary` value per element. The demo has only one boundary (the cluster), so the model shows no inner boundary, which is the finding: shop and admin plane (flagd-ui can enable `emitRawPii`) share one listener without TLS; gRPC with insecure credentials, Kafka PLAINTEXT, PostgreSQL `sslmode=disable`; fixed secrets (`SECRET_KEY_BASE` in compose, DB passwords in `init.sql` and Helm values); collector with the docker socket as user 0:0. The inspection cannot tell the two apart | Supports option (c) of V-05: inspection as a warning, the decision check by a separate query of the decision store | Checklist 11.8 (V-05) |
| C-13 | Several results for one criterion in one model: RE-100 is on the cluster node and on four pods. The criterion record has one rating per scope.
