# Phase 120 Validation Run 2: AERIS-10 (safety-relevant cyber-physical system)

Validation run 2 of Task 120.100. AERIS-10 is the safety-relevant cyber-physical system of QA 0.0340. The run tests the Architecture Model (TXT 30983f27, Draft 0.5) and the checklist matrix (TXT 23ded6d8, Draft 0.12) against a real hardware-heavy system. The focus is the Safety gate (checklist 5.2), the home cell XV x SA, Regulation, Location, Reliability, Concurrency, and whether C4 can represent the split between boards, FPGA, MCU and host software. This is a validation of the catalogue, not a review of AERIS-10. Ratings appear only where they test a catalogue rule.

All facts come from the repository `NawfalMotii79/PLFM_RADAR`, read with `gh api` at commit `62d4c556508927a4192acca24422bd16a979c7dc` (branch `main`, 2026-10-14). Paths below are relative to that repository. Gerber files, board binaries, `.dwg`, `.xlsx` and PDF reports were not read.

## 1. Scope

- System: AERIS-10, open-source 10.5 GHz pulse LFM phased-array radar. Baseline `main` at `62d4c55`. Status "Alpha" (README.md badge), "Pre-Hardware Readiness" (docs/index.html).
- Architecture class: safety-relevant cyber-physical system. Five boards (main, frequency synthesizer, power, 16 PA boards for AERIS-10E, antenna), an Artix-7 FPGA, an STM32F746 MCU, a Python host GUI.
- Variant: AERIS-10E (32x16 waveguide array, 16 x 10 W QPA2962 GaN PAs) with the 50T production board and FT2232H USB. The repository also holds AERIS-10N (8x16 patch, about 1 W x 16), a 200T premium dev board with FT601, and two Trenz dev targets (9_Firmware/9_2_FPGA/constraints/README.md). See A-05.
- Review type used for the test: pre-release. Minimum evidence: design Documented, practice Demonstrated (checklist 8.2). Reason: the project ships designs and seeks beta testers and a crowd-funding campaign (README.md Contributing, 1_Project_Description/Project_Description.docx "What's in Progress").
- Safety gate: safety relevant. Justification: AERIS-10E radiates up to 16 x 10 W at 10.5 GHz into a high-gain array, with high-current PA rails, a rotating antenna and a documented GaN thermal-runaway risk (README.md Technical Specifications; main.cpp handleSystemError comment). See A-01.
- Evidence sources: README.md, CONTRIBUTING.md, Licence, docs/*.html, docs/artifacts/*.md, 1_Project_Description/Project_Description.docx (text extracted), 2_Functional Diagram & Interconnection Matrices/RADAR_V6.drawio (labels extracted), Eagle XML net names of 4_6_Schematics/MainBoard/RADAR_Main_Board.sch and PowerBoard/PowerBoard.sch, 9_Firmware (main.cpp, radar_system_top.v, plfm_chirp_controller.v, radar_transmitter.v, run_regression.sh, GUI v7, radar_protocol.py, MCU tests, cross-layer tests), .github/workflows/ci-tests.yml, GitHub Actions run 38498070468 on `62d4c55`.
- Not readable: 9_Firmware/9_1_Microcontroller/9_1_2_C_Cpp_Algorithms/STM32_ALGO.docx (not a valid zip file), 3_Power Management/Power Management V6.xlsx (not read). The Vivado build reports live on a remote host (docs/reports.html: `~/PLFM_RADAR_work/...`), not in the repository.
- Model: `workspace.dsl` in this folder. Checked with the Structurizr MCP: `validate` OK after two fixes (a wrong hierarchical identifier for an infrastructure node, and container instances without identifiers, which cannot be the source of a deployment relationship). `inspect` with scope `softwaresystem` reports three errors:
  - `The software system "AERIS-10" has containers, but is missing documentation.` Expected.
  - `The software system "AERIS-10" has containers, but is missing decisions.` Expected and true: the repository has no decision records at all (confirms V-05 from the other side).
  - `The deployment node "Field installation AERIS-10E/Public Internet" is missing a description.` A modelling slip, left in place so that the recorded result stays reproducible.

### C4 mapping decision for the hardware

| Thing | C4 construct | Reason |
|-------|--------------|--------|
| FPGA bitstream, MCU firmware image, host GUI | Container | Each is a separately built and loaded unit that executes code. Property `deployment.unit` names the unit (bitstream, firmware image). Key is not in Architecture Model 8.3 |
| FPGA modules, MCU modules, GUI modules | Component | Source modules with a clear responsibility (chirp controller, CFAR, health monitor, ADAR1000 manager, protocol) |
| Recordings | Container (Database) | HDF5 files on the host |
| Boards, the radar unit, the FPGA and MCU devices, the host PC | Deployment node | Physical carriers. 16 PA boards are one node with instance count 16 |
| RF and analog chips (DAC, mixer, ADAR1000, ADTR1107, ADF4382, AD9523, PA, regulators, antenna, stepper) | Infrastructure node | They do not run code from this repository but are configured by it and carry the signal and energy path |
| RF energy path, PA rails, enable lines | Relationships between infrastructure nodes and from container instances to infrastructure nodes | The only place in C4 where the hazard source and the safety function chain can be drawn |
| Exposed person | Person "Bystander" (Inferred) with a relationship from the transmitter | C4 has no element for an affected non-user; a relationship to a person has no defined meaning as an energy path |

It works for structure: `validate` accepts every construct, and the deployment view is the most informative view of the model. It fails for meaning: the context and container views show no hazard source, no RF path and no safety function. See A-03 and A-04.

Observations:

- VP06-RE-120 asks "how long does failover take". For AERIS-10 the designed response is a latched safe stop with manual reset (main.cpp lines 850-857). The criterion is answerable, but its wording assumes redundancy. The safe-state question belongs to SA and has no criterion. See A-08.
- VP06-RE-090 ends Unassessable after a complete search. Same pattern as V-07, confirmed.
- VP06-RE-150 shows a gap in the evidence policy: a Measured result exists, produced by a pipeline, but it is about a replica. See A-07.
- Seven perspectives on one node parsed without an error. Confirms V-10.

## 5. Findings for the catalogue

| ID | Finding | Proposal | Affects |
|----|---------|----------|---------|
| A-01 | The Safety gate decided "safety relevant" easily, but its text does not cover the hazard. It speaks only of software that controls equipment or influences decisions. It names no hazard types (RF exposure, electrical energy, thermal, moving parts) and does not ask who is protected. AERIS-10 has a "Safety Architecture" (docs/release-notes.html Gap 3, f3bbf77) whose stated purpose is to protect the PAs ("any fault that can damage the PAs", main.cpp handleSystemError). A reviewer can read equipment protection as safety. Extends V-09 in the other direction: V-09 found the gate too narrow for development tools, A-01 finds it too vague for energy hazards | Add two bullets to the gate: (1) a system that emits or controls energy that can harm people (radio frequency, electrical, thermal, mechanical) is safety relevant; (2) the justification names the protected party (people, equipment, environment), and protection of equipment alone does not make the SA column satisfied. Source to be confirmed (IEC 61508-1 hazard and risk analysis; ISO 12100 for the machine part) | Checklist 5.2, Architecture Model 8.2 (SA carrier) |
| A-02 | The home cell XV x SA has no criteria. The catalogue defines criteria only for VP06 x RE (section 10). With the SA column switched on, the reviewer has nothing to apply, and "hazard analysis" is named as a model kind (section 4, XV row) without minimum content. For AERIS-10 no hazard analysis exists; the catalogue cannot even say which SA criterion records that absence | Write XV-SA-090 ff. in the section 10 style: hazard identification and the hazard list (090), safety targets and integrity (100), the list of safety functions with their safe state (110), allocation of each safety function to elements across hardware and software (120), independence of the safety function from the mission function (130), verification of each safety function on the real element (140). ## 6. Open

- Hazard facts that are Inferred and need an RF or safety engineer: the EIRP and safe distance of AERIS-10E; whether average power rises with the host-set chirp timing; whether a hardware interlock exists outside the two schematics searched (PA board, enclosure, external switch). The 8x16 patch variant (about 1 W x 16) may give a different gate justification.
- Regulatory facts: which licence or authorisation the 10.5 GHz band needs in a given country; whether export control applies to a 20 km phased-array radar. Not in the repository, not checked.
- The safe-mode path after more than 10 non-critical errors (main.cpp lines 953 and 2037-2059: `system_emergency_state` stays false, so the blink loop is skipped and the main loop continues) was read in the code only. Not run, not confirmed as a defect of AERIS-10.
- Not read: STM32_ALGO.docx (invalid zip), Power Management V6.xlsx, the PDF reports, the Vivado reports on the remote host, the `develop` branch (CI runs on `main` and `develop`; the latest `main` run fails only in ruff lint).
- The C4 mapping covers one variant. A second deployment environment for AERIS-10N or for the 200T board was not modelled.
- None of the proposals is applied. They wait for the other validation runs (enterprise application, cloud-native platform), so that a cell is not changed on data points that share a bias towards technical systems.
